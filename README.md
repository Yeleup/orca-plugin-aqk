# Agent Queue — плагин Orca (orca-plugin-aqk)

Плагин Orca «Agent Queue» (id `agent-queue`): очередь задач агентов agent-queue-kit внутри Orca. Пока это заготовка:
манифест, каркас панели с экранами, воркер с общим слоем трёх систем (каталог данных, id координатора, запуск команд,
поиск CLI Orca) и тесты. Что плагин делает, описывают ТЗ и план MVP в `docs/mvp/`.

## Требования

- Orca 1.4.273 или новее на macOS, Windows или Linux. Манифест требует эту версию (`engines.orca` — `>=1.4.273`), и
  более старая Orca плагин не загружает.
- git.
- `gh` с выполненным входом (`gh auth login`).
- Агенты из настроек проекта (например Claude Code или Codex), установленные и с выполненным входом.

## На компьютере пользователя

Воркер плагина получает от Orca урезанное окружение: только `PATH`, `HOME`, `USERPROFILE`, язык и часовой пояс,
временные каталоги, `XDG_RUNTIME_DIR`, адреса D-Bus и ssh-agent и системные переменные Windows (`SYSTEMROOT`,
`SYSTEMDRIVE`, `WINDIR`, `COMSPEC`, `PATHEXT` …). Переменных вроде `LOCALAPPDATA`, `XDG_DATA_HOME`, `ProgramFiles` и
`ORCA_CLI_COMMAND` в нём нет, поэтому то, что они называют, плагин узнаёт у системы сам.

**Каталог данных.** Своё состояние на компьютере плагин держит вне репозиториев, в месте для данных приложений этой
системы:

| Система | Каталог данных |
|---|---|
| Linux | `$XDG_DATA_HOME/orca-agent-queue`, без `XDG_DATA_HOME` — `~/.local/share/orca-agent-queue` |
| macOS | `~/Library/Application Support/orca-agent-queue` |
| Windows | `<Local AppData>\orca-agent-queue`: папка Local AppData, как её называет Windows (по умолчанию `%USERPROFILE%\AppData\Local`; локальный профиль, не перемещаемый) |

В нём файл `coordinator-id` — id координатора этого компьютера: случайный UUID, без имени компьютера и пользователя.
Воркер создаёт его при первом запуске и дальше только читает; не удаляйте и не копируйте его на другой компьютер: у
каждого компьютера свой id. Если каталог недоступен или в файле не id, воркер всё равно стартует, пишет причину в
журнал (`orca plugin logs`) и файл не трогает. Пути, которые плагин строит, — с разделителем своей системы: на Windows
путь от git (`C:/…`) и от Orca (`C:\…`) — один и тот же путь.

**Команды.** git, `gh` и CLI Orca плагин ищет в PATH так же, как оболочка системы (на Windows — с расширениями из
`PATHEXT`, файлы `.cmd` и `.bat` идут через `cmd.exe`), относительные пути — от рабочего каталога запуска. У каждого
запуска плагин знает код выхода, вывод, время начала и длительность; весь вывод можно писать в файл, а в памяти от
большого вывода остаются начало и конец. Вывод не в UTF-8 на Windows читается в кодовой странице консоли. Команда
тестов проекта идёт оболочкой системы: `/bin/sh -c` на macOS и Linux, `cmd.exe /d /s /c` на Windows; на Windows —
команда для Windows из настроек проекта, если она задана, иначе основная. Команда, которой нет, — ошибка с причиной, а
не успешный запуск. `cmd.exe` не работает в сетевом каталоге (`\\сервер\ресурс\…`): такой запуск — ошибка с причиной.
Запуск, который не уложился в отведённое время, останавливается вместе со всеми процессами, которые он запустил.

**CLI Orca.** `ORCA_CLI_COMMAND` до воркера не доходит, и плагин ищет CLI Orca сам, по порядку:

1. `ORCA_CLI_COMMAND`, если она всё же задана;
2. по имени в PATH: `orca-ide` на Linux, `orca` на macOS и Windows. Голый `orca` на Linux плагин не запускает никогда —
   вне терминалов Orca это экранный диктор GNOME;
3. известные пути CLI в установке Orca: сначала CLI той Orca, в которой работает воркер (в ресурсах рядом с её
   программой — где бы Orca ни стояла), потом обычные места установки:

| Система | Известные пути (по порядку) |
|---|---|
| Linux | `<каталог Orca>/resources/bin/orca-ide`; `~/.local/bin/orca-ide`; `~/.cache/orca/appimage/launcher/orca-ide` (AppImage); `/usr/bin/orca-ide` (пакеты deb и rpm); `/opt/Orca`, `/opt/orca-ide`, `/opt/orca` — `resources/bin/orca-ide` |
| macOS | `<Orca>.app/Contents/Resources/bin/orca` запущенной Orca; `/usr/local/bin/orca`; `~/.local/bin/orca`; `Orca.app/Contents/Resources/bin/orca` в `/Applications` и в `~/Applications` |
| Windows | `<каталог Orca>\resources\bin\orca.exe`; `<Local AppData>\Programs\Orca\resources\bin\orca.exe`; `<системный диск>\Program Files\Orca\resources\bin\orca.exe` |

Найденный CLI должен ответить на `status --json` (`"ok": true`) за 20 секунд, иначе плагин берёт следующий. Не нашёлся
ни один — результат «CLI Orca не найден» с причиной: что и где искали.

## Установка

Из репозитория, CLI Orca (на Linux он называется `orca-ide`, на macOS и Windows — `orca`):

```sh
orca-ide plugin install Yeleup/orca-plugin-aqk
```

Orca ставит новейший тег версии `vX.Y.Z` (без тегов — ветку по умолчанию) и сначала показывает, какой доступ получит
плагин: `trusted-worker` — свой процесс Node.js с правами пользователя. Установка завершается той же командой с
`--approve <отпечаток>`, который Orca печатает. Когда плагин появится в каталоге Orca, его ставят и обновляют оттуда
(запись каталога готовит команда релиза — раздел «Релиз»).

## Устройство

- `orca-plugin.json` — манифест: id `agent-queue`, имя «Agent Queue», `trusted-worker`, точка входа `src/worker.ts`,
  панель «Agent Queue» в правой боковой части Orca и настройка «Interface language» (`interfaceLanguage`: English или
  Русский, по умолчанию English); доступ — только к своим настройкам (`settings:own`).
- `src/panel.tsx` и `src/ui/` — панель на компонентах Orca, в светлой и тёмной теме Orca. Открывается на «Очереди»:
  заголовок «Agent Queue», выбор проекта из подключённых (список даёт воркер; пока подключённых нет — их даст
  подключение проекта), меню «Проверка проекта», «Начать MVP», «Настройки», «Подключить проект». Каждый пункт
  открывает свой экран («Начать MVP» — «Старт MVP», «Подключить проект» — «Подключение проекта»). Все девять экранов
  ТЗ есть; кроме «Очереди», они пока заготовки — заголовок и вверху «Назад» к «Очереди», данные и свои состояния им
  дают задачи их функций. Пока воркер не ответил, экран показывает заготовки строк; ответ с ошибкой — текст ошибки
  и «Повторить», который повторяет запрос. Панель занимает правую боковую часть Orca во всю её ширину: эту ширину
  задаёт пользователь, плагин её не задаёт и не меняет. Экраны не построены под одну ширину; на доске дизайна панель
  нарисована шириной 390 и 420.
- `src/i18n/` — каталоги строк панели на английском и русском: все тексты экранов только оттуда, ключи в обоих
  каталогах одни и те же. Язык — настройка плагина; её смена (в настройках Orca) сразу меняет язык открытой панели.
- `src/protocol.ts` — запросы панели к воркеру (`plugin.request`) и события воркера для открытых панелей.
- `src/worker.ts` — воркер плагина: отвечает панели (подключённые проекты — `projects.list`), при запуске находит
  каталог данных и id координатора. Orca сама транспилирует TypeScript панели и воркера при загрузке: сборки нет,
  зависимостей во время работы нет.
- `src/platform/` — общий слой трёх систем: `machine.ts` — компьютер, на котором работает воркер (система, окружение,
  часы, файлы, запуск процессов; тесты подставляют поддельный), `files.ts` и `process.ts` — файлы и запуск процессов
  настоящего компьютера, `folders.ts` — папки системы, которых нет в окружении воркера, `paths.ts` — каталог данных и
  пути worktree и файлов, `coordinator-id.ts` — id координатора, `run.ts` — запуск команд и команды тестов проекта (её
  настройки задача `project-config` берёт из `.agent-queue.json`), `orca-cli.ts` — поиск CLI Orca.
- `src/node.d.ts` — типы встроенных модулей Node.js, которыми пользуется плагин: пакета `@types/node` нет.
- `src/testing/` — поддельный компьютер для тестов: любая из трёх систем, файлы в памяти, записанные запуски, часы;
  временный домашний каталог, в котором тесты запускают настоящий воркер.
- `src/**/*.test.ts(x)` — тесты плагина на `orca/testing` (поддельный хост Orca), их запускает `orca plugin test`;
  `src/panel.check.ts` — сценарии панели для `orca-ide plugin check .` (английский, русский, тёмная и светлая тема,
  ошибка, воркер как есть).
- `tests/*.test.mjs` — тесты поставки, workflow и релиза: манифест, подготовка worktree, `plugin inspect` чистой
  выгрузки коммита, шаги workflow GitHub Actions, команда релиза.
- `scripts/setup.mjs` — подготовка worktree (`setup` в `orca.yaml`).
- `Makefile` и `scripts/make-test.sh` — `make test`: настройки и сам прогон с записью итога.
- `.github/workflows/plugin.yml` и `scripts/ci.mjs` — проверка плагина на трёх системах в GitHub Actions.
- `scripts/release.mjs` — команда релиза: запись для каталога Orca.
- `package.json` — только инструменты разработки (TypeScript для проверки типов).

## Разработка

```sh
npm ci --no-audit --no-fund --no-bin-links   # подготовка: TypeScript в node_modules/, без bin-ссылок
make test                                    # манифест, типы, тесты — с записью итога для очереди агентов
orca-ide plugin check .                      # отрисовать панель с воркером в каждом сценарии src/panel.check.ts, без Orca
orca-ide plugin dev watch .                  # загрузить папку в Orca, смотреть логи и перезагрузки; Ctrl-C выгружает
```

Подготовка ставит зависимости без bin-ссылок: ссылки npm в `node_modules/.bin` — симлинки, а `orca plugin inspect` не
принимает папку плагина с симлинком. Поэтому TypeScript запускается по пути его пакета
(`node node_modules/typescript/bin/tsc`), а не через `node_modules/.bin`. Worktree, которые создаёт Orca, готовит
`setup` из `orca.yaml` (`node scripts/setup.mjs`): он проверяет, что есть git, node, npm и CLI Orca, и делает ту же
установку. `setup` и `archive` — простые команды без синтаксиса bash: Orca запускает их через bash на macOS и Linux и
через `.cmd` на Windows.

`make test` проходит три шага: `orca plugin validate .` (манифест так, как его загружает Orca), `orca plugin types .`
и `tsc -p .` (типы для этой версии Orca пишутся в `.orca/`, который git игнорирует), `orca plugin test .` (тесты
`src/` и `tests/`). Тесты поставки берут чистую выгрузку закоммиченного HEAD, поэтому перед прогоном изменения надо
закоммитить; npm в них работает без сети, из кэша, который заполнила подготовка.

CLI Orca — `ORCA_CLI_COMMAND` (его задают терминалы Orca), иначе `orca-ide` на Linux и `orca` на macOS и Windows;
другой задают так: `make test ORCA=<путь к CLI>` (относительный путь считается от каталога, где запущен make).
Выбранный CLI получают все шаги и тесты, путь с пробелами работает. Голый `orca` на Linux вне Orca — экранный
диктор GNOME: `make test`, `setup` и тесты его не запускают, нужен `orca-ide` или полный путь CLI.

Для `make test` нужны make и bash 4.4 или новее: этим bash идёт запись итога (`docker/test-result.sh`). На macOS штатный
bash 3.2 — поставьте новый (например `brew install bash`) раньше в PATH; со старым bash `make test` останавливается
до тестов, а не проходит без записи. Каталог записи `TEST_RESULT_DIR` в виде Windows (`C:\…`) `make test` передаёт
регистратору в виде оболочки (`cygpath -u` в Git Bash и MSYS2); если каталог не преобразовался, `make test`
останавливается до тестов, а не идёт без записи. Так же он останавливается, если во временном каталоге системы
(`TMPDIR`, `TMP`, `TEMP`, иначе `/tmp`; путь Windows — через `cygpath -u`) не создать каталог прогона для записи.
Фильтра по имени теста у `orca plugin test` нет: прогон с `test_args="--compact --filter=…"` запускает все тесты
и записывается как отфильтрованный. Сводку тестов печатает `node` из PATH, которым `orca plugin test` их гоняет:
без терминала Node до 22-й версии включительно печатает TAP, с 23-й — spec (`✔`, `ℹ pass N`); проверки
зелёного прогона читают обе.

## Проверка на трёх системах (GitHub Actions)

Workflow `.github/workflows/plugin.yml` («Плагин на трёх системах») проверяет плагин на `ubuntu-latest`,
`macos-latest` и `windows-latest` — на каждый push в `master`, на каждый pull request и вручную (Run workflow). На
каждой системе:

- ставит CLI Orca ровно минимальной версии из `engines.orca` манифеста (сейчас `>=1.4.273` — значит 1.4.273): пакет
  Orca этой системы из релиза `v<версия>` (https://github.com/stablyai/orca/releases), CLI которого идёт под
  Electron в режиме Node, как его запускает сама Orca. Поднимается `engines.orca` — workflow сам берёт новую версию;
- готовит чекаут так, как Orca готовит worktree: `setup` из `orca.yaml`, на Windows — через `.cmd`, как его запускает
  Orca;
- на этом CLI гоняет `plugin validate`, проверку типов (`plugin types` и TypeScript по пути пакета) и `plugin test`;
- проверяет поставку: `plugin inspect` чистой выгрузки коммита (`git archive`, без `node_modules` и `.orca`);
- запускает `archive` из `orca.yaml` так же, как Orca, и ждёт код 0.

Те же команды запускаются и вручную: `node scripts/ci.mjs orca-version` печатает версию CLI для проверки,
`node scripts/ci.mjs install-orca <каталог>` ставит этот CLI (нужны curl и распаковщик пакета системы: `dpkg-deb`,
`ditto` или `7z`), `node scripts/ci.mjs hook setup|archive` запускает скрипт `orca.yaml` так, как Orca на этой
системе. Включить GitHub Actions в репозитории — дело владельца (у частного репозитория считаются минуты); тесты
`make test` проверяют сам workflow-файл и его шаги с поддельным релизом Orca, без сети.

## Релиз

1. Поднять `version` в `orca-plugin.json` и закоммитить — это релизный коммит. Минимальная версия Orca — `engines.orca`
   там же.
2. Пометить его тегом `v<версия>` и запушить тег: Orca ставит из репозитория новейший тег версии.
3. Построить запись для каталога Orca:

   ```sh
   node scripts/release.mjs            # релизный коммит — HEAD
   node scripts/release.mjs v0.1.0     # или тег, ветка, любой коммит репозитория
   ```

   Команда клонирует репозиторий во временный каталог, переходит там на релизный коммит и запускает
   `plugin release-entry` CLI Orca (`ORCA_CLI_COMMAND`, иначе `orca-ide` на Linux и `orca` на macOS и Windows).
   Запись — версия из манифеста коммита, сам коммит, хеш его файлов, доступ и минимальная Orca — печатается в stdout
   как JSON; незакоммиченные изменения в неё не попадают, а рабочий чекаут не меняется: ни файлы, ни ветка, ни
   ссылки. Временный клон удаляется.
4. Внести запись первой в `releases` плагина в `orca-catalog.json` каталога Orca — это делает владелец, со своего
   аккаунта.

## Очередь агентов

Изменения идут через очередь agent-queue-kit (`CLAUDE.md`). Каждый `make test` записывает итог через
`docker/test-result.sh` (копия `reference/test-result.sh` кита) в `~/.cache/agent-queue-kit/orca-plugin-agent-queue/test-results`;
задача вливается только с полным зелёным прогоном на своём коммите. Worktree задач готовит `orca.yaml` (`setup`).
