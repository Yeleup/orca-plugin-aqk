# Agent Queue — плагин Orca (orca-plugin-aqk)

Плагин Orca «Agent Queue» (id `agent-queue`): очередь задач агентов agent-queue-kit внутри Orca. Пока это заготовка:
манифест, каркас панели с экранами, экран «Настройки» с настройками плагина, воркер с общим слоем трёх систем (каталог
данных, id координатора, запуск команд, поиск CLI Orca), формат и чтение настроек проекта, каталоги текстов GitHub на
двух языках и тесты. Что плагин делает, описывают ТЗ и план MVP в `docs/mvp/`.

## Требования

- Orca 1.4.273 или новее на macOS, Windows или Linux. Манифест требует эту версию (`engines.orca` — `>=1.4.273`), и
  более старая Orca плагин не загружает.
- git.
- `gh` с выполненным входом (`gh auth login`).
- Агенты из настроек проекта (например Claude Code или Codex), установленные и с выполненным входом.

## На компьютере пользователя

Воркер плагина получает от Orca урезанное окружение: только `PATH`, `HOME`, `USERPROFILE`, язык и часовой пояс,
временные каталоги, `XDG_RUNTIME_DIR`, адреса D-Bus и ssh-agent и системные переменные Windows (`SYSTEMROOT`,
`SYSTEMDRIVE`, `WINDIR`, `COMSPEC`, `PATHEXT` …). Переменных вроде `LOCALAPPDATA`, `XDG_DATA_HOME`, `ProgramFiles` и
`ORCA_CLI_COMMAND` в нём нет.

**Каталог данных.** Своё состояние на компьютере плагин держит вне репозиториев, в месте для данных приложений этой
системы:

| Система | Каталог данных |
|---|---|
| Linux | `~/.local/share/orca-agent-queue` |
| macOS | `~/Library/Application Support/orca-agent-queue` |
| Windows | `%USERPROFILE%\AppData\Local\orca-agent-queue` (локальный профиль, не перемещаемый) |

`XDG_DATA_HOME` (Linux) и `LOCALAPPDATA` (Windows) плагин учитывает, только когда они есть в окружении воркера и это
абсолютные пути: тогда каталог данных — `$XDG_DATA_HOME/orca-agent-queue` или `%LOCALAPPDATA%\orca-agent-queue`. Orca
эти переменные воркеру не передаёт, поэтому перенесённые туда данные приложений на каталог данных плагина не влияют: он
всегда под домашним каталогом, одинаковый при каждом запуске воркера.

В нём файл `coordinator-id` — id координатора этого компьютера: случайный UUID, без имени компьютера и пользователя.
Воркер создаёт его при первом запуске и дальше только читает; не удаляйте и не копируйте его на другой компьютер: у
каждого компьютера свой id. Файл появляется сразу целым и никогда не заменяется: плагин публикует его жёсткой ссылкой,
поэтому каталогу данных нужна файловая система с жёсткими ссылками — они есть в обычных для домашнего каталога NTFS,
APFS, ext4, btrfs, xfs и NFS. Без жёстких ссылок (FAT, exFAT, сетевой ресурс без них) плагин на этом компьютере не
работает: воркер стартует без id координатора, очередь не запускается, причина — в журнале (`orca plugin logs`). Если
каталог недоступен или в файле не id, воркер так же стартует без id, пишет причину в журнал и файл не трогает.

Пути, которые плагин строит, — с разделителем своей системы: на Windows путь от git (`C:/…`) и от Orca (`C:\…`) — один и
тот же путь.

**Команды.** git, `gh` и CLI Orca плагин ищет в PATH так же, как оболочка системы (на Windows имя без расширения — с
расширениями из `PATHEXT`, путь с расширением — как задан), относительные пути — от рабочего каталога запуска. Файлы
`.cmd` и `.bat` на Windows идут через `cmd.exe`, их аргументы — по правилам для batch-файлов: каждый в кавычках,
кавычка внутри удваивается, `%` не раскрывается, так что `& | < > ( )` остаются текстом и тогда, когда batch-файл
передаёт `%*` дальше; аргумент с переводом строки batch-файлу не передать — это ошибка до запуска. Batch-файл, в пути
которого есть `"`, `^` или `%`, тоже не запускается: `cmd.exe` прочёл бы такой путь по-своему (`%TOOLS%` — как
переменную), это ошибка до запуска.

Программы, которые запускает плагин, получают окружение воркера; на Windows плагин добавляет к нему `APPDATA`
(`%USERPROFILE%\AppData\Roaming`) и `LOCALAPPDATA` (`%USERPROFILE%\AppData\Local`), если их нет, — Orca их воркеру не
передаёт, а программы держат в них настройки (вход `gh` — в `%APPDATA%\GitHub CLI`). Пути берутся из домашнего
каталога, как и каталог данных: перенесённые в другое место папки профиля плагин не знает.

У каждого запуска плагин знает код выхода, вывод, время начала и длительность. Весь вывод можно писать в файл байтами
как есть (ошибка записи — сбой запуска с причиной; файл вывода не открылся, например нет его каталога, — программа не
запускается, ошибка с путём файла и причиной), а в памяти от большого вывода остаются начало и конец. Вывод не в
UTF-8 на Windows читается в кодовой странице консоли: все OEM-страницы Windows (437, 850, 866, 932 и другие); для
незнакомой страницы — UTF-8 с символами замены, исходные байты — в файле вывода. Команда тестов проекта идёт оболочкой
системы: `/bin/sh -c` на macOS и Linux, `cmd.exe /d /s /c` на Windows; на Windows — команда для Windows из настроек
проекта, если она задана, иначе основная. Программа, которой нет, — ошибка с причиной, а не успешный запуск; в строке
оболочки «не найдена» говорит сама оболочка: код 127 у `sh`, 9009 у `cmd.exe`. Если `cmd.exe` отвечает на неизвестную
команду кодом 1, это обычный неуспех с кодом 1 и сообщением `cmd.exe` в выводе ошибок. `cmd.exe` не работает в
сетевом каталоге (`\\сервер\ресурс\…`): такой запуск — ошибка с причиной. Запуск, который не уложился в отведённое
время, останавливается вместе со всеми процессами, которые он запустил; если на Windows `taskkill` не смог остановить
их все, останавливается сам запущенный процесс, а причина — в результате.

**CLI Orca.** `ORCA_CLI_COMMAND` до воркера не доходит, и плагин ищет CLI Orca сам, по порядку:

1. `ORCA_CLI_COMMAND`, если она всё же задана;
2. по имени в PATH: `orca-ide` на Linux, `orca` на macOS и Windows. Голый `orca` на Linux плагин не запускает никогда —
   вне терминалов Orca это экранный диктор GNOME;
3. известные пути CLI в установке Orca: сначала CLI той Orca, в которой работает воркер (в ресурсах рядом с её
   программой — где бы Orca ни стояла), потом обычные места установки:

| Система | Известные пути (по порядку) |
|---|---|
| Linux | `<каталог Orca>/resources/bin/orca-ide`; `~/.local/bin/orca-ide`; `~/.cache/orca/appimage/launcher/orca-ide` (AppImage; `$XDG_CACHE_HOME/…`, только если `XDG_CACHE_HOME` есть в окружении воркера); `/usr/bin/orca-ide` (пакеты deb и rpm); `/opt/Orca`, `/opt/orca-ide`, `/opt/orca` — `resources/bin/orca-ide` |
| macOS | `<Orca>.app/Contents/Resources/bin/orca` запущенной Orca; `/usr/local/bin/orca`; `~/.local/bin/orca`; `Orca.app/Contents/Resources/bin/orca` в `/Applications` и в `~/Applications` |
| Windows | `<каталог Orca>\resources\bin\orca.exe`; `%USERPROFILE%\AppData\Local\Programs\Orca\resources\bin\orca.exe`; `<системный диск>\Program Files\Orca\resources\bin\orca.exe` (`%LOCALAPPDATA%` и `%ProgramFiles%` — только если они есть в окружении воркера) |

Найденный CLI должен ответить на `status --json` (`"ok": true`) за 20 секунд, иначе плагин берёт следующий. Не нашёлся
ни один — результат «CLI Orca не найден» с причиной: что и где искали.

## Настройки проекта

Настройки очереди проекта лежат в двух файлах его репозитория: `.agent-queue.json` (настройки) и `.agent-queue.md`
(правила для заданий агентов). Их пишет мастер подключения, дальше их меняет только владелец; задача очереди их не
меняет.

**Откуда плагин их читает.** Из базовой ветки проекта на `origin` — закоммиченный и запушенный файл
(`origin/<базовая ветка>`), а не рабочее дерево основного чекаута: правка, которую не закоммитили и не запушили, не
действует, как и коммит, которого нет на `origin`. Сам плагин при чтении `fetch` не делает: читается то, что клон знает
об `origin`. Всё решается по одному снимку веток `origin`, которые знает клон: каждая копия файла читается точно —
по её записи в дереве коммита и по id содержимого (`git ls-tree`, `git cat-file`), так что атрибуты git (`-diff`,
`binary`), фильтры и настройки на чтение не влияют, — и настройки берутся из того самого коммита, на котором выбрана
базовая ветка (он и назван в результате), даже если `fetch` сдвинул ветку во время чтения. Одинаковое содержимое на
многих ветках читается один раз; файл больше 1 МиБ не читается — у него своя причина.

Плагин видит только те ветки `origin`, которые загружает клон: обычный `git clone` — все, клон одной ветки
(`--single-branch`, `--depth` без `--no-single-branch`) — только её, и `fetch` других веток ему не приносит. «Файла нет»
значит «нет на ветках `origin`, известных клону». Все ветки такому клону дают `git remote set-branches origin "*"` и
`git fetch origin`.

Когда базовая ветка уже известна, файл читается прямо из неё. Иначе чтение начинается с ветки по умолчанию репозитория
(`origin/HEAD` клона, а если клон его не знает — ответ самого `origin`). Первой решает копия файла на ней, поэтому без
этой ветки в клоне базовая ветка по остальным не выбирается: результат — «не прочитано» с именем ветки по умолчанию.

- файл там есть и не называет другой базовой ветки — это настройки проекта;
- файл называет другую базовую ветку (`baseBranch`; так бывает, например, когда базовую ветку `develop` влили в
  `main`) — настройки берутся из файла той ветки, а копия на ветке по умолчанию нужна только для этого имени: ошибки в
  других её полях не мешают. Файл той ветки должен называть свою же ветку, иначе — ошибка поля `baseBranch`;
- файла там нет — проект может быть подключён на другой базовой ветке: коммит подключения идёт только в ту ветку,
  которую выбрал владелец. Тогда плагин смотрит копии файла на всех ветках `origin`, известных клону (на каждой
  ветке — по одному вызову git, несколько сразу). Базовая ветка — ветка, копия которой называет в `baseBranch` её саму, как её пишет
  мастер подключения; её файл проверяется целиком, и ошибка любого поля называется. Копия на любой другой ветке —
  ветке задачи, ветке, сделанной от базовой, — называет базовую ветку, а не свою, и не считается. Две и больше
  веток, каждая из которых названа в своей копии, — результат «неясно, какая ветка базовая»: ни одна не выбирается.
  Если своя ветка не названа ни в одной копии, файл базовой ветки, видимо, испорчен. Копия, которая называет ветку с
  копией, указывает на неё (так копия ветки задачи указывает на базовую). Базовой может быть ветка любой другой
  копии: у которой базу не понять (не JSON, `baseBranch` не имя ветки, на месте файла каталог или файл больше
  предела) или которая называет ветку без копии (опечатка в `baseBranch`). Одна такая — её ошибки, как у файла
  базовой ветки (например, поле `baseBranch`); несколько — «неясно, какая ветка базовая» с каждой веткой и её
  причиной. Копий нет ни на одной известной клону ветке — проект не подключён.

Если прочитать не удалось (нет git, каталог не репозиторий, в клоне нет `origin/<ветка>` — названной или ветки по
умолчанию, git вернул список веток `origin` не целиком, на месте файла базовой ветки каталог или символическая ссылка,
файл больше предела), результат — «не прочитано» с причиной, а не «файла нет».

### `.agent-queue.json`

```json
{
  "version": 1,
  "baseBranch": "main",
  "testCommand": "make test",
  "testCommandWindows": null,
  "agents": { "implementer": "claude", "reviewer": "codex", "solver": "claude", "start": "claude" },
  "language": "ru",
  "dataRule": "В GitHub не попадают данные клиентов: имена, телефоны, адреса, номера заказов, токены и ключи.",
  "maxInProgress": 1,
  "worktreeDependencies": { "mode": "shared", "directories": ["node_modules"] },
  "afterMerge": [{ "command": "make docs", "name": "Документация" }],
  "forbiddenPatterns": ["ORD-[0-9]{6}"],
  "acceptanceStand": {
    "setup": "npm ci && make stand-setup",
    "up": "make stand-up",
    "url": "http://127.0.0.1:8080",
    "down": "make stand-down"
  }
}
```

| Поле | Что это | Если поля нет |
|---|---|---|
| `version` | версия формата; этот плагин читает `1` | обязательно |
| `baseBranch` | базовая ветка: от неё начинаются worktree задач, в неё вливаются задачи | ветка по умолчанию репозитория |
| `testCommand` | команда полных тестов | обязательно |
| `testCommandWindows` | команда полных тестов на Windows; `null` — нет своей | на Windows идёт `testCommand` |
| `agents` | агенты Orca по ролям — id агента Orca (`claude`, `codex` …): `implementer` — исполнитель, `reviewer` — ревьюер, `solver` — решатель, `start` — агент старта MVP | `claude`, `codex`, `claude`, `claude`; каждая роль отдельно |
| `language` | язык текстов, которые плагин пишет в GitHub: `ru` или `en` | обязательно |
| `dataRule` | правило данных: что никогда не попадает в GitHub | обязательно |
| `maxInProgress` | сколько задач проекта одновременно в работе, целое число от 1 | `1` |
| `worktreeDependencies.mode` | зависимости worktree задачи: `own` — свои, их ставит подготовка worktree; `shared` — общие с основным чекаутом | `shared` |
| `worktreeDependencies.directories` | каталоги зависимостей проекта от корня репозитория (например `node_modules`, `vendor`) | нет каталогов |
| `afterMerge` | шаги после мержа по порядку: `command` — команда в основном чекауте, `name` — имя шага в текстах GitHub (`null` или нет — вместо имени номер шага) | нет шагов |
| `forbiddenPatterns` | шаблоны запрещённых данных — регулярные выражения JavaScript в режиме Unicode (без `/…/` и флагов), дополняют правило данных: например, вид номера заказа клиента | нет шаблонов |
| `acceptanceStand` | стенд приёмки MVP: `setup` и `up` поднимают его в worktree базовой ветки, `url` — адрес `http://` или `https://`, который отвечает, когда стенд поднят, `down` его останавливает; нужны все четыре; `null` — стенда нет | стенда нет |

Проверка файла — только известные поля и верные типы; каждая ошибка называет поле путём, например
`agents.reviewer`, `afterMerge[1].command`, `forbiddenPatterns[0]`, а файл с ошибкой не действует целиком. Ошибка —
это:

- неизвестное поле (опечатка, лишнее поле) на любом уровне и поле неверного типа; `null` можно писать только у
  `testCommandWindows`, `acceptanceStand` и `name` шага, остальные необязательные поля просто не пишут;
- нет обязательного поля, пустой текст в нём или в любом текстовом поле;
- другая версия формата — тогда остальные поля не проверяются: у другой версии они могут быть другими;
- команда (`testCommand`, `testCommandWindows`, `command` шага, `setup`, `up`, `down`) не в одну строку — это строка
  для оболочки системы: `/bin/sh -c` на macOS и Linux, `cmd.exe` на Windows;
- `baseBranch` — не имя ветки по правилам git (пробел, `..`, `~ ^ : ? * [ \` и т. п.) или `HEAD`: так git называет
  текущий коммит, а не ветку;
- каталог зависимостей — абсолютный путь или путь с `..`, выходящий из репозитория;
- шаблон запрещённых данных, который не разбирается как регулярное выражение (ошибка называет причину) или совпадает
  с пустым текстом (например `x*`): такой шаблон отметил бы любое место любого текста.

### `.agent-queue.md`

Правила для заданий агентов: что читать перед задачей, команды проекта, чего нельзя в worktree — как владелец их
напишет. Шаблон мастера подключения — на языке проекта (`language`): разделы «Что читать перед задачей», «Команды
проекта» (с командой полных тестов, а если задана, и с командой для Windows) и «Чего нельзя в worktree»; места в
угловых скобках заполняет владелец. Файл читается из базовой ветки на `origin`, как есть.

### Тексты в GitHub

Комментарии хода, блокировки, итоговые, тела PR и тексты задачи «MVP» плагин пишет на языке проекта (`language`): у
каждого такого текста есть английский и русский вариант под одним ключом, с одними и теми же местами для значений.
Язык интерфейса панели — отдельная настройка плагина на каждом компьютере, на тексты в GitHub она не влияет.

## Установка

Из репозитория, CLI Orca (на Linux он называется `orca-ide`, на macOS и Windows — `orca`):

```sh
orca-ide plugin install Yeleup/orca-plugin-aqk
```

Orca ставит новейший тег версии `vX.Y.Z` (без тегов — ветку по умолчанию) и сначала показывает, какой доступ получит
плагин: `trusted-worker` — свой процесс Node.js с правами пользователя. Установка завершается той же командой с
`--approve <отпечаток>`, который Orca печатает. Когда плагин появится в каталоге Orca, его ставят и обновляют оттуда
(запись каталога готовит команда релиза — раздел «Релиз»).

## Устройство

- `orca-plugin.json` — манифест: id `agent-queue`, имя «Agent Queue», `trusted-worker`, точка входа `src/worker.ts`,
  панель «Agent Queue» в правой боковой части Orca и настройки плагина (ниже, «Настройки плагина»). Доступ: к своим
  настройкам (`settings:own`), к списку проектов и рабочих областей Orca (`workspace:read` — найти основной чекаут
  проекта) и к открытию их файлов в редакторе Orca (`workspace:write`).
- Настройки плагина на этом компьютере Orca хранит для плагина; они видны и в настройках Orca под плагином, меняет их
  владелец на экране «Настройки»:

  | Настройка | Ключ | Значение | По умолчанию |
  |---|---|---|---|
  | Язык интерфейса (Interface language) | `interfaceLanguage` | `en` (English) или `ru` (Русский) | English |
  | Интервал проверки очереди, минут (Queue check interval, minutes) | `queueCheckInterval` | целое число, не меньше 1; верхнего предела нет | 5 |
  | Уведомления о мержах (Merge notifications) | `mergeNotifications` | вкл/выкл; о блокировках уведомления есть всегда | вкл |
  | Координатор на этом компьютере (Coordinator on this computer) | `coordinatorEnabled` | вкл/выкл; выключен — координатор этого компьютера не берёт и не ведёт задачи, панель только показывает очередь | вкл |

  Незаданное или неверное значение читается значением по умолчанию. Работу по интервалу и выключателю координатора,
  сами уведомления и остановленные очереди проектов (они хранятся в тех же настройках) добавляют задачи `claim`,
  `statusbar` и `stop-start`.
- `src/panel.tsx` и `src/ui/` — панель на компонентах Orca, в светлой и тёмной теме Orca. Открывается на «Очереди»:
  заголовок «Agent Queue», выбор проекта из подключённых (список даёт воркер; пока подключённых нет — их даст
  подключение проекта), меню «Проверка проекта», «Начать MVP», «Настройки», «Подключить проект». Каждый пункт
  открывает свой экран («Начать MVP» — «Старт MVP», «Подключить проект» — «Подключение проекта»). Все девять экранов
  ТЗ есть; кроме «Очереди» и «Настроек», они пока заготовки — заголовок и вверху «Назад» к «Очереди», данные и свои
  состояния им дают задачи их функций. Пока воркер не ответил, экран показывает заготовки строк; ответ с ошибкой — текст ошибки
  и «Повторить», который повторяет запрос. Панель занимает правую боковую часть Orca во всю её ширину: эту ширину
  задаёт пользователь, плагин её не задаёт и не меняет. Экраны не построены под одну ширину; на доске дизайна панель
  нарисована шириной 390 и 420.
- Экран «Настройки»: язык интерфейса (English, Русский), интервал проверки очереди в минутах, переключатели
  «Уведомления о мержах» и «Координатор на этом компьютере» и «Настройки проекта» — кнопки `.agent-queue.json` и
  `.agent-queue.md`. Изменение сохраняется сразу, кнопки «Сохранить» нет: выбранный язык — и вся панель сразу на нём;
  интервал — как только в поле целое число минут, не меньше 1 (набор «30» сохраняет 3, затем 30), другой текст
  остаётся в поле с ошибкой «Введите целое число минут, не меньше 1» и не сохраняется. Пока запись идёт, на экране
  то, что человек выбрал или набрал, и в поле можно набирать дальше. После сохранения вверху «Сохранено.»; после
  переключателя и после возврата на русский — что переключатели теперь значат: «Сохранено: уведомлений о мержах не
  будет, о блокировках — будут.», «Сохранено: координатор этого компьютера не берёт и не ведёт задачи; панель только
  показывает очередь.» или (оба выключены) «Сохранено: уведомлений о мержах нет, координатор этого компьютера задачи
  не берёт.»; после выбора English — «Saved.». Не сохранилось — «Не удалось сохранить: <ошибка>», и на экране
  прежнее, сохранённое значение (если человек уже изменил ту же настройку снова, на экране остаётся его новое
  изменение — его запись ещё идёт). Настройка, изменённая в настройках Orca, сразу видна на экране. Строка
  сохранения или ошибки — до ухода с экрана: новый заход начинается без неё. Кнопка файла показывает в Orca основной
  чекаут проекта, выбранного на «Очереди» (рабочая область Orca этого проекта на его хосте, по пути самого проекта),
  и открывает в нём файл в редакторе Orca. Нет подключённых проектов — кнопки недоступны, под ними «Нет подключённых
  проектов»; в Orca нет основного чекаута проекта или Orca отказала — «Не удалось открыть <файл>: <причина>».
- `src/i18n/` — каталоги строк панели на английском и русском: все тексты экранов только оттуда, ключи в обоих
  каталогах одни и те же. Язык — настройка плагина; её смена (в настройках Orca) сразу меняет язык открытой панели.
- `src/protocol.ts` — запросы панели к воркеру (`plugin.request`) и события воркера для открытых панелей:
  `projects.list` — подключённые проекты (id и хост проекта — как у проекта в Orca: один id может быть у копий
  проекта на двух хостах); `project.openFile` — показать основной чекаут проекта (id и хост) и открыть в нём в
  редакторе Orca `.agent-queue.json` или `.agent-queue.md` (другие пути и запрос без хоста воркер отклоняет с
  `invalid_params`); ответ — открыт или `no_checkout`: в Orca нет основного чекаута проекта на его хосте.
- `src/settings.ts` — настройки плагина: ключи, значения по умолчанию, чтение для панели и воркера (`readSettings`).
- `src/worker.ts` — воркер плагина: отвечает панели (подключённые проекты — `projects.list`, файлы проекта —
  `project.openFile`, `src/project-files.ts`), при запуске находит каталог данных и id координатора. Orca сама транспилирует TypeScript панели и воркера при загрузке: сборки нет,
  зависимостей во время работы нет.
- `src/platform/` — общий слой трёх систем: `machine.ts` — компьютер, на котором работает воркер (система, окружение,
  часы, файлы, запуск процессов; тесты подставляют поддельный), `files.ts` и `process.ts` — файлы и запуск процессов
  настоящего компьютера (`code-pages.ts` — таблицы кодовых страниц консоли Windows), `folders.ts` — папки профиля и
  окружение запускаемых программ, `paths.ts` — каталог данных и
  пути worktree и файлов, `coordinator-id.ts` — id координатора, `run.ts` — запуск команд и команды тестов проекта (её
  настройки — из `.agent-queue.json`), `orca-cli.ts` — поиск CLI Orca.
- `src/project/` — настройки проекта (раздел «Настройки проекта»): `settings.ts` — формат `.agent-queue.json`, его
  проверка с полем ошибки, умолчания и чтение, `task-rules.ts` — шаблон и чтение `.agent-queue.md`, `base-branch.ts` —
  точное чтение файла из коммита ветки `origin`, ветки `origin` и ветка по умолчанию репозитория.
- `src/github-texts/` — каталоги текстов, которые плагин пишет в GitHub, на русском и английском: текст берётся по
  языку проекта, ключи в обоих каталогах одни и те же (`src/text-params.ts` — подстановка значений в тексты обоих
  видов каталогов).
- `src/node.d.ts` — типы встроенных модулей Node.js, которыми пользуется плагин: пакета `@types/node` нет.
- `src/testing/` — поддельный компьютер для тестов: любая из трёх систем, файлы в памяти, записанные запуски, часы;
  временный домашний каталог, в котором тесты запускают настоящий воркер; репозиторий проекта с настоящим git и

- `src/**/*.test.ts(x)` — тесты плагина на `orca/testing` (поддельный хост Orca), их запускает `orca plugin test`;

- `tests/*.test.mjs` — тесты поставки, workflow и релиза: манифест, подготовка worktree, `plugin inspect` чистой

- `scripts/setup.mjs` — подготовка worktree (`setup` в `orca.yaml`).

## Разработка

```sh
npm ci --no-audit --no-fund --no-bin-links   # подготовка: TypeScript в node_modules/, без bin-ссылок
make test                                    # манифест, типы, тесты — с записью итога для очереди агентов
orca-ide plugin check .                      # отрисовать панель с воркером в каждом сценарии src/panel.check.ts, без Orca
orca-ide plugin dev watch .                  # загрузить папку в Orca, смотреть логи и перезагрузки; Ctrl-C выгружает
```

Экран «Настройки» и настройки плагина проверяет `src/settings.test.tsx`: панель на поддельном хосте Orca, его
настройки — настройки плагина; открытие файлов проекта — с настоящим воркером на своём поддельном хосте. Сценарии
`orca-ide plugin check .` рисуют панель только на «Очереди»: панель всегда открывается на ней.

Подготовка ставит зависимости без bin-ссылок: ссылки npm в `node_modules/.bin` — симлинки, а `orca plugin inspect` не
принимает папку плагина с симлинком. Поэтому TypeScript запускается по пути его пакета
(`node node_modules/typescript/bin/tsc`), а не через `node_modules/.bin`. Worktree, которые создаёт Orca, готовит
`setup` из `orca.yaml` (`node scripts/setup.mjs`): он проверяет, что есть git, node, npm и CLI Orca, и делает ту же
установку. `setup` и `archive` — простые команды без синтаксиса bash: Orca запускает их через bash на macOS и Linux и
через `.cmd` на Windows.

`make test` проходит три шага: `orca plugin validate .` (манифест так, как его загружает Orca), `orca plugin types .`
и `tsc -p .` (типы для этой версии Orca пишутся в `.orca/`, который git игнорирует), `orca plugin test .` (тесты
`src/` и `tests/`). Тесты поставки берут чистую выгрузку закоммиченного HEAD, поэтому перед прогоном изменения надо
закоммитить; npm в них работает без сети, из кэша, который заполнила подготовка.

CLI Orca — `ORCA_CLI_COMMAND` (его задают терминалы Orca), иначе `orca-ide` на Linux и `orca` на macOS и Windows;
другой задают так: `make test ORCA=<путь к CLI>` (относительный путь считается от каталога, где запущен make).
Выбранный CLI получают все шаги и тесты, путь с пробелами работает. Голый `orca` на Linux вне Orca — экранный
диктор GNOME: `make test`, `setup` и тесты его не запускают, нужен `orca-ide` или полный путь CLI.

Для `make test` нужны make и bash 4.4 или новее: этим bash идёт запись итога (`docker/test-result.sh`). На macOS штатный
bash 3.2 — поставьте новый (например `brew install bash`) раньше в PATH; со старым bash `make test` останавливается
до тестов, а не проходит без записи. Каталог записи `TEST_RESULT_DIR` в виде Windows (`C:\…`) `make test` передаёт
регистратору в виде оболочки (`cygpath -u` в Git Bash и MSYS2); если каталог не преобразовался, `make test`
останавливается до тестов, а не идёт без записи. Так же он останавливается, если во временном каталоге системы
(`TMPDIR`, `TMP`, `TEMP`, иначе `/tmp`; путь Windows — через `cygpath -u`) не создать каталог прогона для записи.
Фильтра по имени теста у `orca plugin test` нет: прогон с `test_args="--compact --filter=…"` запускает все тесты
и записывается как отфильтрованный. Сводку тестов печатает `node` из PATH, которым `orca plugin test` их гоняет:
без терминала Node до 22-й версии включительно печатает TAP, с 23-й — spec (`✔`, `ℹ pass N`); проверки
зелёного прогона читают обе.

## Проверка на трёх системах (GitHub Actions)

Workflow `.github/workflows/plugin.yml` («Плагин на трёх системах») проверяет плагин на `ubuntu-latest`,
`macos-latest` и `windows-latest` — на каждый push в `master`, на каждый pull request и вручную (Run workflow). На
каждой системе:

- ставит CLI Orca ровно минимальной версии из `engines.orca` манифеста (сейчас `>=1.4.273` — значит 1.4.273): пакет
  Orca этой системы из релиза `v<версия>` (https://github.com/stablyai/orca/releases), CLI которого идёт под
  Electron в режиме Node, как его запускает сама Orca. Поднимается `engines.orca` — workflow сам берёт новую версию;
- готовит чекаут так, как Orca готовит worktree: `setup` из `orca.yaml`, на Windows — через `.cmd`, как его запускает
  Orca;
- на этом CLI гоняет `plugin validate`, проверку типов (`plugin types` и TypeScript по пути пакета) и `plugin test`;
- проверяет поставку: `plugin inspect` чистой выгрузки коммита (`git archive`, без `node_modules` и `.orca`);
- запускает `archive` из `orca.yaml` так же, как Orca, и ждёт код 0.

Те же команды запускаются и вручную: `node scripts/ci.mjs orca-version` печатает версию CLI для проверки,
`node scripts/ci.mjs install-orca <каталог>` ставит этот CLI (нужны curl и распаковщик пакета системы: `dpkg-deb`,
`ditto` или `7z`), `node scripts/ci.mjs hook setup|archive` запускает скрипт `orca.yaml` так, как Orca на этой
системе. Включить GitHub Actions в репозитории — дело владельца (у частного репозитория считаются минуты); тесты
`make test` проверяют сам workflow-файл и его шаги с поддельным релизом Orca, без сети.

## Релиз

1. Поднять `version` в `orca-plugin.json` и закоммитить — это релизный коммит. Минимальная версия Orca — `engines.orca`
   там же.
2. Пометить его тегом `v<версия>` и запушить тег: Orca ставит из репозитория новейший тег версии.
3. Построить запись для каталога Orca:

   ```sh
   node scripts/release.mjs            # релизный коммит — HEAD
   node scripts/release.mjs v0.1.0     # или тег, ветка, любой коммит репозитория
   ```

   Команда клонирует репозиторий во временный каталог, переходит там на релизный коммит и запускает
   `plugin release-entry` CLI Orca (`ORCA_CLI_COMMAND`, иначе `orca-ide` на Linux и `orca` на macOS и Windows).
   Запись — версия из манифеста коммита, сам коммит, хеш его файлов, доступ и минимальная Orca — печатается в stdout
   как JSON; незакоммиченные изменения в неё не попадают, а рабочий чекаут не меняется: ни файлы, ни ветка, ни
   ссылки. Временный клон удаляется.
4. Внести запись первой в `releases` плагина в `orca-catalog.json` каталога Orca — это делает владелец, со своего
   аккаунта.

## Очередь агентов

Изменения идут через очередь agent-queue-kit (`CLAUDE.md`). Каждый `make test` записывает итог через
`docker/test-result.sh` (копия `reference/test-result.sh` кита) в `~/.cache/agent-queue-kit/orca-plugin-agent-queue/test-results`;
задача вливается только с полным зелёным прогоном на своём коммите. Worktree задач готовит `orca.yaml` (`setup`).
