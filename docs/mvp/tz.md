Статус: черновик

Папка `docs/mvp/`: это ТЗ, дизайн — `maket/index.html` (доска экранов, после «ТЗ: утверждаю»), план — `plan.md`,
решения владельца дословно — `decisions.md`.

## Цель и проблема

Очередь агентов agent-queue-kit ведёт изменения проекта без человека: задача — issue GitHub, один агент её делает,
другой ревьюит, PR вливается после чистого ревью и зелёных тестов, а человек нужен, только когда задача заблокирована.
Автопилот доводит новый проект от ТЗ до принятого MVP. Сейчас кит — bash-скрипты, навыки Claude и таймер systemd:
работает только на Linux, ставится вручную (`bin/activate`, `install`, `init`), задачу ведёт агент-координатор
(LLM, который тратит токены на рутину), а увидеть очередь можно только в GitHub и в терминале.

Agent Queue — тот же кит, сделанный плагином Orca (решение владельца: «тоже что и agent-queue-kit. Мы поменяем
реализацию на плагин. Который максимально будет использовать функционалы самого orca и будет работать в Mac, Windows,
Linux»). Когда MVP заработает:

- плагин ставится из каталога Orca на macOS, Windows и Linux любым пользователем Orca;
- задачу ведёт код плагина: он берёт задачу, создаёт worktree Orca, запускает агентов через Orca, следит за их
  статусом, сам гоняет тесты, мержит; LLM нужны только исполнителю, ревьюеру, решателю автопилота и агенту старта MVP;
- очередь видна и управляется в Orca: панель, строка состояния, уведомления, ответы на блокировки;
- задачи живут в issues GitHub в своём формате плагина; проекты, которые сейчас на ките, остаются на ките.

## Пользователи и роли

| Роль | Кто это | Что делает в MVP |
|---|---|---|
| Владелец очереди | любой пользователь Orca; на его компьютере плагин работает от его входа в `gh` | подключает проект, ставит задачи, отвечает на блокировки, останавливает и запускает очередь, начинает MVP, утверждает ТЗ, дизайн и план, принимает MVP |
| Координатор | код плагина в Orca владельца; у каждого компьютера свой id координатора | берёт задачи, ведёт агентов, гоняет тесты, открывает PR и мержит, блокирует задачи, перехватывает брошенные |
| Исполнитель | агент Orca из настроек проекта (по умолчанию Claude) | делает задачу в worktree, коммитит и пушит в ветку задачи, пишет отчёт |
| Ревьюер | агент Orca из настроек проекта (по умолчанию Codex) | проверяет изменения задачи, ТЗ и дизайн при старте MVP, MVP при приёмке; пишет отчёт и вердикт |
| Решатель | агент Orca из настроек проекта (по умолчанию Claude) | под автопилотом решает вместо владельца: вопрос задачи, пакет, итог ревью, деление задачи |
| Агент старта MVP | агент Orca из настроек проекта (по умолчанию Claude) в терминале Orca | ведёт старт MVP: вопросы владельцу, ТЗ, дизайн, план |
| Сессии агентов в проекте | любые агенты в терминалах Orca этого проекта | по правилу в `CLAUDE.md` и `AGENTS.md` ставят изменения кода в очередь, а не делают их сами |

Учитываются только тексты владельца очереди: тело задачи и комментарии пользователя GitHub, под которым работает `gh`
плагина. Задачи и комментарии других пользователей плагин не берёт и в задания агентов не передаёт.

## Главные сценарии

Главные сценарии — те же, что у agent-queue-kit (решение владельца «тоже что и agent-queue-kit»):

1. Владелец подключает проект Orca к очереди → в репозитории файл настроек и правила, в GitHub метки, «Проверка
   проекта» без проблем. Экраны: «Подключение проекта», «Проверка проекта». Функции: Ф1, Ф2.
2. Владелец ставит задачу в панели, или сессия агента ставит её по правилу входа → issue с меткой очереди. Экраны:
   «Новая задача», «Очередь». Функции: Ф3.
3. Координатор берёт задачу → исполнитель в worktree → полный прогон тестов → ревьюер → круги замечаний → PR влит,
   задача закрыта, worktree убран. Экраны: «Очередь», «Задача». Функции: Ф4, Ф5.
4. Задача заблокирована → уведомление → владелец отвечает в панели (или в GitHub) → задача продолжается с его ответом.
   Экраны: «Ответ на блокировку», «Задача». Функции: Ф6, Ф8.
5. Владелец открывает Orca → видит, что влито, что в работе и что ждёт его ответа. Экраны: «Очередь». Функции: Ф7, Ф8.
6. Владелец останавливает или запускает очередь проекта, выключает автопилот. Экраны: «Очередь», «MVP». Функции: Ф9.
7. Сторож замечает зависшую задачу, перезапуск Orca, потерянного агента → задача продолжается, владелец получает
   уведомление о том, что сам плагин не исправит. Функции: Ф10.
8. Владелец начинает MVP нового проекта → агент старта в терминале Orca спрашивает, пишет ТЗ, дизайн и план, каждую
   версию проверяет ревьюер, владелец видит её артефактом Orca → после «Да» задача «MVP» и задачи плана в очереди.
   Экраны: «Старт MVP», «MVP». Функции: Ф11.
9. Автопилот доводит задачи MVP без остановок: решатель вместо владельца, деление застрявших задач, пределы, сводка.
   Экраны: «MVP». Функции: Ф12.
10. Все задачи MVP закрыты → приёмка на стенде → «MVP готов к вашей приёмке» → владелец принимает в панели или даёт
    замечания. Экраны: «MVP». Функции: Ф13.

## Функции и критерии приёмки

Каждая функция — с экранами раздела «Экраны» (по названию) и критериями, которые проверяет автоматический тест. Задача
«Приёмочные тесты MVP» пишет e2e-тест на каждый критерий; критерий, который тест проверить не может, переписывается.

Тесты идут только с подделками (решение владельца «Только подделки»): поддельный хост Orca (`orca/testing`:
`mockHost`, `mountWorker`, `mount`), поддельные `gh` и git и поддельные агенты, без сети и без настоящего GitHub.
«Проверка очереди» в критериях — один проход координатора, который тест вызывает сам, а не ждёт по таймеру.

### Ф1. Подключение проекта

Мастер подключает проект Orca к очереди. Экраны: «Подключение проекта», «Проверка проекта».

1. Владелец выбирает проект из проектов Orca, ещё не подключённых (подключён — в основном чекауте есть
   `.agent-queue.json`).
2. Плагин проверяет: проект — git-репозиторий с удалённым репозиторием GitHub; `gh` установлен, вход выполнен, у
   пользователя есть доступ на запись; агенты из настроек известны Orca.
3. Форма настроек: базовая ветка (по умолчанию — ветка по умолчанию репозитория), команда полных тестов
   (обязательна), команда для Windows (по желанию), агенты — исполнитель, ревьюер, решатель, агент старта (из агентов
   Orca; по умолчанию Claude, Codex, Claude, Claude), язык текстов в GitHub, правило данных (шаблон), правила для
   заданий (шаблон), одновременно задач в работе (по умолчанию 1).
4. «Подключить» записывает `.agent-queue.json`, `.agent-queue.md` и блок правила входа в `CLAUDE.md` и `AGENTS.md`
   (файла нет — создаёт), создаёт недостающие метки плагина в GitHub, коммитит только эти четыре файла и пушит коммит
   в базовую ветку. Только когда основной чекаут на базовой ветке, без изменений и не отстаёт от `origin`; иначе
   ничего не пишет и называет причину. Потом открывает «Проверку проекта».

- К1.1. Тест: подключить проект при исправных `gh` и git → коммит в базовой ветке меняет только `.agent-queue.json`,
  `.agent-queue.md`, `CLAUDE.md`, `AGENTS.md`; в GitHub созданы шесть меток плагина; коммит запушен; открыт экран
  «Проверка проекта».
- К1.2. Тест: `gh` без входа → мастер показывает «gh: нет входа — выполните gh auth login», «Подключить» недоступна,
  файлы и GitHub не меняются.
- К1.3. Тест: основной чекаут не на базовой ветке (или с изменениями, или отстаёт от `origin`) → «Подключить»
  отказывает с этой причиной, ничего не записано и не запушено.
- К1.4. Тест: пустая команда полных тестов → ошибка у поля, ничего не записано.
- К1.5. Тест: у проекта нет удалённого репозитория GitHub → «Подключение невозможно: нет удалённого репозитория
  GitHub», форма настроек не открывается.
- К1.6. Тест: у части меток уже есть → создаются только недостающие; в `CLAUDE.md` с чужим текстом этот текст
  остаётся, блок правила добавлен один раз.

### Ф2. Проверка проекта

То же, что `doctor` кита: строки «ок», «проблема» (с тем, как исправить) и «не проверено» (с ошибкой). Где плагин
может исправить сам — кнопка «Исправить». Строки: версия плагина и Orca; `gh` (установлен, вход, доступ на запись);
git; файл настроек (разбирается, известные поля, верные типы); правила для заданий есть; блок правила входа совпадает
с шаблоном этой версии плагина; метки в GitHub; агенты из настроек известны Orca; координатор на этом компьютере
включён, очередь проекта не остановлена; у открытой задачи «MVP» под автопилотом — пределы читаются и стенд приёмки
задан. Экраны: «Проверка проекта».

- К2.1. Тест: всё исправно → все строки «ок».
- К2.2. Тест: в GitHub нет метки `agent-queue:blocked` → строка «проблема» с «Исправить»; после нажатия метка
  создана, строка «ок».
- К2.3. Тест: в `.agent-queue.json` неизвестное поле или поле неверного типа → строка «проблема» называет поле.
- К2.4. Тест: блок правила в `CLAUDE.md` изменён руками → «проблема: правило входа устарело»; «Исправить»
  переписывает только текст между маркерами, остальное в файле не меняется.
- К2.5. Тест: агента исполнителя из настроек Orca не знает → «проблема» с именем агента.
- К2.6. Тест: `gh` падает с ошибкой → строка «не проверено: <ошибка>», а не «ок».

### Ф3. Постановка задачи

Задача ставится из панели или сессией агента по правилу входа: issue владельца с меткой `agent-queue`. Зависимость —
строка «Зависит от #N» (или «Depends on #N»): пока #N открыта, задачу не берут. Экраны: «Новая задача», «Очередь».

Правило входа говорит сессиям агентов: изменение кода — в очередь, командой `gh issue create` с меткой `agent-queue`
и текстом по формату плагина (запрос пользователя, его решения, предложения сессии раздельно; зависимости строкой
«Зависит от #N»); открытые вопросы — с пользователем до постановки; данных с прода в задаче нет; «сделай сам» и «без
очереди» — сессия делает сама; файлы настроек очереди меняет только владелец.

- К3.1. Тест: «Поставить» в «Новой задаче» с заголовком и текстом → issue с меткой `agent-queue`, этим заголовком и
  текстом; задача в разделе «Ждут» экрана «Очередь»; открыт экран «Задача» новой задачи.
- К3.2. Тест: задача с «Зависит от #5», #5 открыта → в «Ждут» с пометкой «ждёт #5», проверка очереди её не берёт;
  после закрытия #5 следующая проверка её берёт.
- К3.3. Тест: пустой заголовок → ошибка у поля, issue не создаётся.
- К3.4. Тест: issue с меткой `agent-queue` от другого пользователя GitHub → проверка очереди её не берёт, в «Очереди»
  её нет.
- К3.5. Тест: блок правила входа, который пишет плагин, называет репозиторий проекта, метку `agent-queue` и строку
  «Зависит от #N».

### Ф4. Координатор: взятие и ведение задачи

Пока Orca открыта, координатор этого компьютера включён и очередь проекта не остановлена, плагин раз в интервал
(настройка, по умолчанию 5 минут) проверяет очередь каждого подключённого проекта. Берёт самую старую задачу в
очереди: метка `agent-queue`, нет `working`, `blocked`, `split`, нет открытых зависимостей, задач в работе меньше
предела проекта (и пределов MVP для задачи MVP). Захват — метка `agent-queue:working` и комментарий с id
координатора. Перед каждым действием координатор проверяет, что задачу ведёт он (последний захват в её комментариях);
нет — пишет «Задачу ведёт <id>» и больше по задаче ничего не делает.

Дальше: worktree Orca на ветке `agent-queue/issue-<N>` от `origin/<базовая ветка>` (Orca готовит его своей
подготовкой проекта, `orca.yaml`); исполнитель в нём с заданием — текст задачи и комментарии владельца, правила для
заданий, правило данных, ограничения (тесты только полной командой проекта; коммит и пуш только в ветку задачи; не
мержить; не менять зависимости, `.env*`, `.agent-queue.json`, `.agent-queue.md`; вопрос — в отчёт, не догадкой) и
путь файла отчёта. Отчёт готов, когда агент в Orca закончил («done») и файл отчёта есть. После первого пуша —
черновой PR в базовую ветку с `Closes #N`. После каждого этапа — комментарий хода в задаче на языке проекта: взята,
исполнитель запущен, сделано и PR, круг ревью k — m замечаний, исправлено, влита; последний комментарий живой задачи
не старше 2 часов.

После отчёта исполнителя плагин сам запускает полную команду тестов в worktree на закоммиченном дереве без
незакоммиченных и неотслеживаемых файлов и записывает итог: SHA, код выхода, время, последние строки вывода. Красный
прогон — вывод уходит тому же исполнителю; три красных прогона подряд — блокировка (Ф6).

- К4.1. Тест: задача в «Ждут» → после проверки очереди у неё метка `agent-queue:working`, комментарий захвата с id
  координатора, worktree на ветке `agent-queue/issue-<N>`, исполнитель запущен с заданием, где есть текст задачи,
  правила для заданий и правило данных.
- К4.2. Тест: предел «одновременно в работе» 1 и одна задача в работе → вторая не берётся, пока первая не закрыта
  или не заблокирована.
- К4.3. Тест: два координатора с разными id захватили одну задачу → агентов запускает только один; второй пишет
  «Задачу ведёт <id первого>» и больше ничего не делает.
- К4.4. Тест: исполнитель отчитался, тесты красные → исполнитель получает вывод теста; после третьего красного прогона
  подряд задача заблокирована.
- К4.5. Тест: исполнитель запушил первый коммит → черновой PR из `agent-queue/issue-<N>` в базовую ветку с
  `Closes #<N>` в теле.
- К4.6. Тест: в worktree есть неотслеживаемый файл → прогон тестов записан как «дерево не чистое» и для мержа не
  засчитывается.
- К4.7. Тест: в задаче есть комментарий другого пользователя GitHub → его текста нет в задании исполнителя.

### Ф5. Ревью, круги замечаний и мерж

Ревьюер запускается в worktree задачи только на чтение, с ожидаемым SHA и заданием: проверить изменения против
задачи, правил и правила данных, запустить полные тесты, записать отчёт и файл вердикта — `issue`, `round`,
`reviewed_sha`, `verdict` (`approve`, `changes`, `head-mismatch`), замечания с важностью (`critical`, `major`,
`minor`, `nit`), файлом, строкой и одной строкой сути. Неверный файл вердикта не засчитывается: ревьюер получает
причину, круг не считается. `changes` — все замечания тому же исполнителю, потом новый круг. Не больше трёх кругов;
после третьего только minor/nit — ещё один круг по изменениям после последнего ревью; иначе блокировка (под автопилотом
— Ф12).

Мерж — только при `approve` и полном зелёном прогоне на чистом дереве ровно того SHA, который одобрен. Базовая ветка
ушла вперёд — исполнитель делает rebase, полный прогон на новом SHA; конфликт вне простых случаев — ещё круг ревью
разрешения конфликта. Мерж: тело PR переписано по итогам (Зачем, Что сделано, Проверка, Ревью), PR готов к ревью,
merge-коммит с проверкой, что голова PR — проверенный SHA; потом ветка удалена, задача закрыта, итоговый комментарий,
основной чекаут обновлён (когда он на базовой ветке и чистый), шаги после мержа из настроек, worktree убран. Мержи
проекта на одном компьютере идут по одному. Ветка, которая меняет `.agent-queue.json` или `.agent-queue.md`, не
вливается.

- К5.1. Тест: ревьюер вернул `changes` с двумя замечаниями → исполнитель получает оба, идёт круг 2; в задаче
  комментарий «круг 1: 2 замечания».
- К5.2. Тест: `approve` и зелёный прогон того же SHA → PR влит merge-коммитом, ветка удалена, задача закрыта,
  итоговый комментарий со ссылкой на PR, worktree убран, метки `working` нет.
- К5.3. Тест: `approve`, а зелёного прогона этого SHA нет → мержа нет, плагин запускает полные тесты на этом SHA.
- К5.4. Тест: файл вердикта с чужим SHA или без `verdict` → не засчитан, ревьюеру отправлена причина, номер круга не
  вырос.
- К5.5. Тест: после третьего круга осталось замечание `major` (вне автопилота) → задача заблокирована, в комментарии
  оставшиеся замечания.
- К5.6. Тест: базовая ветка ушла вперёд после `approve` → исполнитель получает задание на rebase, полный прогон на
  новом SHA, влит новый SHA.
- К5.7. Тест: ветка задачи меняет `.agent-queue.json` → мерж отказан, задача заблокирована с этой причиной.
- К5.8. Тест: шаг после мержа из настроек вышел с кодом 1 → мерж остаётся, итоговый комментарий называет команду и
  код выхода.

### Ф6. Блокировка и ответ владельца

Блокировка — когда нужен человек: вопрос, на который задача и документы не отвечают (выбор технологии тоже); нужен
новый пакет или зависимость (под автопилотом — Ф12); задача требует изменить настройки очереди; три неудачи одного
шага; ревью не одобрено за разрешённые круги; конфликт rebase, который исполнитель не разрешил; сбой Orca, GitHub или
агента, который не запускается. Плагин: работа исполнителя запушена в ветку, агенты остановлены, worktree убран,
метка `agent-queue:blocked` вместо `working`, комментарий — что сделано, что мешает, точный вопрос; уведомление Orca.
Владелец отвечает в панели («Ответ на блокировку»: комментарий от его имени и снятие метки одним действием) или в
GitHub (комментарий и снятие метки). Задача снова в очереди, следующий захват продолжает её с ветки, задание содержит
ответ владельца, круги ревью считаются заново. Экраны: «Ответ на блокировку», «Задача», «Очередь».

- К6.1. Тест: исполнитель написал в отчёте вопрос → метка `agent-queue:blocked`, комментарий с вопросом, уведомление
  Orca «#<N> ждёт ответа: <заголовок>», агенты остановлены, worktree убран, последний коммит исполнителя в ветке
  задачи.
- К6.2. Тест: ответ в «Ответе на блокировку» → в задаче комментарий с этим текстом, метка `agent-queue:blocked`
  снята; следующая проверка очереди берёт задачу, и задание исполнителя содержит ответ.
- К6.3. Тест: метку сняли в GitHub после комментария владельца → задача берётся, задание содержит этот комментарий.
- К6.4. Тест: поле ответа пустое → кнопка «Ответить и вернуть в очередь» недоступна.

### Ф7. Панель очереди

Панель плагина в Orca: проекты и их задачи по разделам — «Ждут ответа» (заблокированы), «В работе» (этап: исполнитель,

задачи «MVP». Обновляется после каждого шага координатора и при открытии; данные из GitHub не старше интервала
проверки. Экраны: «Очередь», «Задача».

- К7.1. Тест: две задачи ждут, одна в работе, одна заблокирована, одна влита вчера → каждая в своём разделе, у
  разделов счётчики 1, 1, 2, 1.
- К7.2. Тест: подключённых проектов нет → «Очередь» в состоянии «Нет подключённых проектов» с кнопкой «Подключить
  проект».
- К7.3. Тест: чтение GitHub упало → «Очередь» в состоянии ошибки «Не удалось прочитать GitHub: <ошибка>» с кнопкой
  «Повторить»; задачи прежнего чтения не показаны как текущие.
- К7.4. Тест: задача на втором круге ревью → в «В работе» у неё этап «Ревью, круг 2».
- К7.5. Тест: нажать на задачу → экран «Задача» с её текстом, кругами ревью и прогонами тестов.
- К7.6. Тест: язык интерфейса «English» → заголовки и кнопки панели на английском; «Русский» — на русском.

### Ф8. Строка состояния и уведомления

Элемент строки состояния Orca: «Очередь: <в работе> · <ждут ответа>»; тон «предупреждение», когда есть задачи,

задача влита (выключается в «Настройках»), MVP ждёт приёмки, условия сторожа (Ф10). Одно уведомление на событие.

- К8.1. Тест: задача заблокирована → строка состояния «Очередь: 0 · 1» с тоном предупреждения; уведомление одно,

- К8.2. Тест: задача влита → уведомление «#<N> влита: <заголовок>».
- К8.3. Тест: уведомления о мержах выключены → о мерже уведомления нет, о блокировке есть.

### Ф9. Стоп и пуск очереди

«Остановить» у проекта — координатор этого компьютера не берёт новые задачи проекта; начатые доводит до мержа или
блокировки. «Запустить» — снова берёт. «Выключить автопилот» на экране «MVP» снимает `agent-queue:autopilot` с
задачи «MVP», «Включить автопилот» — ставит. Экраны: «Очередь», «MVP».

- К9.1. Тест: очередь проекта остановлена, одна задача в работе, одна ждёт → проверка очереди новую не берёт, задача в
  работе доходит до мержа.
- К9.2. Тест: «Запустить» → следующая проверка очереди берёт ждущую задачу.
- К9.3. Тест: «Выключить автопилот» → метка `agent-queue:autopilot` снята; следующий вопрос задачи MVP блокирует её

### Ф10. Сторож

Внутри плагина, раз в 5 минут, пока Orca открыта. Только по задачам и проектам этого компьютера; сбой чтения GitHub
никогда не считается пустой очередью или брошенной задачей. Одно уведомление на условие, пока оно держится.

- задача в работе у этого координатора, а её агента в Orca нет (перезапуск Orca, закрытый терминал) → задача
  продолжается с ветки новым агентом в её worktree (worktree нет — новый), комментарий «Продолжено после потери
  агента»;
- задача в работе у другого координатора, комментариев хода 3 часа → перехват: комментарий «Перехват: предыдущий
  координатор молчал 3 часа», продолжение с ветки;
- агент задачи ждёт ввода человека 30 минут → уведомление «#<N>: агент ждёт ввода» с переходом к его терминалу;
- агент упёрся в лимит использования → задача отложена на час: комментарий «Отложено до <время>», метка `working`
  снята, до этого времени задачу не берут;
- GitHub не прочитан три проверки подряд → уведомление;
- задача «MVP» под автопилотом: 6 часов ни одного мержа и ничего в работе; достигнут предел; готова к приёмке или
  заблокирована → уведомление.

- К10.1. Тест: задача в работе у этого координатора, агента в Orca нет → после проверки сторожа запущен новый
  исполнитель в worktree задачи, в задаче комментарий «Продолжено после потери агента».
- К10.2. Тест: задача в работе у другого id, последний комментарий хода 3 часа назад → перехват: комментарий
  «Перехват…», захват этим координатором, исполнитель продолжает с ветки.
- К10.3. Тест: агент в состоянии «waiting» 30 минут → одно уведомление «#<N>: агент ждёт ввода»; вторая проверка
  нового не показывает; после выхода из ожидания условие снято.
- К10.4. Тест: GitHub не прочитан три проверки подряд → уведомление; ни одна задача не перехвачена и не взята.
- К10.5. Тест: отчёт агента о лимите использования → комментарий «Отложено до <время + 1 ч>», метки `working` нет;
  проверка до этого времени задачу не берёт, после — берёт.

### Ф11. Старт MVP

«Начать MVP» в панели (подключённый проект без открытой задачи «MVP») запускает агента старта в терминале Orca
основного чекаута проекта с инструкцией плагина. Агент делает то, что сейчас навык `/agent-queue-start`: спрашивает
владельца в чате по блокам (цель, данные и интеграции, состав MVP, «только владелец»), записывает его ответы дословно
в `decisions.md`, пишет ТЗ (экраны словами), после «ТЗ: утверждаю» — доску дизайна `maket/index.html`, после «Дизайн:
утверждаю» — план; всё в `docs/mvp/` на своей ветке в своём worktree. Каждую версию до показа проверяет ревьюер с
чистым контекстом: агент старта просит плагин о ревью файлом в каталоге старта, плагин запускает ревьюера и кладёт
отчёт с вердиктом рядом; до 3 кругов, потом решатель, потом ещё до 3. Показ владельцу — артефакт Orca (решение
владельца «Артефакты Orca, как сейчас»): публикует агент старта через CLI Orca только проверенную версию; ссылки
снимаются после вопроса о запуске. Вопрос о запуске — в чате: «Да» (с автопилотом), «В обычную очередь», «Правки»,
«Нет». После «Да» или «В обычную очередь» агент отдаёт плагину файл плана; плагин проверяет его и создаёт задачу «MVP»
и задачи плана, первая — «Утверждённые документы MVP» (перенос `docs/mvp/` в базовую ветку), последняя — «Приёмочные
тесты MVP». Экраны: «Старт MVP», «MVP».

- К11.1. Тест: «Начать MVP» в подключённом проекте без задачи «MVP» → в Orca запущен агент старта из настроек с
  инструкцией плагина в основном чекауте проекта; экран «Старт MVP» в состоянии «идёт», кнопка недоступна.
- К11.2. Тест: у проекта открыта задача «MVP» → «Начать MVP» недоступна, экран «Старт MVP» ведёт на экран «MVP».
- К11.3. Тест: в каталоге старта появился запрос ревью документа → плагин запускает ревьюера из настроек в новом
  терминале с документом и решениями владельца, его отчёт с вердиктом лежит в каталоге старта.
- К11.4. Тест: файл плана с «Да» → issue «MVP: <название>» с метками `agent-queue:mvp` и `agent-queue:autopilot`,
  критериями, «Только владелец», чек-листом по этапам и пределами; задачи плана с «MVP: #E», зависимостями «Зависит
  от #N» и меткой `agent-queue`; повторная подача того же файла не создаёт ничего второй раз.
- К11.5. Тест: файл плана с неизвестным полем или зависимостью от ключа, которого нет в плане → отказ с причиной,
  ни одной задачи не создано.
- К11.6. Тест: «В обычную очередь» → та же задача «MVP» без метки `agent-queue:autopilot`.

### Ф12. Автопилот MVP

Пока задача «MVP» открыта и у неё `agent-queue:autopilot`, там, где задача MVP была бы заблокирована, решает плагин:

| Вне автопилота | Под автопилотом |
|---|---|
| вопрос, на который задача и документы не отвечают (выбор технологии тоже) | решатель решает; вопрос о ключах, оплате, аккаунтах, доступах, деплое или пункте «Только владелец» — блокировка |
| нужен пакет | пакет из плана задачи ставится в задаче; другой — решатель |
| ревью не одобрено после круга 3 | решатель один раз по оставшимся замечаниям, потом круги 4–6; не одобрено — деление |
| три неудачи одного шага | деление |
| конфликт rebase | одна новая попытка от свежей базовой ветки, потом деление |
| лимит агента | задача отложена (Ф10) |

Решение — комментарий «Решение по #<N>» (вопрос, решение, обоснование) в задаче и в задаче «MVP». Деление: решатель
делит задачу на 2–3 части — новые задачи с «Часть #<N>», `MVP: #E` и материалом исходной (ветка, причина);
задачи, ждавшие #N, ждут части; черновой PR закрыт без мержа, исходная задача закрыта. Часть или задача, начатая
заново дважды, не делится — блокируется с историей попыток. Пределы задачи «MVP» (`in_progress`, `per_day`, `total`;
по умолчанию 3, 20 и задач плана × 1,5) соблюдаются при захвате. Раз в сутки — сводка в задаче «MVP»: влито, в
работе, заблокировано, осталось. Экраны: «MVP».

- К12.1. Тест: задача MVP под автопилотом, исполнитель задал вопрос → решатель запущен, комментарий «Решение по #<N>»
  в задаче и в задаче «MVP», исполнитель получает решение, метки `agent-queue:blocked` нет.
- К12.2. Тест: вопрос о ключах оплаты из списка «Только владелец» → задача заблокирована с «Автопилот: только
  владелец», решатель не запускался.
- К12.3. Тест: ревью не одобрено после круга 6 → решатель делит задачу; созданы 2–3 задачи с «Часть #<N>»; задача,
  ждавшая #N, теперь ждёт части; исходная задача закрыта, её PR закрыт без мержа.
- К12.4. Тест: часть разделённой задачи не одобрена после круга 6 → блокировка с историей попыток, деления нет.
- К12.5. Тест: `in_progress` 3 и три задачи MVP в работе → четвёртая не берётся.
- К12.6. Тест: с последней сводки прошли сутки → в задаче «MVP» комментарий-сводка с числами «влито», «в работе»,
  «заблокировано», «осталось».

### Ф13. Приёмка MVP

Когда все задачи MVP закрыты: полные тесты на свежей базовой ветке в своём worktree; стенд из настроек — `setup`,
`up`, ожидание ответа `url`, ревьюер проверяет MVP по критериям задачи «MVP», ТЗ и доске дизайна во встроенном
браузере Orca, `down`. Найденное — новые задачи того же MVP, не больше двух раундов. Прошла — комментарий «MVP готов к
вашей приёмке», метка `agent-queue:blocked` на задаче «MVP», уведомление. На экране «MVP» владелец: «Принимаю» —
метка `agent-queue:autopilot` снята, задача «MVP» закрыта, проект дальше живёт обычной очередью; «Есть замечания» —
агент старта в терминале Orca уточняет их с владельцем и отдаёт плагину файл с задачами того же MVP; плагин ставит их
и снимает блокировку — автопилот продолжает, потом снова приёмка. Стенда в настройках нет — задача «MVP» заблокирована
с просьбой добавить стенд. Экраны: «MVP».

- К13.1. Тест: закрыта последняя задача MVP → полные тесты на базовой ветке, стенд поднят командами `setup` и `up`,
  ревьюер запущен с критериями MVP и адресом стенда; после отчёта выполнен `down`.
- К13.2. Тест: ревьюер приёмки нашёл две проблемы → две новые задачи того же MVP с «MVP: #E»; в задаче «MVP»
  «приёмка: раунд 1 из 2».
- К13.3. Тест: приёмка прошла → комментарий «MVP готов к вашей приёмке», метка `agent-queue:blocked` на «MVP»,
  уведомление; на экране «MVP» кнопки «Принимаю» и «Есть замечания».
- К13.4. Тест: «Принимаю» → метка `agent-queue:autopilot` снята, задача «MVP» закрыта.
- К13.5. Тест: в настройках нет стенда → задача «MVP» заблокирована с текстом «Добавьте стенд приёмки в настройки
  проекта».
- К13.6. Тест: приёмка не прошла во втором раунде → задача «MVP» заблокирована с итогом обоих раундов.

### Ф14. Три системы и релиз

Плагин работает на macOS, Windows и Linux: пути, каталог данных, запуск команд проекта и агентов — по правилам
системы; команда тестов идёт оболочкой системы, на Windows — команда для Windows из настроек, если задана. Тесты
плагина идут в GitHub Actions на `ubuntu-latest`, `macos-latest`, `windows-latest`. Релиз: версия в манифесте, запись
для каталога Orca (`orca plugin release-entry`), README с установкой и требованиями. Манифест: id `agent-queue`, имя
«Agent Queue» (решение владельца). Экраны: нет.

- К14.1. Тест: путь worktree и каталога данных на подделке Windows (`win32`) и macOS (`darwin`) → путь по правилам
  этой системы, без смешения разделителей.
- К14.2. Тест: в настройках есть команда для Windows, платформа `win32` → запускается она; на `linux` — основная.
- К14.3. Тест: workflow GitHub Actions плагина гоняет его тесты на `ubuntu-latest`, `macos-latest` и
  `windows-latest`.
- К14.4. Тест: `orca plugin validate .` проходит; в манифесте id `agent-queue` и имя «Agent Queue».

## Экраны

Каждый экран словами. По этому разделу, когда владелец утвердит ТЗ, рисуется дизайн — доска `maket/index.html`: каждый

Все экраны — в панели плагина в правой боковой части Orca: на ширине 390 — панель на всю ширину кадра, на 1440 —
окно Orca с панелью справа. Вверху каждого экрана, кроме «Очереди», — «Назад» к «Очереди».

### Очередь

- Что на экране: заголовок «Agent Queue»; выбор проекта (подключённые проекты); строка проекта — «Очередь работает» или
  «Очередь остановлена», итог проверки (ок или число проблем); кнопки «Поставить задачу», «Остановить» или
  «Запустить»; меню — «Проверка проекта», «Начать MVP», «Настройки», «Подключить проект»; блок открытой задачи «MVP»
  (название, задач закрыто из всех, автопилот вкл/выкл, «MVP готов к приёмке», если ждёт); разделы со счётчиками:
  «Ждут ответа» (номер, заголовок, начало вопроса, кнопка «Ответить»), «В работе» (номер, заголовок, этап, состояние
  агента, сколько идёт), «Ждут» (номер, заголовок, «ждёт #N»), «Влиты» (номер, заголовок, когда).
- Состояния: с данными — разделы с задачами; пусто — «Очередь пуста» и «Поставить задачу»; нет подключённых
  проектов — «Нет подключённых проектов» и «Подключить проект»; загрузка — заготовки строк; ошибка — «Не удалось
  прочитать GitHub: <ошибка>» и «Повторить»; очередь остановлена — полоса «Очередь остановлена на этом компьютере» и
  «Запустить».
- Переходы: задача → «Задача»; «Ответить» → «Ответ на блокировку»; «Поставить задачу» → «Новая задача»; блок MVP →
  «MVP»; «Проверка проекта» и итог проверки → «Проверка проекта»; «Начать MVP» → «Старт MVP»; «Настройки» →
  «Настройки»; «Подключить проект» → «Подключение проекта».

### Задача

- Что на экране: номер и заголовок; бейдж статуса (ждёт, в работе, ждёт ответа, влита, отдана на деление); этап и
  состояние агента; кнопки «Открыть в GitHub», «PR», «Терминал исполнителя», «Терминал ревьюера», «Ответить» (когда
  ждёт ответа); вкладки: «Ход» (комментарии хода по времени), «Ревью» (круги: вердикт, замечания с важностью, файлом и
  строкой), «Тесты» (прогоны: SHA, итог, время, последние строки вывода), «Текст» (текст задачи Markdown).
- Состояния: в работе; ждёт ответа — вопрос сверху и «Ответить»; влита — ссылка на merge-коммит; ждёт — «ждёт #N»;
  загрузка; ошибка — «Не удалось прочитать задачу» и «Повторить».
- Переходы: «Ответить» → «Ответ на блокировку»; «Назад» → «Очередь»; «Открыть в GitHub», «PR» — браузер;
  терминалы — терминал агента в Orca.

### Новая задача

- Что на экране: поле «Заголовок»; поле «Текст» (Markdown); список «Зависит от» — открытые задачи с галочками;
  кнопки «Поставить», «Отмена».
- Состояния: форма; ошибка поля — «Нужен заголовок»; отправка — «Ставлю…», кнопки недоступны; ошибка GitHub —
  «Не удалось создать задачу: <ошибка>», введённое сохранено.
- Переходы: «Поставить» → «Задача» новой задачи; «Отмена» → «Очередь».

### Ответ на блокировку

- Что на экране: номер и заголовок задачи; вопрос координатора (Markdown); поле «Ответ»; кнопки «Ответить и
  вернуть в очередь», «Отмена».
- Состояния: форма; пустой ответ — кнопка ответа недоступна; отправка; ошибка — «Не удалось отправить: <ошибка>»,
  текст сохранён.
- Переходы: «Ответить и вернуть в очередь» → «Очередь»; «Отмена» → «Задача».

### Подключение проекта

- Что на экране: шаг 1 — список проектов Orca, ещё не подключённых; шаг 2 — проверки (git и GitHub, `gh`, агенты)
  со статусами; шаг 3 — форма: базовая ветка, команда полных тестов, команда для Windows, агенты (исполнитель,
  ревьюер, решатель, агент старта), язык текстов в GitHub, одновременно в работе, правило данных, правила для
  заданий; кнопка «Подключить».
- Состояния: выбор проекта; проверки идут; проверка не прошла — что не так и что сделать («выполните gh auth
  login», «нет удалённого репозитория GitHub»); форма; ошибки полей; подключение — «Подключаю…»; отказ — «Основной
  чекаут не на базовой ветке (или с изменениями, или отстаёт)», ничего не записано.
- Переходы: «Подключить» → «Проверка проекта»; «Назад» → «Очередь».

### Проверка проекта

- Что на экране: строки — значок «ок», «проблема» или «не проверено», текст, как исправить, кнопка «Исправить» (где

- Переходы: «Исправить» — та же строка после исправления; «Назад» → «Очередь».

### Настройки

  (вкл/выкл); координатор на этом компьютере (вкл/выкл); «Настройки проекта» — открыть `.agent-queue.json` и

- Состояния: с данными; сохранено — «Сохранено»; ошибка — «Не удалось сохранить: <ошибка>».
- Переходы: «Настройки проекта» → файл в редакторе Orca; «Назад» → «Очередь».

### MVP

- Что на экране: «MVP: <название>», бейдж (идёт, ждёт ответа, ждёт приёмки, принят); автопилот — переключатель
  «Автопилот»; пределы — в работе x из `in_progress`, взято за сутки x из `per_day`, задач x из `total`; этапы —
  задачи с их статусом; «Журнал решений» (решения решателя); «Только владелец»; приёмка — раунд и итог; кнопки
  «Открыть в GitHub», а когда ждёт приёмки — «Принимаю» и «Есть замечания».
- Состояния: идёт; заблокирована — причина; упёрлась в предел — какой; ждёт приёмки; принята; загрузка; ошибка.
- Переходы: задача этапа → «Задача»; «Есть замечания» → терминал агента старта в Orca; «Назад» → «Очередь».

### Старт MVP

- Что на экране: шаги «Вопросы → ТЗ → Дизайн → План → Запуск» с текущим; агент старта; кнопка «Открыть чат старта»

  MVP».
- Состояния: не начат — «Начать MVP» и что нужно; идёт — текущий шаг; ждёт владельца — «Ответьте в чате старта»;
  запущен — ссылка на «MVP»; ошибка — «Агент старта не запустился: <ошибка>» и «Повторить»; уже есть MVP —
  «У проекта уже есть MVP» и переход к нему.
- Переходы: «Открыть чат старта» → терминал агента в Orca; «MVP» → «MVP»; «Назад» → «Очередь».
