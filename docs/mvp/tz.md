Статус: черновик

Папка `docs/mvp/`: это ТЗ, дизайн — `maket/index.html` (доска экранов, после «ТЗ: утверждаю»), план — `plan.md`,
решения владельца дословно — `decisions.md`.

## Цель и проблема

Очередь агентов agent-queue-kit ведёт изменения проекта без человека: задача — issue GitHub, один агент её делает,
другой ревьюит, PR вливается после чистого ревью и зелёных тестов, а человек нужен, только когда задача заблокирована.
Автопилот доводит новый проект от ТЗ до принятого MVP. Сейчас кит — bash-скрипты, навыки Claude и таймер systemd:
работает только на Linux, ставится вручную (`bin/activate`, `install`, `init`), задачу ведёт агент-координатор
(LLM, который тратит токены на рутину), а увидеть очередь можно только в GitHub и в терминале.

Agent Queue — тот же кит, сделанный плагином Orca (решение владельца: «тоже что и agent-queue-kit. Мы поменяем
реализацию на плагин. Который максимально будет использовать функционалы самого orca и будет работать в Mac, Windows,
Linux»). Когда MVP заработает:

- плагин ставится из каталога Orca на macOS, Windows и Linux любым пользователем Orca;
- задачу ведёт код плагина: он берёт задачу, создаёт worktree Orca, запускает агентов через Orca, следит за их
  статусом, сам гоняет тесты, мержит; LLM нужны только исполнителю, ревьюеру, решателю автопилота и агенту старта MVP;
- очередь видна и управляется в Orca: панель, строка состояния, уведомления, ответы на блокировки;
- задачи живут в issues GitHub в своём формате плагина; проекты, которые сейчас на ките, остаются на ките.

## Пользователи и роли

| Роль | Кто это | Что делает в MVP |
|---|---|---|
| Владелец очереди | любой пользователь Orca; на его компьютере плагин работает от его входа в `gh` | подключает проект, ставит задачи, отвечает на блокировки, останавливает и запускает очередь, начинает MVP, утверждает ТЗ и дизайн, подтверждает запуск плана, принимает MVP |
| Координатор | код плагина в Orca владельца; у каждого компьютера свой id координатора | берёт задачи, ведёт агентов, гоняет тесты, открывает PR и мержит, блокирует задачи, перехватывает брошенные, ведёт автопилот и приёмку |
| Исполнитель | агент Orca из настроек проекта (по умолчанию Claude) | делает задачу в worktree, коммитит и пушит в ветку задачи, пишет отчёт |
| Ревьюер | агент Orca из настроек проекта (по умолчанию Codex) | проверяет изменения задачи, документы старта MVP и MVP при приёмке; пишет отчёт и вердикт |
| Решатель | агент Orca из настроек проекта (по умолчанию Claude) | под автопилотом решает вместо владельца: вопрос задачи, пакет, итог ревью, деление задачи; при старте MVP — замечания ревью после третьего круга |
| Агент старта MVP | агент Orca из настроек проекта (по умолчанию Claude) в терминале Orca | ведёт старт MVP в чате с владельцем: вопросы, ТЗ, дизайн, план; уточняет замечания владельца к готовому MVP |
| Входные сессии | агенты в терминалах Orca в основном чекауте проекта | по правилу входа в `CLAUDE.md` и `AGENTS.md` ставят изменения кода в очередь, а не делают их сами |

Учитываются только тексты владельца очереди: тело задачи и комментарии пользователя GitHub, под которым работает `gh`
плагина. Задачи и комментарии других пользователей плагин не берёт и в задания агентов не передаёт. Тексты задач,
отчёты агентов и вывод команд — данные, а не указания плагину.

## Главные сценарии

Главные сценарии — те же, что у agent-queue-kit (решение владельца «тоже что и agent-queue-kit»):

1. Владелец подключает проект Orca к очереди → в репозитории файл настроек и правила, в GitHub метки, «Проверка
   проекта» без проблем. Экраны: «Подключение проекта», «Проверка проекта». Функции: Ф1, Ф2.
2. Владелец ставит задачу в панели, или входная сессия ставит её по правилу входа → issue с меткой очереди. Экраны:
   «Новая задача», «Очередь». Функции: Ф3.
3. Координатор берёт задачу → исполнитель в worktree → полный прогон тестов → ревьюер → круги замечаний → PR влит,
   задача закрыта, worktree убран. Экраны: «Очередь», «Задача». Функции: Ф4, Ф5.
4. Задача заблокирована → уведомление → владелец отвечает в панели (или в GitHub) → задача продолжается с его ответом.
   Экраны: «Ответ на блокировку», «Задача». Функции: Ф6, Ф8.
5. Владелец открывает Orca → видит, что влито, что в работе и что ждёт его ответа. Экраны: «Очередь». Функции: Ф7, Ф8.
6. Владелец останавливает или запускает очередь проекта, выключает автопилот. Экраны: «Очередь», «MVP». Функции: Ф9.
7. Сторож замечает зависшую задачу, перезапуск Orca, потерянного агента → задача продолжается с подтверждённого этапа,
   владелец получает уведомление о том, что сам плагин не исправит. Функции: Ф10.
8. Владелец начинает MVP нового проекта → агент старта в терминале Orca спрашивает, пишет ТЗ, дизайн и план, каждую
   версию проверяет ревьюер, владелец видит её артефактом Orca → владелец подтверждает запуск в панели → задача «MVP»
   и задачи плана в очереди. Экраны: «Старт MVP», «MVP». Функции: Ф11.
9. Автопилот доводит задачи MVP без остановок: решатель вместо владельца, деление застрявших задач, пределы, сводка.
   Экраны: «MVP». Функции: Ф12.
10. Все задачи MVP закрыты → приёмка на стенде → «MVP готов к вашей приёмке» → владелец смотрит стенд, принимает в
    панели или даёт замечания. Экраны: «MVP». Функции: Ф13.

| Состояние на компьютере — каталог данных плагина вне репозиториев | задания и отчёты агентов, файлы вердиктов ревью, полный вывод прогонов тестов, сохранённая незапушенная работа (коммиты пачкой, изменения патчем, неотслеживаемые файлы архивом; `.env*` — никогда), журнал координатора и сторожа, отметки уведомлений | координатор и сторож | 30 дней после закрытия задачи, потом плагин удаляет |
| Настройки плагина в Orca | язык интерфейса (`English` или `Русский`); интервал проверки очереди (минуты, по умолчанию 5); уведомления о мержах (вкл/выкл); координатор на этом компьютере (вкл/выкл); остановленные очереди проектов на этом компьютере | владелец в экране «Настройки» и кнопками «Остановить»/«Запустить» | в хранилище плагина Orca |

В GitHub плагин пишет только сводки: отчёты агентов и вывод команд остаются в каталоге данных. Строки замечаний и
сводки, которые попадают в GitHub, подчиняются правилу данных проекта: задания агентов требуют писать их без данных,
которые правило запрещает.

## Функции и критерии приёмки

Каждая функция — с экранами раздела «Экраны» (по названию) и критериями, которые проверяет автоматический тест. Задача
«Приёмочные тесты MVP» пишет e2e-тест на каждый критерий; критерий, который тест проверить не может, переписывается.

Тесты идут только с подделками (решение владельца «Только подделки»): поддельный хост Orca (`orca/testing`:
`mockHost`, `mountWorker`, `mount`), поддельные `gh`, git, CLI Orca и агенты, без сети и без настоящего GitHub.
«Проверка очереди» в критериях — один проход координатора, который тест вызывает сам, а не ждёт по таймеру; время в
тестах — поддельное.

### Ф1. Подключение проекта

Мастер подключает проект Orca к очереди. Экраны: «Подключение проекта», «Проверка проекта».

1. Владелец выбирает проект из проектов Orca, ещё не подключённых (подключён — в основном чекауте есть закоммиченный
   `.agent-queue.json`). Проект на agent-queue-kit (есть `.agent-queue/config.json`) в списке помечен «На
   agent-queue-kit — переход после MVP» и не выбирается: его файлы, метки и правило входа плагин не трогает.
2. Плагин проверяет: проект — git-репозиторий с удалённым репозиторием GitHub; `gh` установлен, вход выполнен, у
   пользователя есть доступ на запись; агенты из настроек известны Orca.
3. Форма настроек: базовая ветка (по умолчанию — ветка по умолчанию репозитория), команда полных тестов
   (обязательна), команда для Windows (по желанию), агенты — исполнитель, ревьюер, решатель, агент старта (из агентов
   Orca; по умолчанию Claude, Codex, Claude, Claude), язык текстов в GitHub, правило данных (шаблон), правила для
   заданий (шаблон), одновременно задач в работе (по умолчанию 1), зависимости worktree (по умолчанию `shared`).
4. «Подключить» — только когда основной чекаут на базовой ветке, без изменений и его HEAD после свежего `fetch`
   совпадает с удалённой базовой веткой (ни отстаёт, ни опережает); иначе ничего не пишет и называет причину. Порядок:
   недостающие метки плагина в GitHub (повтор создаёт только недостающие); `.agent-queue.json`, `.agent-queue.md` и
   блок правила входа в `CLAUDE.md` и `AGENTS.md` (файла нет — создаёт); коммит только этих четырёх файлов; пуш в
   базовую ветку. Пуш отклонён — локальный коммит отменяется, чекаут снова на прежнем SHA, проект не подключён;
   «Подключить» можно нажать снова. Потом открывается «Проверка проекта».

- К1.1. Тест: подключить проект при исправных `gh` и git → коммит в базовой ветке меняет только `.agent-queue.json`,
  `.agent-queue.md`, `CLAUDE.md`, `AGENTS.md`; в GitHub шесть меток плагина; коммит запушен; открыт экран «Проверка
  проекта».
- К1.2. Тест: `gh` без входа → мастер показывает «gh: нет входа — выполните gh auth login», «Подключить» недоступна,
  файлы и GitHub не меняются.
- К1.3. Тест: основной чекаут не на базовой ветке, или с изменениями, или его HEAD отстаёт от удалённой базовой ветки
  или опережает её → «Подключить» отказывает с этой причиной, ничего не записано и не запушено.
- К1.4. Тест: пустая команда полных тестов → ошибка у поля, ничего не записано.
- К1.5. Тест: у проекта нет удалённого репозитория GitHub → «Подключение невозможно: нет удалённого репозитория
  GitHub», форма настроек не открывается.
- К1.6. Тест: у части меток уже есть → создаются только недостающие; в `CLAUDE.md` с чужим текстом этот текст
  остаётся, блок правила добавлен один раз.
- К1.7. Тест: пуш отклонён → основной чекаут на прежнем SHA без нового коммита и без новых файлов, проект в списке не
  подключён; повторное «Подключить» после устранения причины подключает его.
- К1.8. Тест: в проекте есть `.agent-queue/config.json` → проект помечен «На agent-queue-kit — переход после MVP», его
  нельзя выбрать; его файлы и метки не меняются.

### Ф2. Проверка проекта

То же, что `doctor` кита: строки «ок», «проблема» (с тем, как исправить) и «не проверено» (с ошибкой). Где плагин
может исправить сам — кнопка «Исправить». Строки: версия плагина и Orca (не старше 1.4.273); CLI Orca доступен;
`gh` (установлен, вход, доступ на запись); git; файл настроек (разбирается, известные поля, верные типы); правила для
заданий есть; блок правила входа совпадает с шаблоном этой версии плагина; метки в GitHub; агенты из настроек известны
Orca; координатор на этом компьютере включён, очередь проекта не остановлена; у открытой задачи «MVP» под автопилотом

### Ф3. Постановка задачи

Задача ставится из панели или входной сессией по правилу входа: issue владельца с меткой `agent-queue`. Зависимость —
строка «Зависит от #N» (или «Depends on #N»): пока #N открыта, задачу не берут. Экраны: «Новая задача», «Очередь».

Правило входа говорит только входным сессиям — агентам в основном чекауте проекта: изменение кода — в очередь,
командой `gh issue create` с меткой `agent-queue` и текстом по формату плагина (запрос пользователя, его решения и
предложения сессии раздельно; зависимости строкой «Зависит от #N»); открытые вопросы — с пользователем до постановки;
данных с прода в задаче нет; «сделай сам» и «без очереди» — сессия делает сама; файлы настроек очереди меняет только
владелец. Агент в worktree задачи (исполнитель, ревьюер) правило входа не выполняет: его задание говорит об этом прямо.

### Ф4. Координатор: захват и ведение задачи

Пока Orca открыта, координатор этого компьютера включён и очередь проекта не остановлена, плагин раз в интервал
(настройка, по умолчанию 5 минут) проверяет очередь каждого подключённого проекта. Берёт самую старую задачу в
очереди: метка `agent-queue`, нет `working`, `blocked`, `split`, нет открытых зависимостей, нет отложения, задач в
работе меньше предела проекта (и для задачи MVP — в пределах `in_progress` и `per_day`, Ф12).

**Захват.** GitHub не даёт атомарного замка, поэтому захват — порядок комментариев. Координатор ставит
`agent-queue:working` и пишет заявку со своим id; через 60 секунд перечитывает комментарии задачи. Ведёт задачу автор
первой заявки после последнего освобождения (блокировка, отложение, деление, снятие метки владельцем); перехват
(Ф10) — заявка с пометкой «перехват», которая открывает новый отсчёт. Все координаторы читают один и тот же порядок
комментариев GitHub и решают одинаково. Проигравший пишет «Задачу ведёт <id>» и не запускает агентов. Перед каждым
действием по задаче — запуск или сообщение агенту, комментарий, метка, PR, мерж, удаление worktree — координатор
перечитывает заявки; задача ведёт не он (перехват после его заявки или освобождение) — он останавливает своих агентов
этой задачи, сохраняет незапушенную работу её worktree в каталог данных (Ф6), пишет об этом один комментарий и больше
по задаче ничего не делает.

**Ведение.** Worktree Orca на ветке `agent-queue/issue-<N>` от `origin/<базовая ветка>` (Orca готовит его своей
подготовкой проекта, `orca.yaml`). Исполнитель в нём с заданием: текст задачи и комментарии владельца; правила для
заданий; правило данных; что правило входа к нему не относится; ограничения — тесты только полной командой проекта;
коммит и пуш только в ветку задачи; не мержить; не трогать `.env*`, `.agent-queue.json`, `.agent-queue.md`;
зависимости не менять, кроме пакетов, которые задание разрешает (Ф12); вопрос — в отчёт, не догадкой; выбор
технологии, который задача и документы не фиксируют, — вопрос, не решение исполнителя. Путь файла отчёта — в
каталоге данных. Отчёт готов, когда агент в Orca закончил («done») и файл отчёта есть. После первого пуша — черновой
PR в базовую ветку с `Closes #N`. После каждого этапа — комментарий хода на языке проекта со служебной меткой этапа:
захват, исполнитель запущен, сделано и PR, прогон тестов, круг ревью k — m замечаний, исправлено, влита; последний
комментарий живой задачи не старше 2 часов.

**Тесты.** После отчёта исполнителя плагин сам запускает полную команду тестов в worktree на закоммиченном дереве без
незакоммиченных и неотслеживаемых файлов и записывает прогон: SHA, код выхода, время, чистое ли дерево до и после,
полный вывод в каталог данных, строку сводки — в комментарий хода. Засчитывается только прогон с кодом 0 на чистом
дереве, у которого HEAD в конце тот же. Красный прогон — вывод уходит тому же исполнителю; три красных прогона подряд
— блокировка (Ф6) или деление (Ф12).

- К4.1. Тест: задача в «Ждут» → после проверки очереди у неё метка `agent-queue:working`, заявка с id координатора,

### Ф5. Ревью, круги замечаний и мерж

**Ревью.** Ревьюер запускается в worktree задачи с ожидаемым SHA и заданием: только чтение; проверить изменения
против задачи, правил и правила данных; запустить полные тесты; записать отчёт и файл вердикта — `issue`, `round`,
`reviewed_sha`, `verdict` (`approve`, `changes`, `head-mismatch`), замечания с важностью (`critical`, `major`,
`minor`, `nit`), файлом, строкой и одной строкой сути без данных, которые запрещает правило данных. Ни один агент не
даёт режима «только чтение», поэтому после ревью плагин сам проверяет, что HEAD и состояние worktree не изменились;
изменились — ревью отбрасывается, worktree возвращается к запушенной ветке, ревью повторяется. Неверный файл вердикта
не засчитывается: ревьюер получает причину, круг не считается.

**Круги.** `changes` — замечания тому же исполнителю (его терминал не принимает — новый исполнитель в том же worktree
с отчётами), потом новый круг. Замечание о выборе технологии, который задача и документы не фиксируют, исполнителю не
идёт: сначала владелец (блокировка, Ф6) или решатель (Ф12), потом решение — исполнителю вместе с остальными
замечаниями круга. Не больше трёх кругов; после третьего только minor/nit — ещё один круг по изменениям после
последнего ревью; иначе блокировка (под автопилотом — Ф12).

**Допуск к мержу.** Мерж только когда все условия выполнены на свежем `fetch`:

1. ревьюер одобрил SHA X (`approve`, файл вердикта верный);
2. есть засчитанный прогон тестов SHA Y, где Y = X, или Y — rebase X на новую базу без конфликтов, и изменения Y
   относительно базы совпадают с изменениями X (отличаются только строки контекста); rebase с разрешением конфликтов
   — ещё круг ревью разрешения, который одобряет сам Y;
3. база — предок Y, голова PR — Y, ветка задачи не меняет `.agent-queue.json` и `.agent-queue.md`.

База ушла вперёд — исполнитель делает rebase, полный прогон на новом SHA. Мерж — merge-коммит GitHub с условием, что
голова PR — Y; GitHub отказал (база или голова сдвинулись) — снова допуск с шага 2. После мержа плагин читает PR из
GitHub: состояние `MERGED`, база — базовая ветка, merge-коммит содержит Y; только тогда тело PR переписано по итогам
(Зачем, Что сделано, Проверка, Ревью), ветка удалена, задача закрыта, итоговый комментарий, основной чекаут обновлён
(когда он на базовой ветке и чистый), шаги после мержа из настроек, worktree убран. PR влит иначе (другая голова или
база) — блокировка. Перезапуск плагина после мержа: PR уже `MERGED` — координатор доводит оставшиеся шаги и второй раз
не мержит. Мержи проекта на одном компьютере идут по одному.

- К5.1. Тест: ревьюер вернул `changes` с двумя замечаниями → исполнитель получает оба, идёт круг 2; в задаче

### Ф6. Блокировка, сохранение работы и ответ владельца

**Когда.** Нужен человек: вопрос, на который задача и документы не отвечают (выбор технологии тоже); нужен новый пакет
или зависимость (под автопилотом — Ф12); задача требует изменить настройки очереди; три неудачи одного шага; ревью не
одобрено за разрешённые круги; конфликт rebase, который исполнитель не разрешил; сбой Orca, GitHub или агента,
который не запускается.

**Сохранение работы.** Перед тем как убрать worktree (блокировка, перехват, потеря агента, деление) плагин проверяет в
нём незапушенные коммиты, изменённые и неотслеживаемые файлы. Есть — пушит коммиты в ветку задачи; пуш не прошёл или
остались файлы — сохраняет их в каталог данных (коммиты пачкой git, изменения патчем, неотслеживаемые файлы архивом;
`.env*` — никогда) и worktree не убирает. В комментарии — только имена файлов и путь сохранения, не содержимое.

**Блокировка.** Работа сохранена, агенты задачи остановлены, worktree убран (если сохранение позволило), метка
`agent-queue:blocked` вместо `working` — последней записью, комментарий: что сделано, что мешает, точный вопрос;
уведомление Orca. GitHub не принимает записи — блокировка не записана: задача остаётся у координатора, агенты
остановлены, worktree не трогается, уведомление «Не удалось заблокировать #<N>: <ошибка>», повтор на следующей
проверке.

**Ответ.** Владелец отвечает в панели («Ответ на блокировку») или в GitHub (комментарий и снятие метки). Панель
сначала пишет комментарий, потом снимает метку; метка не снялась — «Повторить» снимает только метку, комментарий не
повторяется. Задача снова в очереди, следующий захват продолжает её с ветки, задание содержит ответ владельца, круги
ревью считаются заново. Экраны: «Ответ на блокировку», «Задача», «Очередь».

- К6.1. Тест: исполнитель написал в отчёте вопрос → метка `agent-queue:blocked`, комментарий с вопросом, уведомление

  задачи.

- К6.3. Тест: метку сняли в GitHub после комментария владельца → задача берётся, задание содержит этот комментарий.
- К6.4. Тест: поле ответа пустое → кнопка «Ответить и вернуть в очередь» недоступна.
- К6.5. Тест: при блокировке пуш отклонён → незапушенный коммит сохранён пачкой в каталоге данных, worktree не убран,

### Ф7. Панель очереди

интервала проверки. Экран «Задача» берёт ход, круги ревью (вердикт, строки замечаний) и прогоны (SHA, итог, строка

компьютере, который вёл задачу, 30 дней. Экраны: «Очередь», «Задача».

  «Повторить»; задачи прежнего чтения не показаны как текущие.
- К7.4. Тест: задача на втором круге ревью → в «В работе» у неё этап «Ревью, круг 2».
- К7.5. Тест: нажать на задачу → экран «Задача» с её текстом, кругами ревью и прогонами тестов из комментариев хода.
- К7.6. Тест: язык интерфейса «English» → заголовки и кнопки панели на английском; «Русский» — на русском.
- К7.7. Тест: задачу вёл другой компьютер → на вкладке «Тесты» строки сводки прогонов и пометка «Полный вывод — на
  компьютере <id>»; кнопок терминалов агентов нет.

- К8.1. Тест: задача заблокирована → строка состояния «Очередь: 0 · 1» с тоном предупреждения; уведомление одно,

### Ф9. Стоп и пуск

**«Остановить» очередь проекта** (на этом компьютере): координатор не берёт новые задачи проекта, не перехватывает
чужие, не начинает новых шагов автопилота (деление, сводка, приёмка) по задаче «MVP» проекта. Задачи, которые он уже
ведёт, доводит до мержа или блокировки — со сторожем (Ф10) для них; начатое деление доводит до конца (части созданы,
зависимости перенесены, исходная закрыта), чтобы не оставить его наполовину. «Запустить» — снова всё.

**«Выключить автопилот»** на экране «MVP» снимает `agent-queue:autopilot` с задачи «MVP»; «Включить автопилот» —
ставит. Без автопилота вопросы задач MVP идут владельцу (Ф6), деление и приёмка не начинаются; задача с
`agent-queue:split`, деление которой ещё не начато, получает `agent-queue:blocked` вместо `split` и комментарий
«Автопилот выключен: задача ждала деления — решите сами». Экраны: «Очередь», «MVP».

- К9.1. Тест: очередь проекта остановлена, одна задача в работе, одна ждёт → проверка очереди новую не берёт, задача в
  работе доходит до мержа.
- К9.2. Тест: «Запустить» → следующая проверка очереди берёт ждущую задачу.
- К9.3. Тест: «Выключить автопилот» → метка `agent-queue:autopilot` снята; следующий вопрос задачи MVP блокирует её
  (Ф6), решатель не спрашивается.
- К9.4. Тест: остановка после создания первой части деления → деление доведено: все части созданы, зависимые ждут
  части, исходная закрыта; новых задач координатор не берёт.
- К9.5. Тест: автопилот выключен, у задачи `agent-queue:split`, деление не начато → метка `split` заменена на
  `blocked`, комментарий «Автопилот выключен: задача ждала деления — решите сами».

### Ф10. Сторож

Внутри плагина, раз в 5 минут, пока Orca открыта. Сбой чтения GitHub никогда не считается пустой очередью или брошенной
задачей. Одно уведомление на условие, пока оно держится.

**Восстановление с подтверждённого этапа.** Этап задачи — служебная метка последнего комментария хода. Задача в работе
у этого координатора, а её агента в Orca нет (перезапуск Orca, закрытый терминал): живые агенты задачи (их видно в
Orca) не дублируются; продолжение по этапу — исполнитель: новый исполнитель в worktree задачи (worktree нет — новый
с ветки) с последним отчётом; тесты: прогон заново; ревью: новый ревьюер того же SHA; мерж: проверка PR в GitHub —
`MERGED` доводится до конца (Ф5). Комментарий «Продолжено после потери агента: <этап>».

**Перехват.** Задача в работе у другого координатора, комментариев хода 3 часа → заявка «Перехват: предыдущий
координатор молчал 3 часа»; продолжение с ветки по этапу. Незапушенная работа прежнего координатора остаётся на его
компьютере: он сохранит её, когда увидит перехват (Ф4).

**Уведомления.** Агент задачи ждёт ввода человека 30 минут — «#<N>: агент ждёт ввода» (в панели у задачи — переход к
его терминалу). Агент упёрся в лимит использования — задача отложена на час: комментарий «Отложено до <время>», метка
`working` снята, до этого времени задачу не берут. GitHub не прочитан три проверки подряд. Задача «MVP» под
автопилотом: 6 часов ни одного мержа и ничего в работе; достигнут предел; готова к приёмке или заблокирована.

- К10.1. Тест: задача на этапе «исполнитель», агента в Orca нет → запущен новый исполнитель в worktree задачи,
  комментарий «Продолжено после потери агента: исполнитель».
- К10.2. Тест: задача на этапе «ревью» SHA X, ревьюера в Orca нет, исполнитель жив → запущен новый ревьюер с SHA X,
  нового исполнителя нет.
- К10.3. Тест: задача на этапе «мерж», PR в GitHub уже `MERGED` → задача закрыта, ветка удалена, ни одного агента не
  запущено.
- К10.4. Тест: задача в работе у другого id, последний комментарий хода 3 часа назад → заявка «Перехват…», агенты
  этого координатора продолжают с ветки.
- К10.5. Тест: агент в состоянии «waiting» 30 минут → одно уведомление «#<N>: агент ждёт ввода»; вторая проверка
  нового не показывает; после выхода из ожидания условие снято.
- К10.6. Тест: GitHub не прочитан три проверки подряд → уведомление; ни одна задача не перехвачена и не взята.
- К10.7. Тест: отчёт агента о лимите использования → комментарий «Отложено до <время + 1 ч>», метки `working` нет;
  проверка до этого времени задачу не берёт, после — берёт.

### Ф11. Старт MVP

**Запуск агента.** «Начать MVP» в панели (подключённый проект без открытой задачи «MVP») запускает агента старта в
терминале Orca основного чекаута проекта с инструкцией плагина. Агент делает то, что сейчас навык
`/agent-queue-start`: спрашивает владельца в чате по блокам (цель, данные и интеграции, состав MVP, «только
владелец»), записывает ответы дословно в `decisions.md`, пишет ТЗ (экраны словами), после «ТЗ: утверждаю» в чате —
доску дизайна `maket/index.html`, после «Дизайн: утверждаю» — план; всё в `docs/mvp/` в своём worktree на ветке
`agent-queue/mvp-spec`, каждая версия — коммит.

**Ревью и показ — через плагин.** Агент старта не публикует и не ревьюит сам: он кладёт в каталог старта запрос с
коммитом и файлами. Ревью: плагин запускает ревьюера из настроек в новом терминале с файлами этого коммита и
решениями владельца из `decisions.md`, записывает отчёт с вердиктом, кругом, коммитом и хэшами файлов; до трёх кругов
на показ, потом решатель отвечает по оставшимся замечаниям, потом ещё до трёх. Показ: плагин публикует файл
артефактом Orca (решение владельца «Артефакты Orca, как сейчас») только когда файл на диске совпадает с версией,
которую видело последнее ревью этого показа (или ревью не смогло пройти — тогда с пометкой «ревьюер не проверял:
<причина>»); следующий показ того же файла обновляет тот же артефакт, ссылка не меняется. Ссылку и итог ревью агент
передаёт владельцу в чате; «Правки» — новые версии, ревью и показы по той же ссылке.

**Подтверждение запуска — в панели.** Когда план показан, агент кладёт запрос запуска с файлом плана. Плагин
принимает его, только если файл плана совпадает с версией, которую одобрило последнее ревью плана, а ТЗ, доска и
план в коммите запроса — те, что видели их последние ревью и показы. Экран «Старт MVP» показывает сводку (задач,
этапов, пределы, «Только владелец», коммит, итоги ревью ТЗ, дизайна и плана) и вопрос «Запустить MVP?»: «Да» (с
автопилотом), «В обычную очередь», «Правки» (агент правит план, новое ревью и показ), «Нет». Задачи создаёт только
нажатие владельца в панели: файл плана без него ничего не создаёт. После «Да», «В обычную очередь» или «Нет» плагин
снимает ссылки всех показов старта, потом пушит ветку `agent-queue/mvp-spec` (для «Да» и «В обычную очередь») и
убирает worktree старта; ссылка, которую снять не удалось, названа на экране — владелец удалит её в панели
артефактов Orca.

**План в очередь.** Плагин проверяет план (известные поля, уникальные ключи, зависимости только на ключи плана, без
циклов) и создаёт в таком порядке: задача «MVP» со служебной меткой плана (id плана, коммит документов), потом задачи
плана по одной, каждая со служебной меткой своего ключа; потом чек-лист задачи «MVP». Повтор после сбоя находит уже
созданное по меткам и создаёт только недостающее. Первая задача плана — «Утверждённые документы MVP»: перенести
`docs/mvp/` из запушенного коммита ветки `agent-queue/mvp-spec` в базовую ветку как есть; все остальные задачи
зависят от неё; последняя — «Приёмочные тесты MVP», зависит от всех остальных. Экраны: «Старт MVP», «MVP».

- К11.1. Тест: «Начать MVP» в подключённом проекте без задачи «MVP» → в Orca запущен агент старта из настроек с
  инструкцией плагина в основном чекауте проекта; экран «Старт MVP» в состоянии «идёт», кнопка недоступна.
- К11.2. Тест: у проекта открыта задача «MVP» → «Начать MVP» недоступна, экран «Старт MVP» ведёт на экран «MVP».
- К11.3. Тест: в каталоге старта запрос ревью `tz.md` коммита C → плагин запускает ревьюера из настроек в новом
  терминале с файлом коммита C и решениями владельца; отчёт с вердиктом, кругом, C и хэшем файла лежит в каталоге
  старта.
- К11.4. Тест: запрос показа файла, изменённого после последнего ревью → отказ «не проверенная версия», ничего не
  опубликовано; файл той версии, что видело ревью, → опубликован, второй показ того же файла обновляет тот же
  артефакт.
- К11.5. Тест: запрос запуска, файл плана отличается от версии последнего ревью плана → отказ, экран «Старт MVP» не
  показывает вопрос запуска.
- К11.6. Тест: запрос запуска верный, владелец не нажимал → ни одной задачи не создано; «Да» → issue «MVP: <название>»
  с метками `agent-queue:mvp` и `agent-queue:autopilot`, критериями, «Только владелец», чек-листом по этапам и
  пределами; задачи плана с «MVP: #E», «Зависит от #N» и меткой `agent-queue`.
- К11.7. Тест: «В обычную очередь» → та же задача «MVP» без метки `agent-queue:autopilot`.
- К11.8. Тест: план с неизвестным полем, зависимостью от ключа, которого нет в плане, или циклом зависимостей → отказ
  с причиной, ни одной задачи не создано.
- К11.9. Тест: сбой после создания задачи «MVP» и двух задач плана, повтор → создаются только недостающие задачи,
  задача «MVP» одна, чек-лист полный.
- К11.10. Тест: после «Да» ссылки всех показов старта сняты до удаления worktree старта; ссылку, которую снять не
  удалось, экран «Старт MVP» называет.
- К11.11. Тест: задачи плана, кроме первой, зависят от «Утверждённых документов MVP»; «Приёмочные тесты MVP» зависят
  от всех остальных.

### Ф12. Автопилот MVP

Пока задача «MVP» открыта и у неё `agent-queue:autopilot`, там, где задача MVP была бы заблокирована, решает плагин:

| Вне автопилота | Под автопилотом |
|---|---|
| вопрос, на который задача и документы не отвечают (выбор технологии тоже, найденный исполнителем или ревьюером) | решатель решает; вопрос о ключах, оплате, аккаунтах, доступах, деплое или пункте «Только владелец» — блокировка |
| нужен пакет | зависимости worktree `own` и пакет в разделе «Пакеты» задачи — исполнитель ставит его в задаче (задание разрешает именно эти пакеты); другой пакет — решатель, разрешение приходит исполнителю после решения; зависимости `shared` — блокировка |
| ревью не одобрено после круга 3 | решатель один раз по оставшимся замечаниям, потом круги 4–6; не одобрено — деление |
| три неудачи одного шага | деление |
| конфликт rebase | одна новая попытка от свежей базовой ветки (прежняя ветка сохранена пачкой), потом деление |
| лимит агента | задача отложена (Ф10) |

Решение — комментарий «Решение по #<N>» (вопрос, решение, обоснование) в задаче и в задаче «MVP».

**Деление.** Решатель делит задачу на 2–3 части. Порядок записей: части — новые задачи с «Часть #<N>», `MVP: #E` и
материалом исходной (ветка, причина, сохранённая работа); затем задачи, ждавшие #N, ждут части; затем чек-лист «MVP»;
черновой PR закрыт без мержа; исходная задача закрыта последней — пока у неё остаются зависимые, она открыта. Повтор
после сбоя делает только оставшиеся записи. Часть или задача, начатая заново дважды, не делится — блокируется с
историей попыток.

**Пределы.** Из текста задачи «MVP» (владелец может менять числа): `in_progress` — задач MVP в работе одновременно,
держит захват; `per_day` — задач MVP, взятых за последние 24 часа (скользящее окно), держит захват; `total` — всего
задач MVP с частями и исправлениями после приёмки, держит только добавление задач (части, задачи приёмки), не
захват. По умолчанию 3, 20 и число задач плана × 1,5 с округлением вверх. Деление, которое превысило бы `total`, не
делается: задача блокируется с просьбой поднять `total`.

**Сводка.** Раз в сутки — комментарий в задаче «MVP»: влито, в работе, заблокировано, осталось. Экраны: «MVP».

- К12.1. Тест: задача MVP под автопилотом, исполнитель задал вопрос → решатель запущен, комментарий «Решение по #<N>»
  в задаче и в задаче «MVP», исполнитель получает решение, метки `agent-queue:blocked` нет.
- К12.2. Тест: вопрос о ключах оплаты из списка «Только владелец» → задача заблокирована с «Автопилот: только
  владелец», решатель не запускался.
- К12.3. Тест: ревью не одобрено после круга 6 → решатель делит задачу; созданы 2–3 задачи с «Часть #<N>»; задача,
  ждавшая #N, теперь ждёт части; исходная задача закрыта последней, её PR закрыт без мержа.
- К12.4. Тест: часть разделённой задачи не одобрена после круга 6 → блокировка с историей попыток, деления нет.
- К12.5. Тест: `in_progress` 3 и три задачи MVP в работе → четвёртая не берётся.
- К12.6. Тест: `total` равен числу задач MVP → захват следующей задачи плана идёт; деление, которое добавило бы
  задачи, не делается — задача заблокирована с просьбой поднять `total`.
- К12.7. Тест: за последние 24 часа взято 20 задач MVP при `per_day` 20 → новая не берётся; когда самый ранний захват
  выходит из окна — берётся.
- К12.8. Тест: зависимости `own`, пакет в разделе «Пакеты» задачи → задание исполнителя разрешает ставить именно его;
  зависимости `shared` → задача заблокирована с вопросом о пакете.
- К12.9. Тест: сбой деления после создания частей, повтор → частей не больше, чем решил решатель; зависимые ждут
  части; исходная закрыта.
- К12.10. Тест: с последней сводки прошли сутки → в задаче «MVP» комментарий-сводка с числами «влито», «в работе»,
  «заблокировано», «осталось».

### Ф13. Приёмка MVP

**Когда.** Только под автопилотом: все задачи MVP закрыты, задача «MVP» открыта и не заблокирована, очередь проекта
на этом компьютере не остановлена. В обычной очереди («В обычную очередь» или автопилот выключен) приёмки нет:
экран «MVP» показывает «Все задачи закрыты» и кнопки владельца.

**Ход.** Новый worktree на свежей базовой ветке → `setup` стенда → полная команда тестов → `up` → ожидание ответа
`url` → ревьюер проверяет MVP по критериям задачи «MVP», ТЗ и доске дизайна во встроенном браузере Orca → `down` →
worktree убран. `down` и уборка выполняются при любом исходе, ошибке тоже. Найденное — новые задачи того же MVP (в
пределах `total`), не больше двух раундов. Прошла — комментарий «MVP готов к вашей приёмке» с числом задач MVP,
метка `agent-queue:blocked` на задаче «MVP», уведомление. Не прошла во втором раунде — блокировка «MVP» с итогом обоих
раундов. Стенда в настройках нет — задача «MVP» заблокирована с просьбой добавить стенд.

**Владелец.** На экране «MVP», когда приёмка прошла или не прошла за два раунда: «Открыть стенд» — плагин поднимает
стенд базовой ветки (`setup`, `up`) и открывает `url` во встроенном браузере Orca, «Закрыть стенд» — `down` и уборка;
«Принимаю» — плагин перечитывает задачу «MVP»: все её задачи закрыты, и число задач то же, что в комментарии «MVP
готов»; тогда метка `agent-queue:autopilot` снята, задача «MVP» закрыта, проект дальше живёт обычной очередью; иначе
отказ с причиной. «Есть замечания» — агент старта в терминале Orca уточняет их с владельцем и кладёт файл задач того
же MVP; плагин ставит их (как план, Ф11, в пределах `total`) и снимает блокировку — автопилот продолжает, потом снова
приёмка. Экраны: «MVP».

- К13.1. Тест: закрыта последняя задача MVP под автопилотом → в порядке: worktree базовой ветки, `setup`, полные
  тесты, `up`, ответ `url`, ревьюер с критериями MVP и адресом стенда, `down`, worktree убран.
- К13.2. Тест: `up` упал → `down` выполнен, worktree убран, задача «MVP» заблокирована с ошибкой стенда.
- К13.3. Тест: ревьюер приёмки нашёл две проблемы → две новые задачи того же MVP с «MVP: #E»; в задаче «MVP»
  «приёмка: раунд 1 из 2».
- К13.4. Тест: приёмка прошла → комментарий «MVP готов к вашей приёмке», метка `agent-queue:blocked` на «MVP»,
  уведомление; на экране «MVP» кнопки «Открыть стенд», «Принимаю» и «Есть замечания».
- К13.5. Тест: «Принимаю», все задачи закрыты и их число то же → метка `agent-queue:autopilot` снята, задача «MVP»
  закрыта; добавилась открытая задача MVP → отказ «Есть открытые задачи MVP».
- К13.6. Тест: в настройках нет стенда → задача «MVP» заблокирована с текстом «Добавьте стенд приёмки в настройки
  проекта».
- К13.7. Тест: приёмка не прошла во втором раунде → задача «MVP» заблокирована с итогом обоих раундов; на экране
  «MVP» есть «Есть замечания».
- К13.8. Тест: все задачи MVP закрыты, автопилота нет → приёмка не запускается, экран «MVP» показывает «Все задачи
  закрыты».

### Ф14. Три системы, поставка и релиз

- К14.1. Тест: путь worktree и каталога данных на подделке Windows (`win32`) и macOS (`darwin`) → путь по правилам

- К14.2. Тест: в настройках есть команда для Windows, платформа `win32` → запускается она; на `linux` — основная.
- К14.3. Тест: workflow GitHub Actions плагина гоняет проверку манифеста, типов и тестов на `ubuntu-latest`,

  Queue»; в папке плагина после подготовки разработки нет симлинков.

этого сам, а зовёт владельца.

- Внести плагин в каталог Orca со своего аккаунта — нужен для Ф14 (релиз); задача MVP готовит запись релиза.
- Включить GitHub Actions в репозитории плагина (у частного репозитория считаются минуты) — нужен для Ф14 (К14.3
  проверяет workflow, сам прогон на трёх системах — в Actions).
- Аккаунт Orca с включённой публикацией артефактов — нужен для показов старта MVP (Ф11) у каждого пользователя;
  у владельца он уже есть.
