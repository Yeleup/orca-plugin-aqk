Статус: черновик

Папка `docs/mvp/`: это ТЗ, дизайн — `maket/index.html` (доска экранов, после «ТЗ: утверждаю»), план — `plan.md`,
решения владельца дословно — `decisions.md`.

## Цель и проблема

Очередь агентов agent-queue-kit ведёт изменения проекта без человека: задача — issue GitHub, один агент её делает,
другой ревьюит, PR вливается после чистого ревью и зелёных тестов, а человек нужен, только когда задача заблокирована.
Автопилот доводит новый проект от ТЗ до принятого MVP. Сейчас кит — bash-скрипты, навыки Claude и таймер systemd:
работает только на Linux, ставится вручную (`bin/activate`, `install`, `init`), задачу ведёт агент-координатор
(LLM, который тратит токены на рутину), а увидеть очередь можно только в GitHub и в терминале.

Agent Queue — тот же кит, сделанный плагином Orca (решение владельца: «тоже что и agent-queue-kit. Мы поменяем
реализацию на плагин. Который максимально будет использовать функционалы самого orca и будет работать в Mac, Windows,
Linux»). Когда MVP заработает:

- плагин ставится из каталога Orca на macOS, Windows и Linux любым пользователем Orca;
- задачу ведёт код плагина: он берёт задачу, создаёт worktree Orca, запускает агентов через Orca, следит за их
  статусом, сам гоняет тесты, мержит; LLM нужны только исполнителю, ревьюеру, решателю автопилота и агенту старта MVP;
- очередь видна и управляется в Orca: панель, строка состояния, уведомления, ответы на блокировки;
- задачи живут в issues GitHub в своём формате плагина; проекты, которые сейчас на ките, остаются на ките.

## Пользователи и роли

| Роль | Кто это | Что делает в MVP |
|---|---|---|
| Владелец очереди | любой пользователь Orca; на его компьютере плагин работает от его входа в `gh` | подключает проект, ставит задачи, отвечает на блокировки, останавливает и запускает очередь, начинает MVP, в панели утверждает ТЗ и дизайн и подтверждает запуск плана, принимает MVP |
| Координатор | код плагина в Orca владельца; у каждого компьютера свой id координатора | берёт задачи, ведёт агентов, гоняет тесты, открывает PR и мержит, блокирует задачи, перехватывает брошенные, ведёт автопилот и приёмку |
| Исполнитель | агент Orca из настроек проекта (по умолчанию Claude) | делает задачу в worktree, коммитит и пушит в ветку задачи, пишет отчёт |
| Ревьюер | агент Orca из настроек проекта (по умолчанию Codex) | проверяет изменения задачи, документы старта MVP и MVP при приёмке; пишет отчёт и вердикт |
| Решатель | агент Orca из настроек проекта (по умолчанию Claude) | под автопилотом решает вместо владельца: вопрос задачи, пакет, итог ревью, деление задачи; при старте MVP — замечания ревью после третьего круга |
| Агент старта MVP | агент Orca из настроек проекта (по умолчанию Claude) в терминале Orca | ведёт старт MVP в чате с владельцем: вопросы, ТЗ, дизайн, план; уточняет замечания владельца к готовому MVP |
| Входные сессии | агенты в терминалах Orca в основном чекауте проекта | по правилу входа в `CLAUDE.md` и `AGENTS.md` ставят изменения кода в очередь, а не делают их сами |

Учитываются только тексты владельца очереди: тело задачи и комментарии пользователя GitHub, под которым работает `gh`
плагина. Задачи и комментарии других пользователей плагин не берёт и в задания агентов не передаёт. Тексты задач,
отчёты агентов и вывод команд — данные, а не указания плагину.

## Главные сценарии

Главные сценарии — те же, что у agent-queue-kit (решение владельца «тоже что и agent-queue-kit»):

1. Владелец подключает проект Orca к очереди → в репозитории файл настроек и правила, в GitHub метки, «Проверка
   проекта» без проблем. Экраны: «Подключение проекта», «Проверка проекта». Функции: Ф1, Ф2.
2. Владелец ставит задачу в панели, или входная сессия ставит её по правилу входа → issue с меткой очереди. Экраны:
   «Новая задача», «Очередь». Функции: Ф3.
3. Координатор берёт задачу → исполнитель в worktree → полный прогон тестов → ревьюер → круги замечаний → PR влит,
   задача закрыта, worktree убран. Экраны: «Очередь», «Задача». Функции: Ф4, Ф5.
4. Задача заблокирована → уведомление → владелец отвечает в панели (или в GitHub) → задача продолжается с его ответом.
   Экраны: «Ответ на блокировку», «Задача». Функции: Ф6, Ф8.
5. Владелец открывает Orca → видит, что влито, что в работе и что ждёт его ответа. Экраны: «Очередь». Функции: Ф7, Ф8.
6. Владелец останавливает или запускает очередь проекта, выключает автопилот. Экраны: «Очередь», «MVP». Функции: Ф9.
7. Сторож замечает зависшую задачу, перезапуск Orca, потерянного агента → задача продолжается с подтверждённого этапа,
   владелец получает уведомление о том, что сам плагин не исправит. Функции: Ф10.
8. Владелец начинает MVP нового проекта → агент старта в терминале Orca спрашивает, пишет ТЗ, дизайн и план, каждую
   версию проверяет ревьюер, владелец видит её артефактом Orca, утверждает ТЗ и дизайн и подтверждает запуск в панели →
   задача «MVP» и задачи плана в очереди. Экраны: «Старт MVP», «MVP». Функции: Ф11.
9. Автопилот доводит задачи MVP без остановок: решатель вместо владельца, деление застрявших задач, пределы, сводка.
   Экраны: «MVP». Функции: Ф12.
10. Все задачи MVP закрыты → приёмка на стенде → «MVP готов к вашей приёмке» → владелец смотрит стенд, принимает в
    панели или даёт замечания. Экраны: «MVP». Функции: Ф13.

В GitHub плагин пишет только сводки; отчёты агентов и вывод команд остаются в каталоге данных. Поля, которые
формирует сам координатор, — номера, SHA, пути файлов в репозитории, коды выхода, время, id координатора — данных
пользователя не содержат: локальные пути (с именем пользователя) и имя компьютера в GitHub не пишутся, сохранённая
работа называется так: «сохранено на компьютере <id координатора>». Строки замечаний пишет ревьюер: его задание
требует писать их без данных, которые запрещает правило данных проекта, а вывод тестов в GitHub не попадает вовсе.

## Функции и критерии приёмки

Каждая функция — с экранами раздела «Экраны» (по названию) и критериями, которые проверяет автоматический тест. Задача
«Приёмочные тесты MVP» пишет e2e-тест на каждый критерий; критерий, который тест проверить не может, переписывается.

Тесты идут только с подделками (решение владельца «Только подделки»): поддельный хост Orca (`orca/testing`:
`mockHost`, `mountWorker`, `mount`), поддельные `gh`, git, CLI Orca и агенты, без сети и без настоящего GitHub.
«Проверка очереди» в критериях — один проход координатора, который тест вызывает сам, а не ждёт по таймеру; время в
тестах — поддельное.

### Ф1. Подключение проекта

Мастер подключает проект Orca к очереди. Экраны: «Подключение проекта», «Проверка проекта».

1. Владелец выбирает проект из проектов Orca, ещё не подключённых. Подключён — в удалённой базовой ветке есть коммит
   подключения плагина (`.agent-queue.json`). Проект на agent-queue-kit (есть `.agent-queue/config.json`) в списке
   помечен «На agent-queue-kit — переход после MVP» и не выбирается: его файлы, метки и правило входа плагин не
   трогает.
2. Плагин проверяет: проект — git-репозиторий с удалённым репозиторием GitHub; `gh` установлен, вход выполнен, у
   пользователя есть доступ на запись; агенты из настроек известны Orca.
3. Форма настроек: базовая ветка (по умолчанию — ветка по умолчанию репозитория), команда полных тестов
   (обязательна), команда для Windows (по желанию), агенты — исполнитель, ревьюер, решатель, агент старта (из агентов
   Orca; по умолчанию Claude, Codex, Claude, Claude), язык текстов в GitHub, правило данных (шаблон), правила для
   заданий (шаблон), одновременно задач в работе (по умолчанию 1), зависимости worktree (по умолчанию `shared`) и
   каталоги зависимостей.
4. «Подключить» — только когда основной чекаут на базовой ветке, без изменений и его HEAD после свежего `fetch`
   совпадает с удалённой базовой веткой (ни отстаёт, ни опережает); иначе ничего не пишет и называет причину. Порядок:
   недостающие метки плагина в GitHub (повтор создаёт только недостающие); `.agent-queue.json`, `.agent-queue.md` и
   блок правила входа в `CLAUDE.md` и `AGENTS.md` (файла нет — создаёт); коммит только этих четырёх файлов, его SHA —
   в журнал операций; пуш в базовую ветку. Пуш отклонён — локальный коммит отменяется, чекаут снова на прежнем SHA.
   Потом открывается «Проверка проекта».
5. Прерванное подключение (плагин или Orca остановились после коммита, или ответ на пуш потерян): при следующем
   открытии панели плагин сверяет коммит из журнала операций с удалённой базовой веткой после `fetch`. Коммит там —
   проект подключён, операция закрыта. Коммита там нет, а основной чекаут на нём — «Подключение не завершено»:
   «Завершить» пушит его (с теми же условиями), «Отменить» возвращает чекаут на прежний SHA.

- К1.1. Тест: подключить проект при исправных `gh` и git → коммит в базовой ветке меняет только `.agent-queue.json`,
  `.agent-queue.md`, `CLAUDE.md`, `AGENTS.md`; в GitHub шесть меток плагина; коммит запушен; открыт экран «Проверка
  проекта».
- К1.2. Тест: `gh` без входа → мастер показывает «gh: нет входа — выполните gh auth login», «Подключить» недоступна,
  файлы и GitHub не меняются.
- К1.3. Тест: основной чекаут не на базовой ветке, или с изменениями, или его HEAD отстаёт от удалённой базовой ветки

### Ф3. Постановка задачи

Задача ставится из панели или входной сессией по правилу входа: issue владельца с меткой `agent-queue`. Зависимость —
строка «Зависит от #N» (или «Depends on #N»): пока #N открыта, задачу не берут. Экраны: «Новая задача», «Очередь».

Правило входа говорит только входным сессиям — агентам в основном чекауте проекта: изменение кода — в очередь,
командой `gh issue create` с меткой `agent-queue` и текстом по формату плагина (запрос пользователя, его решения и
предложения сессии раздельно; зависимости строкой «Зависит от #N»); открытые вопросы — с пользователем до постановки;
данных с прода в задаче нет; «сделай сам» и «без очереди» — сессия делает сама; файлы настроек очереди меняет только
владелец. Агент в worktree задачи (исполнитель, ревьюер) правило входа не выполняет: его задание говорит об этом прямо.

- К3.1. Тест: «Поставить» в «Новой задаче» с заголовком и текстом → issue с меткой `agent-queue`, этим заголовком и

- К3.4. Тест: issue с меткой `agent-queue` от другого пользователя GitHub → проверка очереди её не берёт, в «Очереди»

### Ф4. Координатор: захват и ведение задачи

Пока Orca открыта, координатор этого компьютера включён и очередь проекта не остановлена, плагин раз в интервал
(настройка, по умолчанию 5 минут) проверяет очередь каждого подключённого проекта и берёт самую старую задачу в
очереди: метка `agent-queue`, нет `working`, `blocked`, `split`, нет открытых зависимостей, нет отложения, задач в
работе меньше предела проекта (и для задачи MVP — в пределах `in_progress` и `per_day`, Ф12). Задачи, которые он уже
ведёт, координатор проверяет и при остановленной очереди (Ф9).

**Захват и перехват — один протокол отсчётов.** GitHub не даёт атомарного замка, поэтому право вести задачу решает
порядок комментариев. У каждой заявки — номер отсчёта: номер последнего отсчёта в задаче + 1 (у первой — 1).
Координатор пишет заявку (обычную или «перехват»), ставит `agent-queue:working`, через 60 секунд перечитывает
комментарии. Ведёт задачу автор первой по порядку GitHub заявки с наибольшим номером отсчёта; все координаторы читают
один порядок и решают одинаково. Новый отсчёт открывают: заявка после освобождения (блокировка, отложение, деление,
снятие `working` владельцем) и перехват (Ф10) — только когда ведущий последнего отсчёта молчит 3 часа. Два
одновременных перехвата пишут один и тот же номер — ведёт первый; проигравший пишет «Задачу ведёт <id>» и не
запускает агентов. Незавершённый захват (`working` стоит, а заявки нового отсчёта нет 10 минут — сбой между записями)
считается освобождением: задачу можно захватить новым отсчётом.

**Право на ветку.** Перед каждым действием по задаче — запуск или сообщение агенту, комментарий, метка, PR, мерж,
удаление worktree — координатор перечитывает заявки. Ведёт не он — останавливает своих агентов этой задачи,
сохраняет незапушенную работу её worktree (Ф6), пишет об этом один комментарий и больше по задаче ничего не делает.
Плагин не может отнять у агента прав на `git push`, поэтому пуш агента прежнего ведущего, успевший после перехвата,
ведущий обнаруживает: голова ветки не та, что он ожидал (последний SHA его исполнителя или ветки при перехвате). Такой
SHA не допускается к ревью и мержу; исполнитель ведущего получает чужие коммиты как черновик — принять (с проверкой)
или отбросить, и отчитаться, что сделал.

**Worktree.** Ветка задачи — ровно `agent-queue/issue-<N>`. Есть на `origin` — worktree открывается на ней, на её
голове; нет — создаётся от `origin/<базовая ветка>`. Orca готовит worktree своей подготовкой проекта (`orca.yaml`).
Перед запуском агента плагин сверяет фактические ветку и HEAD worktree с ожидаемыми; не совпадают (например, Orca дала
ветке другое имя) — worktree убирается, задача блокируется со сбоем инфраструктуры.

**Ведение.** Исполнитель в worktree с заданием: текст задачи и комментарии владельца; правила для заданий; правило
данных; что правило входа к нему не относится; ограничения — тесты только полной командой проекта; коммит и пуш
только в ветку задачи; не мержить и ничего не писать в GitHub, кроме пуша в ветку; не трогать `.env*`,
`.agent-queue.json`, `.agent-queue.md`; зависимости не менять, кроме пакетов, которые задание разрешает (Ф6, Ф12);
вопрос — в отчёт, не догадкой; выбор технологии, который задача и документы не фиксируют, — вопрос, не решение
исполнителя. Путь файла отчёта — в каталоге данных. Отчёт готов, когда агент в Orca закончил («done») и файл отчёта
есть. После первого пуша — черновой PR в базовую ветку с `Closes #N`. После каждого этапа — комментарий хода на языке
проекта со служебной меткой этапа: захват, исполнитель запущен, сделано и PR, прогон тестов, круг ревью k — m
замечаний, исправлено, влита; последний комментарий живой задачи не старше 2 часов.

**Тесты.** После отчёта исполнителя плагин сам запускает полную команду тестов в worktree на закоммиченном дереве без
незакоммиченных и неотслеживаемых файлов и записывает прогон: SHA, код выхода, время начала, длительность, чистое ли
дерево до и после, полный вывод — в каталог данных. Засчитывается только прогон с кодом 0 на чистом дереве, у которого
HEAD в конце тот же. Красный прогон — вывод уходит тому же исполнителю; три красных прогона подряд — блокировка (Ф6)
или деление (Ф12).

- К4.1. Тест: задача в «Ждут» → после проверки очереди у неё заявка отсчёта 1 с id координатора, метка
  `agent-queue:working`, worktree на ветке `agent-queue/issue-<N>`, исполнитель запущен с заданием, где есть текст
  задачи, правила для заданий и правило данных.
- К4.2. Тест: предел «одновременно в работе» 1 и одна задача в работе → вторая не берётся, пока первая не закрыта
  или не заблокирована.
- К4.3. Тест: координаторы A и B читают задачу свободной, затем A пишет заявку, затем B; оба перечитывают → агентов
  запускает только A; B пишет «Задачу ведёт A» и больше ничего не делает. Тот же результат при порядке чтений «A, B,
  запись B, запись A» для того, чья заявка в GitHub первая.
- К4.4. Тест: исполнитель отчитался, тесты красные → исполнитель получает вывод теста; после третьего красного прогона
  подряд задача заблокирована.
- К4.5. Тест: исполнитель запушил первый коммит → черновой PR из `agent-queue/issue-<N>` в базовую ветку с
  `Closes #<N>` в теле.
- К4.6. Тест: в worktree есть неотслеживаемый файл → прогон записан как «дерево не чистое» и для мержа не
  засчитывается.
- К4.7. Тест: в задаче есть комментарий другого пользователя GitHub → его текста нет в задании исполнителя.
- К4.8. Тест: ведёт A (отсчёт 1), B и C одновременно пишут перехват отсчёта 2 → ведёт тот из B и C, чья заявка в
  GitHub первая; второй пишет «Задачу ведёт <id>»; A перед следующим действием останавливает агентов и пишет только
  комментарий о сохранённой работе.
- К4.9. Тест: после перехвата агент прежнего ведущего запушил коммит → ведущий видит неожиданную голову ветки; этот
  SHA не идёт на ревью; исполнитель ведущего получает чужой коммит как черновик и отчитывается о нём.
- К4.10. Тест: `working` стоит, заявки нового отсчёта нет 10 минут → проверка очереди захватывает задачу новым

- К4.11. Тест: worktree задачи удалён, ветка `agent-queue/issue-<N>` и PR есть → новый worktree на этой ветке на её

### Ф5. Ревью, круги замечаний и мерж

**Ревью.** Ревьюер запускается в worktree задачи с ожидаемым SHA и заданием: только чтение, ничего не писать в git и
GitHub; проверить изменения против задачи, правил и правила данных; запустить полные тесты; записать отчёт и файл
вердикта — `issue`, `round`, `reviewed_sha`, `verdict` (`approve`, `changes`, `head-mismatch`), замечания с важностью
(`critical`, `major`, `minor`, `nit`), путём файла, строкой и одной строкой сути без данных, которые запрещает правило
данных. Отнять у агента права записи плагин не может, он обнаруживает их нарушение: после ревью HEAD и состояние
worktree те же, голова ветки на `origin` — та же; иначе ревью отбрасывается, worktree возвращается к запушенной
ветке, а изменённая голова ветки — чужой коммит, как в Ф4. Неверный файл вердикта не засчитывается: ревьюер получает
причину, круг не считается.

**Круги.** `changes` — замечания тому же исполнителю (его терминал не принимает — новый исполнитель в том же worktree
с отчётами), потом новый круг. Замечание о выборе технологии, который задача и документы не фиксируют, исполнителю не
идёт: сначала владелец (блокировка, Ф6) или решатель (Ф12), потом решение — исполнителю вместе с остальными
замечаниями круга. Не больше трёх кругов; после третьего только minor/nit — ещё один круг по изменениям после
последнего ревью; иначе блокировка (под автопилотом — Ф12).

**Допуск к мержу.** Мерж только когда все условия выполнены на свежем `fetch`:

1. ревьюер одобрил SHA X (`approve`, файл вердикта верный);
2. есть засчитанный прогон тестов SHA Y, где Y = X, или Y — rebase X на новую базу без конфликтов, и изменения Y
   относительно базы совпадают с изменениями X (отличаются только строки контекста); rebase с разрешением конфликтов
   — ещё круг ревью разрешения, который одобряет сам Y;
3. база B (её SHA запоминается) — предок Y, голова PR — Y, ветка задачи не меняет `.agent-queue.json` и
   `.agent-queue.md`.

База ушла вперёд — исполнитель делает rebase, полный прогон на новом SHA. Перед мержем тело PR переписано по итогам
(Зачем, Что сделано, Проверка, Ревью) и PR переведён из черновика в готовые. Мерж — merge-коммит GitHub с условием,
что голова PR — Y; отказ GitHub — снова допуск с шага 2.

**После мержа.** Плагин читает PR из GitHub: состояние `MERGED`, база — базовая ветка; merge-коммит M: второй родитель
— Y, первый — B. Первый родитель не B (база сдвинулась между проверкой и мержем, а GitHub всё равно влил) — плагин
гоняет полные тесты на M в своём worktree: зелёные — продолжает, в итоговом комментарии «база сдвинулась при мерже,
тесты M зелёные»; красные — уведомление «Базовая ветка после мержа #<N> не проходит тесты», задача остаётся с этим
комментарием, новые задачи проекта не берутся, пока владелец не разберётся (снимет остановку в панели). PR влит не в
базовую ветку или не с головой Y — блокировка. Дальше: ветка удалена, задача закрыта (если `Closes #N` её ещё не
закрыл), итоговый комментарий, основной чекаут обновлён (когда он на базовой ветке и чистый), шаги после мержа из
настроек, worktree убран, `working` снята. Уборка, которую прервал перезапуск, доводится сторожем (Ф10), в том числе
у задачи, которую GitHub уже закрыл по `Closes #N`. Мержи проекта на одном компьютере идут по одному.

- К5.1. Тест: ревьюер вернул `changes` с двумя замечаниями → исполнитель получает оба, идёт круг 2; в задаче
  комментарий «круг 1: 2 замечания» со строками замечаний (важность, путь, строка, суть).
- К5.2. Тест: `approve` и засчитанный прогон того же SHA → PR переведён в готовые, влит merge-коммитом с родителями
  B и Y; ветка удалена, задача закрыта, итоговый комментарий со ссылкой на PR, worktree убран, метки `working` нет.
- К5.3. Тест: `approve`, а засчитанного прогона этого SHA нет → мержа нет, плагин запускает полные тесты на этом SHA.
- К5.4. Тест: файл вердикта с чужим SHA или без `verdict` → не засчитан, ревьюеру отправлена причина, номер круга не
  вырос.
- К5.5. Тест: после третьего круга осталось замечание `major` (вне автопилота) → задача заблокирована, в комментарии

- К5.6. Тест: база ушла вперёд после `approve`, rebase без конфликтов, изменения совпадают → полный прогон нового SHA,

- К5.7. Тест: rebase с разрешением конфликта → круг ревью разрешения; мерж только после `approve` нового SHA.
- К5.8. Тест: GitHub влил PR, но первый родитель merge-коммита — не запомненная база B → плагин гоняет тесты на
  merge-коммите; зелёные — задача закрыта с пометкой «база сдвинулась при мерже»; красные — уведомление и
  остановка взятия новых задач проекта.
- К5.9. Тест: плагин перезапущен после мержа, GitHub уже закрыл задачу по `Closes #N` → сторож доводит уборку: ветка
  удалена, итоговый комментарий, worktree убран, `working` снята; второго мержа нет.
- К5.10. Тест: ветка задачи меняет `.agent-queue.json` → мерж отказан, задача заблокирована с этой причиной.
- К5.11. Тест: ревьюер изменил файл в worktree или запушил в ветку → ревью отброшено, worktree на запушенной ветке;
  запушенный ревьюером коммит не идёт на мерж; ревью запущено снова, номер круга не вырос.
- К5.12. Тест: ревьюер нашёл выбор технологии, которого задача не фиксирует (вне автопилота) → задача заблокирована с
  вопросом и остальными замечаниями круга; исполнитель этого замечания не получал.
- К5.13. Тест: шаг после мержа из настроек вышел с кодом 1 → мерж остаётся, итоговый комментарий называет команду и
  код выхода.

### Ф6. Блокировка, сохранение работы и ответ владельца

**Когда.** Нужен человек: вопрос, на который задача и документы не отвечают (выбор технологии тоже); нужен новый пакет
или зависимость (под автопилотом — Ф12); задача требует изменить настройки очереди; три неудачи одного шага; ревью не
одобрено за разрешённые круги; конфликт rebase, который исполнитель не разрешил; сбой Orca, GitHub или агента,
который не запускается.

**Порядок.** Остановить агентов задачи → сохранить работу → записать блокировку в GitHub (комментарий, затем метка
`agent-queue:blocked` вместо `working` — последней записью) → только после подтверждения записи убрать worktree.
Сохранение: незапушенные коммиты пушатся в ветку задачи; пуш не прошёл или остались изменённые и неотслеживаемые
файлы — плагин сохраняет их в каталог данных (коммиты пачкой git, изменения патчем, неотслеживаемые файлы архивом;
`.env*` — никогда), и worktree остаётся. Комментарий блокировки: что сделано, что мешает, точный вопрос; сохранённое —
именами файлов и «сохранено на компьютере <id>», без содержимого и локальных путей; уведомление Orca. GitHub не
принимает записи — блокировка не записана: агенты остановлены, worktree не трогается, задача остаётся у
координатора, уведомление «Не удалось заблокировать #<N>: <ошибка>», повтор на следующей проверке.

**Ответ.** Владелец отвечает в панели («Ответ на блокировку») или в GitHub (комментарий и снятие метки). Панель пишет
комментарий со служебной меткой операции, затем снимает метку. Ответ GitHub потерян — повтор ищет комментарий с этой
меткой и пишет его, только если не нашёл; снятие метки повторяется отдельно. Задача снова в очереди, следующий захват
продолжает её с ветки, задание содержит ответ владельца, круги ревью считаются заново.

**Сохранённая работа при возобновлении.** Координатор, у которого есть сохранённая работа задачи, при захвате
отдаёт её новому исполнителю как черновик: применить пачку коммитов, патч и архив, проверить, закоммитить нужное,
отбросить остальное; отчёт называет каждый сохранённый коммит и файл — взят или отброшен и почему. Пока отчёт не
принят, сохранённое не удаляется. Другой компьютер сохранённой работы не видит: его задание исполнителя говорит, что
часть работы осталась на компьютере <id>.

**Зависимости вне автопилота.** Задача, которой нужен пакет, блокируется с вопросом. Владелец добавляет пакет в
базовую ветку сам, или отвечает в блокировке строкой «Пакеты: <имена>»: при зависимостях `own` задание следующего
исполнителя разрешает ставить именно эти пакеты — после того как плагин проверил, что каталоги зависимостей worktree
— его собственные (не симлинки и не общие с основным чекаутом); при `shared` такой ответ не принимается — задача
снова блокируется с объяснением. Экраны: «Ответ на блокировку», «Задача», «Очередь».

- К6.1. Тест: исполнитель написал в отчёте вопрос → метка `agent-queue:blocked`, комментарий с вопросом, уведомление
  Orca «#<N> ждёт ответа: <заголовок>», агенты остановлены, worktree убран после записи метки, последний коммит
  исполнителя в ветке задачи.
- К6.2. Тест: ответ в «Ответе на блокировку» → в задаче комментарий с этим текстом, метка `agent-queue:blocked`
  снята; следующая проверка очереди берёт задачу, и задание исполнителя содержит ответ.
- К6.3. Тест: метку сняли в GitHub после комментария владельца → задача берётся, задание содержит этот комментарий.
- К6.4. Тест: поле ответа пустое → кнопка «Ответить и вернуть в очередь» недоступна.
- К6.5. Тест: при блокировке пуш отклонён → коммит сохранён пачкой в каталоге данных, worktree не убран, комментарий
  блокировки называет «сохранено на компьютере <id>» без локального пути; после ответа владельца тот же компьютер
  захватывает задачу, задание исполнителя содержит сохранённую работу, отчёт называет её коммит взятым или
  отброшенным.
- К6.6. Тест: GitHub отказал в записи блокировки → метки не изменились, worktree на месте, уведомление «Не удалось
  заблокировать #<N>»; следующая проверка при рабочем GitHub записывает блокировку и только потом убирает worktree.
- К6.7. Тест: комментарий ответа записан, а ответ GitHub потерян → повтор находит комментарий по метке операции и
  второго не пишет; снимает метку.
- К6.8. Тест: ответ «Пакеты: left-pad» при зависимостях `own` и собственных каталогах зависимостей → задание
  исполнителя разрешает ставить `left-pad`; при `shared` → задача снова заблокирована с объяснением.

### Ф7. Панель очереди

Панель плагина в Orca: проекты и их задачи по разделам — «Ждут ответа» (заблокированы), «В работе» (этап: исполнитель,
тесты, ревью круг k, мерж; состояние агента из Orca), «Ждут» (с зависимостями и отложенные), «Влиты» (за 7 дней);
блок открытой задачи «MVP». Обновляется после каждого шага координатора и при открытии; данные из GitHub не старше
интервала проверки. Экран «Задача» берёт ход, круги ревью (вердикт; замечания — важность, путь, строка, суть) и
прогоны (SHA, код выхода, время начала, длительность, чистое ли дерево) из комментариев хода в GitHub — их видно с
любого компьютера и после очистки каталога данных; полные отчёты и вывод тестов — только на компьютере, который вёл
задачу, 30 дней. Экраны: «Очередь», «Задача».

- К7.1. Тест: две задачи ждут, одна в работе, одна заблокирована, одна влита вчера → каждая в своём разделе, у
  разделов счётчики 1, 1, 2, 1.
- К7.2. Тест: подключённых проектов нет → «Очередь» в состоянии «Нет подключённых проектов» с кнопкой «Подключить
  проект».
- К7.3. Тест: чтение GitHub упало → «Очередь» в состоянии ошибки «Не удалось прочитать GitHub: <ошибка>» с кнопкой
  «Повторить»; задачи прежнего чтения не показаны как текущие.
- К7.4. Тест: задача на втором круге ревью → в «В работе» у неё этап «Ревью, круг 2».
- К7.5. Тест: нажать на задачу → экран «Задача» с её текстом, кругами ревью (с путём и строкой замечаний) и
  прогонами тестов (SHA, код выхода, время, длительность) из комментариев хода.
- К7.6. Тест: язык интерфейса «English» → заголовки и кнопки панели на английском; «Русский» — на русском.
- К7.7. Тест: задачу вёл другой компьютер (или каталог данных очищен) → вкладки «Ревью» и «Тесты» заполнены из
  комментариев хода, пометка «Полный вывод — на компьютере <id>» (или «Подробные отчёты удалены через 30 дней»);
  кнопок терминалов агентов нет.

### Ф9. Стоп и пуск

**«Остановить» очередь проекта** (на этом компьютере; так же плагин останавливает её сам, когда базовая ветка после
мержа не проходит тесты — Ф5, с этой причиной). Не делается: захват новых задач проекта, перехват чужих, новые шаги
автопилота по задаче «MVP» проекта (новое деление, сводка, приёмка). Продолжается для задач, которые координатор уже
ведёт: проверка их этапов, ревью, тесты, мерж, блокировка, сторож (восстановление после потери агента,
уведомления); начатое деление доводится до конца (части, перенос зависимостей, закрытие исходной), чтобы не оставить
его наполовину. «Запустить» — снова всё; причина остановки снимается.

**«Выключить автопилот»** на экране «MVP» снимает `agent-queue:autopilot` с задачи «MVP» — для всех компьютеров;
«Включить автопилот» — ставит. Без автопилота вопросы задач MVP идут владельцу (Ф6), новое деление и приёмка не
начинаются. Деление, у которого уже создана хоть одна часть, доводится до конца (как при остановке); задача с
`agent-queue:split`, деление которой не начато, получает `agent-queue:blocked` вместо `split` и комментарий
«Автопилот выключен: задача ждала деления — решите сами». Идущая приёмка останавливается: `down` стенда, worktree
приёмки убран, итога нет; после включения автопилота приёмка начинается заново. Экраны: «Очередь», «MVP».

- К9.1. Тест: очередь проекта остановлена, одна задача в работе, одна ждёт → проверка очереди новую не берёт, задача в
  работе доходит до мержа.
- К9.2. Тест: «Запустить» → следующая проверка очереди берёт ждущую задачу.
- К9.3. Тест: «Выключить автопилот» → метка `agent-queue:autopilot` снята; следующий вопрос задачи MVP блокирует её
  (Ф6), решатель не спрашивается.
- К9.4. Тест: остановка очереди после создания первой части деления → деление доведено: все части созданы, зависимые
  ждут части, исходная закрыта; новых задач координатор не берёт.
- К9.5. Тест: автопилот выключен, у задачи `agent-queue:split`, деление не начато → метка `split` заменена на
  `blocked`, комментарий «Автопилот выключен: задача ждала деления — решите сами».
- К9.6. Тест: автопилот выключен после создания первой части деления → деление доведено до конца.
- К9.7. Тест: автопилот выключен, когда стенд приёмки поднят → выполнен `down`, worktree приёмки убран, комментария с
  итогом приёмки нет.
- К9.8. Тест: очередь остановлена, агент задачи в работе пропал → сторож запускает нового агента по этапу задачи.

### Ф10. Сторож

Внутри плагина, раз в 5 минут, пока Orca открыта. Сбой чтения GitHub никогда не считается пустой очередью или брошенной
задачей. Одно уведомление на условие, пока оно держится.

**Восстановление с подтверждённого этапа.** Этап задачи — служебная метка последнего комментария хода. Задача, которую
ведёт этот координатор, а её агента в Orca нет (перезапуск Orca, закрытый терминал): живые агенты задачи (их видно в
Orca) не дублируются; продолжение по этапу — исполнитель: новый исполнитель в worktree задачи (worktree нет — по Ф4)
с последним отчётом и сохранённой работой (Ф6); тесты: прогон заново; ревью: новый ревьюер того же SHA; мерж:
проверка PR в GitHub — `MERGED` доводится по Ф5. Комментарий «Продолжено после потери агента: <этап>». Сюда же —
задачи, закрытые (по `Closes #N` или плагином) с незавершённой уборкой: у них ещё стоит `working`, есть ветка или
worktree, или нет итогового комментария — уборка доводится, агенты не запускаются.

**Перехват.** Задача в работе у другого координатора, комментариев хода 3 часа → заявка «Перехват: предыдущий
координатор молчал 3 часа» нового отсчёта (Ф4); продолжение с ветки по этапу. Незапушенная работа прежнего
координатора остаётся на его компьютере: он сохранит её, когда увидит перехват (Ф4).

**Уведомления.** Агент задачи ждёт ввода человека 30 минут — «#<N>: агент ждёт ввода» (в панели у задачи — переход к
его терминалу). Агент упёрся в лимит использования — задача отложена на час: комментарий «Отложено до <время>», метка
`working` снята, до этого времени задачу не берут. GitHub не прочитан три проверки подряд. Задача «MVP» под
автопилотом: 6 часов ни одного мержа и ничего в работе; достигнут предел; готова к приёмке или заблокирована.

- К10.1. Тест: задача на этапе «исполнитель», агента в Orca нет → запущен новый исполнитель в worktree задачи,
  комментарий «Продолжено после потери агента: исполнитель».
- К10.2. Тест: задача на этапе «ревью» SHA X, ревьюера в Orca нет, исполнитель жив → запущен новый ревьюер с SHA X,
  нового исполнителя нет.
- К10.3. Тест: задача на этапе «мерж», PR в GitHub уже `MERGED`, задача закрыта GitHub → ветка удалена, итоговый
  комментарий, `working` снята, ни одного агента не запущено.
- К10.4. Тест: задача в работе у другого id, последний комментарий хода 3 часа назад → заявка «Перехват…» нового
  отсчёта, агенты этого координатора продолжают с ветки.
- К10.5. Тест: агент в состоянии «waiting» 30 минут → одно уведомление «#<N>: агент ждёт ввода»; вторая проверка
  нового не показывает; после выхода из ожидания условие снято.
- К10.6. Тест: GitHub не прочитан три проверки подряд → уведомление; ни одна задача не перехвачена и не взята.
- К10.7. Тест: отчёт агента о лимите использования → комментарий «Отложено до <время + 1 ч>», метки `working` нет;
  проверка до этого времени задачу не берёт, после — берёт.

### Ф11. Старт MVP

**Запуск агента.** «Начать MVP» в панели (подключённый проект без открытой задачи «MVP») запускает агента старта в
терминале Orca основного чекаута проекта с инструкцией плагина. Агент делает то, что сейчас навык
`/agent-queue-start`: спрашивает владельца в чате по блокам (цель, данные и интеграции, состав MVP, «только
владелец»), записывает ответы дословно в `decisions.md`, пишет ТЗ (экраны словами), после утверждения ТЗ — доску
дизайна `maket/index.html`, после утверждения дизайна — план `plan.json`; всё в `docs/mvp/` в своём worktree на ветке
`agent-queue/mvp-spec`, каждая версия — коммит. Вопросы и замечания владельца — в чате; решения, от которых зависит,
что будет построено, — в панели (ниже).

**Ревью и показ — через плагин.** Агент старта не публикует и не ревьюит сам: он кладёт в каталог старта запрос с
коммитом и файлами. Ревью: плагин запускает ревьюера из настроек в новом терминале с файлами этого коммита и
решениями владельца из `decisions.md`, записывает отчёт с вердиктом, кругом, коммитом и хэшами файлов; до трёх кругов
на показ, потом решатель отвечает по оставшимся замечаниям, потом ещё до трёх. `plan.md` агент не пишет: плагин строит
его из `plan.json` того же коммита (те же задачи со всеми полями), и ревью и показ плана — это `plan.md`, построенный
из этого `plan.json`, вместе с ним. Показ: плагин публикует файл артефактом Orca (решение владельца «Артефакты Orca,
как сейчас») только когда файл на диске совпадает с версией, которую видело последнее ревью этого показа (или ревью
не смогло пройти — тогда с пометкой «ревьюер не проверял: <причина>»); следующий показ того же файла обновляет тот
же артефакт, ссылка не меняется. Ссылку и итог ревью агент передаёт владельцу в чате, плагин — на экран «Старт MVP».

**Решения владельца — в панели, по версиям.** На экране «Старт MVP» у последнего показа ТЗ — «ТЗ: утверждаю» и «Есть
правки», у показа доски — «Дизайн: утверждаю» и «Есть правки». Плагин записывает решение вместе с версией (коммит и
хэш файла), которую показывал. Агент переходит к дизайну только с записанным «ТЗ: утверждаю» той версии ТЗ, что
лежит в его коммите, и к плану — только с «Дизайн: утверждаю» той версии доски; изменённое после утверждения ТЗ или
доска снова требуют показа и утверждения. «Есть правки» — агент спрашивает о них в чате, новые версии, ревью и показы
по той же ссылке.

**Подтверждение запуска.** Когда план показан, агент кладёт запрос запуска с коммитом. Плагин принимает его, только
если в этом коммите: `tz.md` и `maket/index.html` — те версии, что владелец утвердил; `plan.json` — тот, из которого
построен показанный и одобренный последним ревью `plan.md`. Экран «Старт MVP» показывает сводку (задач, этапов,
пределы, «Только владелец», коммит, итоги ревью ТЗ, дизайна и плана) и вопрос «Запустить MVP?»: «Да» (с
автопилотом), «В обычную очередь», «Правки» (агент правит план, новое ревью и показ), «Нет». В момент нажатия
плагин сохраняет снимок `plan.json` этого коммита; задачи создаются только из снимка и только после нажатия — файл
плана сам по себе ничего не создаёт. После «Да», «В обычную очередь» или «Нет» плагин снимает ссылки всех показов
старта, потом пушит ветку `agent-queue/mvp-spec` (для «Да» и «В обычную очередь») и убирает worktree старта; ссылка,
которую снять не удалось, названа на экране — владелец удалит её в панели артефактов Orca.

**План в очередь.** Плагин проверяет снимок (известные поля, уникальные ключи, зависимости только на ключи плана, без
циклов) и пишет одной операцией с id: задача «MVP» со служебной меткой плана (id плана, коммит документов), затем
задачи плана по одной, каждая со служебной меткой своего ключа, затем чек-лист задачи «MVP», последней записью —
отметка «план записан» в служебной метке задачи «MVP». Повтор после сбоя или потерянного ответа GitHub находит уже
созданное по меткам и создаёт только недостающее. Пока отметки «план записан» нет, координаторы задачи этого плана не
берут. Первая задача плана — «Утверждённые документы MVP»: перенести `docs/mvp/` из запушенного коммита ветки
`agent-queue/mvp-spec` в базовую ветку как есть; все остальные задачи зависят от неё; последняя — «Приёмочные тесты
MVP», зависит от всех остальных. Экраны: «Старт MVP», «MVP».

- К11.1. Тест: «Начать MVP» в подключённом проекте без задачи «MVP» → в Orca запущен агент старта из настроек с
  инструкцией плагина в основном чекауте проекта; экран «Старт MVP» в состоянии «идёт», кнопка недоступна.
- К11.2. Тест: у проекта открыта задача «MVP» → «Начать MVP» недоступна, экран «Старт MVP» ведёт на экран «MVP».

- К11.4. Тест: запрос показа файла, изменённого после последнего ревью → отказ «не проверенная версия», ничего не

- К11.5. Тест: «ТЗ: утверждаю» в панели для показанной версии V, затем в коммите запроса запуска `tz.md` другой версии

- К11.7. Тест: запрос запуска верный, владелец не нажимал → ни одной задачи не создано; «Да» → issue «MVP: <название>»

- К11.9. Тест: снимок с неизвестным полем, зависимостью от ключа, которого нет в плане, или циклом зависимостей →

### Ф12. Автопилот MVP

Пока задача «MVP» открыта и у неё `agent-queue:autopilot`, там, где задача MVP была бы заблокирована, решает плагин:

| Вне автопилота | Под автопилотом |
|---|---|
| вопрос, на который задача и документы не отвечают (выбор технологии тоже, найденный исполнителем или ревьюером) | решатель решает; вопрос о ключах, оплате, аккаунтах, доступах, деплое или пункте «Только владелец» — блокировка |
| нужен пакет | зависимости worktree `own`, каталоги зависимостей worktree собственные (Ф6) и пакет в разделе «Пакеты» задачи — исполнитель ставит его в задаче (задание разрешает именно эти пакеты); другой пакет — решатель, разрешение приходит исполнителю после решения; зависимости `shared` — блокировка |
| ревью не одобрено после круга 3 | решатель один раз по оставшимся замечаниям, потом круги 4–6; не одобрено — деление |
| три неудачи одного шага | деление |
| конфликт rebase | одна новая попытка от свежей базовой ветки (прежняя ветка сохранена пачкой), потом деление |
| лимит агента | задача отложена (Ф10) |

Решение — комментарий «Решение по #<N>» (вопрос, решение, обоснование) в задаче и в задаче «MVP»; он же — запись,
по которой повтор после сбоя действует, не спрашивая решателя снова.

**Деление** — операция с id. Сначала решение решателя о частях (их число, заголовки и тексты) записывается
комментарием «Решение по #<N>: деление» — повтор берёт части из него. Затем: части — новые задачи с «Часть #<N>»,
`MVP: #E`, материалом исходной (ветка, причина, сохранённая работа) и служебной меткой «часть k операции <id>»;
затем задачи, ждавшие #N, ждут части; затем чек-лист «MVP»; черновой PR закрыт без мержа; исходная задача закрыта
последней — пока у неё остаются зависимые, она открыта. Повтор после сбоя или потерянного ответа находит созданные
части по меткам и делает только оставшиеся записи. Часть или задача, начатая заново дважды, не делится —
блокируется с историей попыток.

**Пределы.** Из текста задачи «MVP» (владелец может менять числа): `in_progress` — задач MVP в работе одновременно,
держит захват; `per_day` — задач MVP, взятых за последние 24 часа (скользящее окно), держит захват; `total` — всего
задач MVP с частями и задачами приёмки, держит только добавление задач (части, задачи приёмки), не захват. По
умолчанию 3, 20 и число задач плана × 1,5 с округлением вверх. Деление или задачи приёмки, которые превысили бы
`total`, не создаются: задача (или задача «MVP») блокируется с просьбой поднять `total`.

**Сводка.** Раз в сутки — комментарий в задаче «MVP»: влито, в работе, заблокировано, осталось. Экраны: «MVP».

- К12.1. Тест: задача MVP под автопилотом, исполнитель задал вопрос → решатель запущен, комментарий «Решение по #<N>»
  в задаче и в задаче «MVP», исполнитель получает решение, метки `agent-queue:blocked` нет.
- К12.2. Тест: вопрос о ключах оплаты из списка «Только владелец» → задача заблокирована с «Автопилот: только
  владелец», решатель не запускался.
- К12.3. Тест: ревью не одобрено после круга 6 → решатель делит задачу; созданы 2–3 задачи с «Часть #<N>»; задача,
  ждавшая #N, теперь ждёт части; исходная задача закрыта последней, её PR закрыт без мержа.
- К12.4. Тест: часть разделённой задачи не одобрена после круга 6 → блокировка с историей попыток, деления нет.
- К12.5. Тест: `in_progress` 3 и три задачи MVP в работе → четвёртая не берётся.
- К12.6. Тест: `total` равен числу задач MVP → захват следующей задачи плана идёт; деление, которое добавило бы
  задачи, не делается — задача заблокирована с просьбой поднять `total`.
- К12.7. Тест: за последние 24 часа взято 20 задач MVP при `per_day` 20 → новая не берётся; когда самый ранний захват
  выходит из окна — берётся.
- К12.8. Тест: зависимости `own`, пакет в разделе «Пакеты» задачи → задание исполнителя разрешает ставить именно его;
  зависимости `shared` → задача заблокирована с вопросом о пакете.
- К12.9. Тест: сбой деления после создания первой части (или потерянный ответ GitHub на её создание), повтор →
  решатель второй раз не запускается, части — по записанному решению, каждая одна; зависимые ждут части; исходная
  закрыта.
- К12.10. Тест: с последней сводки прошли сутки → в задаче «MVP» комментарий-сводка с числами «влито», «в работе»,
  «заблокировано», «осталось».

### Ф13. Приёмка MVP

**Когда.** Только под автопилотом: все задачи MVP закрыты, задача «MVP» открыта и не заблокирована, очередь проекта
на этом компьютере не остановлена. В обычной очереди («В обычную очередь» или автопилот выключен) приёмки нет:
экран «MVP» показывает «Все задачи закрыты» и кнопку «Принимаю».

**Проверка.** Новый worktree на свежей базовой ветке → `setup` стенда → полная команда тестов → `up` → ожидание ответа
`url` → ревьюер проверяет MVP по критериям задачи «MVP», ТЗ и доске дизайна во встроенном браузере Orca → `down` →
worktree убран. `down` и уборка выполняются при любом исходе, ошибке тоже. Стенда в настройках нет — задача «MVP»
заблокирована с просьбой добавить стенд.

**Раунды** — как в ките. Раунд — проверка, после которой то, что не прошло, стало задачами того же MVP (в пределах
`total`, операцией с id, как деление) с комментарием «Приёмка не прошла: раунд <r> из 2». В одном цикле не больше
двух раундов: третья не прошедшая проверка — комментарий «Приёмка MVP не прошла за 2 раунда» с итогом, метка
`agent-queue:blocked` на задаче «MVP», уведомление. Проверка прошла — комментарий «MVP готов к вашей приёмке» с
числом задач MVP, метка `agent-queue:blocked`, уведомление. Цикл начинается заново после каждого итога для владельца
(«готов» или «не прошла за 2 раунда»): исправления после него снова получают два раунда. Раунды считаются по этим
комментариям задачи «MVP», а не по памяти плагина.

**Владелец.** «Открыть стенд» (когда итог — «готов» или «не прошла за 2 раунда») — плагин поднимает стенд базовой
ветки (`setup`, `up`) и открывает `url` во встроенном браузере Orca; «Закрыть стенд» — `down` и уборка. «Принимаю»
показан, только когда последний итог — «готов» и с него не добавлено задач MVP; при нажатии плагин перечитывает
задачу «MVP»: все её задачи закрыты, и их число то же, что в комментарии «готов»; тогда метка `agent-queue:autopilot`
снята, задача «MVP» закрыта, проект дальше живёт обычной очередью; иначе отказ с причиной. «Есть замечания» (при
любом итоге) — агент старта в терминале Orca уточняет их с владельцем и кладёт файл задач того же MVP; плагин ставит
их операцией с id (как план, Ф11, в пределах `total`) и снимает блокировку — автопилот продолжает, потом снова
приёмка. Экраны: «MVP».

- К13.1. Тест: закрыта последняя задача MVP под автопилотом → в порядке: worktree базовой ветки, `setup`, полные
  тесты, `up`, ответ `url`, ревьюер с критериями MVP и адресом стенда, `down`, worktree убран.
- К13.2. Тест: `up` упал → `down` выполнен, worktree убран, задача «MVP» заблокирована с ошибкой стенда.
- К13.3. Тест: первая проверка нашла две проблемы → две новые задачи того же MVP с «MVP: #E»; в задаче «MVP»
  «Приёмка не прошла: раунд 1 из 2».
- К13.4. Тест: проверка прошла → комментарий «MVP готов к вашей приёмке» с числом задач, метка
  `agent-queue:blocked` на «MVP», уведомление; на экране «MVP» кнопки «Открыть стенд», «Принимаю» и «Есть
  замечания».
- К13.5. Тест: «Принимаю», все задачи закрыты и их число то же → метка `agent-queue:autopilot` снята, задача «MVP»
  закрыта; после «готов» добавилась задача MVP → «Принимаю» не показан, а нажатие по старому экрану — отказ «Есть
  задачи MVP после итога».
- К13.6. Тест: в настройках нет стенда → задача «MVP» заблокирована с текстом «Добавьте стенд приёмки в настройки
  проекта».
- К13.7. Тест: третья проверка цикла не прошла → комментарий «Приёмка MVP не прошла за 2 раунда», блокировка «MVP»;
  на экране «MVP» есть «Есть замечания» и «Открыть стенд», нет «Принимаю».
- К13.8. Тест: все задачи MVP закрыты, автопилота нет → приёмка не запускается, экран «MVP» показывает «Все задачи
  закрыты».
- К13.9. Тест: после «не прошла за 2 раунда» владелец дал замечания, их задачи закрыты → новая проверка — раунд 1
  нового цикла.
- К13.10. Тест: сбой после создания первой задачи раунда, повтор → задачи раунда не дублируются.

### Ф14. Три системы, поставка и релиз

Плагин работает на macOS, Windows и Linux: пути, каталог данных, запуск команд проекта, git, `gh`, CLI Orca и агентов
— по правилам системы; команда тестов идёт оболочкой системы, на Windows — команда для Windows из настроек, если
задана. Манифест: id `agent-queue`, имя «Agent Queue» (решение владельца). Везде CLI Orca — `ORCA_CLI_COMMAND`,
иначе `orca-ide`; голый `orca` — никогда (на Linux вне терминала Orca это экранный диктор GNOME).

Папка плагина проходит `plugin inspect` CLI Orca: инструменты разработки не кладут в неё симлинков (сейчас
`node_modules/.bin/tsc` заготовки ломает `inspect`). GitHub Actions на `ubuntu-latest`, `macos-latest`,
`windows-latest`: CLI Orca из релиза Orca (как в пробном плагине: пакет Orca, CLI под Electron в режиме Node),
`plugin validate`, проверка типов и тестов плагина (`plugin test`); проверка поставки — на чистой выгрузке коммита
(`git archive`, без `node_modules` и `.orca`): `plugin inspect` проходит. Релиз: версия в манифесте, запись для
каталога Orca из `plugin release-entry` релизного коммита (запускается во временном клоне), README с установкой и
требованиями.

- К14.1. Тест: путь worktree и каталога данных на подделке Windows (`win32`) и macOS (`darwin`) → путь по правилам
  этой системы, без смешения разделителей.
- К14.2. Тест: в настройках есть команда для Windows, платформа `win32` → запускается она; на `linux` — основная.
- К14.3. Тест: workflow GitHub Actions плагина гоняет `plugin validate`, проверку типов и `plugin test` на
  `ubuntu-latest`, `macos-latest` и `windows-latest` и `plugin inspect` чистой выгрузки коммита.
- К14.4. Тест: на чистой выгрузке коммита `plugin inspect` CLI Orca проходит; в манифесте id `agent-queue` и имя
  «Agent Queue»; в папке плагина после подготовки разработки нет симлинков.
- К14.5. Тест: на подделке системы без `ORCA_CLI_COMMAND` плагин вызывает `orca-ide`, с ним — его значение; голого
  `orca` среди вызовов нет.

### Ф16. Демо-стенд для приёмки этого MVP

Этот MVP принимает автопилот agent-queue-kit на стенде с адресом, а у панели на компонентах Orca своего адреса нет.
Демо-стенд даёт его только на подделках (решение владельца «Только подделки»), без воркера плагина и без настоящих
`gh`, git и агентов:

- для каждого экрана и состояния раздела «Экраны» — сценарий проверки панели (`panel.check`) с подставным хостом
  Orca и придуманными данными: ответы воркера (`plugin.request`) задаёт сценарий; для действий владельца (кнопки и
  поля экранов) — последовательности `--act` со сценарием, кадр до и после;
- команды проекта `stand-setup`, `stand-up`, `stand-down`. `stand-up` собирает во временном каталоге демо-копию
  панели принимаемого коммита: манифест с id `agent-queue-demo`, без `main` (воркера нет, координатор и сторож не
  запускаются, `gh`, git и агенты не вызываются), только панель; загружает её в Orca как плагин разработки; снимает
  каждый сценарий `plugin shot` CLI Orca: кадр панели шириной 390 (`--width 390`) и кадр окна Orca (`--window`) для
  ширины компьютера, в светлой и тёмной теме; `--scenario`, `--theme` и `--act` снимают, только пока окно Orca
  скрыто или свёрнуто — иначе `stand-up` ждёт и пишет, что окно надо свернуть; затем отдаёт страницу стенда на
  `http://127.0.0.1:<порт>`: кадры по экранам и состояниям, кадры действий владельца, итоги `plugin check` и тестов
  плагина (поведение воркера проверяют они, на подделках);
- `stand-down` останавливает страницу, выгружает демо-копию из Orca и удаляет временный каталог.

Ревьюер приёмки открывает страницу во встроенном браузере Orca и сверяет кадры с доской дизайна и критериями. Экраны:
нет (стенд показывает экраны панели).

- К16.1. Тест: у каждого экрана и состояния раздела «Экраны» есть сценарий проверки панели, и у каждого сценария —
  экран и состояние из этого раздела.
- К16.2. Тест: `plugin check` CLI Orca рендерит все сценарии без ошибок.
- К16.3. Тест: демо-копия, которую собирает `stand-up`, — манифест с id `agent-queue-demo` без `main`, в ней нет
  файлов воркера.
- К16.4. Тест: страница стенда, собранная из набора кадров, перечисляет каждый сценарий с кадрами 390 и окна, кадры
  действий владельца и итоги `check` и тестов.
- К16.5. Тест: `stand-down` после `stand-up` (с поддельным CLI Orca) → страница не отвечает, поддельный CLI получил
  выгрузку демо-копии, временный каталог удалён.

  ревьюера» (только на компьютере, который ведёт задачу), «Ответить» (когда ждёт ответа); вкладки: «Ход» (комментарии
  хода по времени), «Ревью» (круги: вердикт, замечания — важность, путь файла, строка, суть), «Тесты» (прогоны: SHA,

### MVP

- Что на экране: «MVP: <название>», бейдж (идёт, ждёт ответа, приёмка идёт, готов к приёмке, приёмка не прошла,
  принят); переключатель «Автопилот»; пределы — в работе x из `in_progress`, взято за сутки x из `per_day`, задач x из
  `total`; этапы — задачи с их статусом; «Журнал решений» (решения решателя); «Только владелец»; приёмка — цикл,
  раунд и последний итог; кнопки «Открыть в GitHub»; «Открыть стенд» («Закрыть стенд», пока он поднят) — когда
  последний итог «готов» или «не прошла за 2 раунда»; «Принимаю» — только когда последний итог «готов» и после него
  нет новых задач MVP (без автопилота — когда все задачи закрыты); «Есть замечания» — когда есть итог.
- Состояния: идёт; заблокирована — причина; упёрлась в предел — какой; приёмка идёт — раунд; готов к приёмке;
  приёмка не прошла за два раунда — итог, без «Принимаю»; все задачи закрыты, автопилота нет; стенд поднят — адрес и
  «Закрыть стенд»; «Принимаю» отклонено — причина («Есть задачи MVP после итога»); принята; загрузка; ошибка.
- Переходы: задача этапа → «Задача»; «Открыть стенд» → стенд во встроенном браузере Orca; «Есть замечания» →
  терминал агента старта в Orca; «Назад» → «Очередь».

### Старт MVP

- Что на экране: шаги «Вопросы → ТЗ → Дизайн → План → Запуск» с текущим; агент старта; кнопка «Открыть чат старта»
  (терминал агента); показы — файл, версия (коммит), итог ревью (круг, вердикт или «ревьюер не проверял»), ссылка
  артефакта; у последнего показа ТЗ — «ТЗ: утверждаю» и «Есть правки», у показа доски — «Дизайн: утверждаю» и «Есть
  правки»; записанные решения владельца с версиями; что нужно для старта — вход в аккаунт Orca и включённая
  публикация артефактов; кнопка «Начать MVP»; на шаге «Запуск» — сводка плана (задач, этапов, пределы, «Только
  владелец», коммит, итоги ревью ТЗ, дизайна и плана) и вопрос «Запустить MVP?» с кнопками «Да», «В обычную
  очередь», «Правки», «Нет».
- Состояния: не начат — «Начать MVP» и что нужно; идёт — текущий шаг; ждёт владельца в чате — «Ответьте в чате
  старта»; ждёт утверждения ТЗ (или дизайна) — показ и кнопки; утверждено — версия и дата; ждёт подтверждения
  запуска — сводка и вопрос; запрос запуска отклонён — причина («ТЗ не той версии, что утверждена», «план изменён
  после ревью»); запускается — «Ставлю задачи…»; запущен — ссылка на «MVP», снятые ссылки показов (или какие снять
  не удалось); отказ «Нет» — ссылки сняты, ветка сохранена; ошибка — «Агент старта не запустился: <ошибка>» и
  «Повторить»; уже есть MVP — «У проекта уже есть MVP» и переход к нему.
- Переходы: «Открыть чат старта» и «Есть правки» → терминал агента в Orca; «Да» и «В обычную очередь» → «MVP»;
  «Правки» → «Старт MVP» на шаге «План»; ссылка показа — браузер; «Назад» → «Очередь».

## Вне MVP

- Перенос проектов, которые работают на agent-queue-kit (их очередей, `.agent-queue/`, открытых задач), на плагин:

- Ревью документов по правилу входа и согласование макетов дизайн-задач перед постановкой: сессия предложила их
  отложить (вопрос блока 3), владелец выбрал состав MVP без них. Ревью документов при старте MVP (Ф11) — в MVP.
- Тесты на настоящем GitHub и тестовый репозиторий для приёмки: решение владельца «Только подделки».
- Работа координатора и сторожа, когда Orca закрыта.
- Очередь самого плагина и его самообновление в стиле `bin/activate` кита: обновления — через каталог Orca.
- Деплой на прод.

## Только владелец

Что делает или даёт только владелец: аккаунты, ключи, оплата, домен, доступы внешних сервисов. Автопилот не делает
этого сам, а зовёт владельца.

- Внести плагин в каталог Orca со своего аккаунта — нужен для Ф14 (релиз); задача MVP готовит запись релиза.
- Включить GitHub Actions в репозитории плагина (у частного репозитория считаются минуты) — нужен для Ф14 (К14.3
  проверяет workflow, сам прогон на трёх системах — в Actions).
- Аккаунт Orca с включённой публикацией артефактов — нужен для показов старта MVP (Ф11) у каждого пользователя;
  у владельца он уже есть.
