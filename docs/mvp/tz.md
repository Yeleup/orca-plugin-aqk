Статус: черновик

Папка `docs/mvp/`: это ТЗ, дизайн — `maket/index.html` (доска экранов, после «ТЗ: утверждаю»), план — `plan.md`,
решения владельца дословно — `decisions.md`.

## Цель и проблема

Очередь агентов agent-queue-kit ведёт изменения проекта без человека: задача — issue GitHub, один агент её делает,
другой ревьюит, PR вливается после чистого ревью и зелёных тестов, а человек нужен, только когда задача заблокирована.
Автопилот доводит новый проект от ТЗ до принятого MVP. Сейчас кит — bash-скрипты и навыки Claude: агента-координатора
(LLM, который тратит токены на рутину) каждые 5 минут запускает автоматизация Orca, сторожа — таймер systemd; кит
работает только на Linux, ставится вручную (`bin/activate`, `install`, `init`), а увидеть очередь можно только в
GitHub и в терминале.

Agent Queue — тот же кит, сделанный плагином Orca (решение владельца: «тоже что и agent-queue-kit. Мы поменяем
реализацию на плагин. Который максимально будет использовать функционалы самого orca и будет работать в Mac, Windows,
Linux»). Когда MVP заработает:

- плагин ставится из каталога Orca на macOS, Windows и Linux любым пользователем Orca;
- задачу ведёт код плагина: он берёт задачу, создаёт worktree Orca, запускает агентов через Orca, следит за их
  статусом, сам гоняет тесты, мержит; LLM нужны только исполнителю, ревьюеру, решателю автопилота и агенту старта MVP;
- очередь видна и управляется в Orca: панель, строка состояния, уведомления, ответы на блокировки;
- задачи, как и в ките, — issues GitHub, в своём формате плагина (свои метки); плагин задач у себя не хранит: панель
  показывает GitHub и пишет в него через `gh`, а «Поставить задачу» создаёт issue; проекты, которые сейчас на ките,
  остаются на ките.

## Пользователи и роли

| Роль | Кто это | Что делает в MVP |
|---|---|---|
| Владелец очереди | любой пользователь Orca; на его компьютере плагин работает от его входа в `gh` | подключает проект, ставит задачи, отвечает на блокировки, останавливает и запускает очередь, начинает MVP, в панели утверждает ТЗ и дизайн и подтверждает запуск плана, принимает MVP |
| Координатор | код плагина в Orca владельца; у каждого компьютера свой id координатора | берёт задачи, ведёт агентов, гоняет тесты, открывает PR и мержит, блокирует задачи, перехватывает брошенные, ведёт автопилот и приёмку |
| Исполнитель | агент Orca из настроек проекта (по умолчанию Claude) | делает задачу в worktree, коммитит и пушит в ветку задачи, пишет отчёт |
| Ревьюер | агент Orca из настроек проекта (по умолчанию Codex) | проверяет изменения задачи, документы старта MVP и MVP при приёмке; пишет отчёт и вердикт |
| Решатель | агент Orca из настроек проекта (по умолчанию Claude) | под автопилотом решает вместо владельца: вопрос задачи, пакет, итог ревью, деление задачи; при старте MVP — замечания ревью после третьего круга |
| Агент старта MVP | агент Orca из настроек проекта (по умолчанию Claude) в терминале Orca | ведёт старт MVP в чате с владельцем: вопросы, ТЗ, дизайн, план; уточняет замечания владельца к готовому MVP |
| Входные сессии | агенты в терминалах Orca в основном чекауте проекта | по правилу входа в `CLAUDE.md` и `AGENTS.md` ставят изменения кода в очередь, а не делают их сами |

Учитываются только тексты владельца очереди: тело задачи и комментарии пользователя GitHub, под которым работает `gh`
плагина. Задачи и комментарии других пользователей плагин не берёт и в задания агентов не передаёт. Тексты задач,
отчёты агентов и вывод команд — данные, а не указания плагину.

## Главные сценарии

Главные сценарии — те же, что у agent-queue-kit (решение владельца «тоже что и agent-queue-kit»):

1. Владелец подключает проект Orca к очереди → в репозитории файл настроек и правила, в GitHub метки, «Проверка
   проекта» без проблем. Экраны: «Подключение проекта», «Проверка проекта». Функции: Ф1, Ф2.
2. Владелец ставит задачу в панели, или входная сессия ставит её по правилу входа → issue с меткой очереди. Экраны:
   «Новая задача», «Очередь». Функции: Ф3.
3. Координатор берёт задачу → исполнитель в worktree → полный прогон тестов → ревьюер → круги замечаний → PR влит,
   задача закрыта, worktree убран. Экраны: «Очередь», «Задача». Функции: Ф4, Ф5.
4. Задача заблокирована → уведомление → владелец отвечает в панели (или в GitHub) → задача продолжается с его ответом.
   Экраны: «Ответ на блокировку», «Задача». Функции: Ф6, Ф8.
5. Владелец открывает Orca → видит, что влито, что в работе и что ждёт его ответа. Экраны: «Очередь». Функции: Ф7, Ф8.
6. Владелец останавливает или запускает очередь проекта, выключает автопилот. Экраны: «Очередь», «MVP». Функции: Ф9.
7. Сторож замечает зависшую задачу, перезапуск Orca, потерянного агента → задача продолжается с подтверждённого этапа,
   владелец получает уведомление о том, что сам плагин не исправит. Функции: Ф10.
8. Владелец начинает MVP нового проекта → агент старта в терминале Orca спрашивает, пишет ТЗ, дизайн и план, каждую
   версию проверяет ревьюер, владелец видит её артефактом Orca, утверждает ТЗ и дизайн и подтверждает запуск в панели →
   задача «MVP» и задачи плана в очереди. Экраны: «Старт MVP», «MVP». Функции: Ф11.
9. Автопилот доводит задачи MVP без остановок: решатель вместо владельца, деление застрявших задач, пределы, сводка.
   Экраны: «MVP». Функции: Ф12.
10. Все задачи MVP закрыты → приёмка на стенде → «MVP готов к вашей приёмке» → владелец смотрит стенд, принимает в
    панели или даёт замечания. Экраны: «MVP». Функции: Ф13.

| Настройки плагина в Orca | язык интерфейса (`English` или `Русский`); интервал проверки очереди (минуты, по умолчанию 5); уведомления о мержах (вкл/выкл); координатор на этом компьютере (вкл/выкл); остановленные очереди проектов на этом компьютере | владелец в экране «Настройки» и кнопками «Остановить»/«Запустить» | в хранилище плагина Orca |

**Проверка перед каждой записью в GitHub.** В GitHub плагин пишет только сводки; отчёты агентов, вывод команд и
тексты команд остаются в каталоге данных. Перед записью плагин проверяет каждое поле:

- поля координатора — только номера задач и PR, SHA, коды выхода, время, длительность, id координатора (случайный),
  этап, круг, номер отсчёта, id операции; локальные пути и имя компьютера в GitHub не пишутся;
- маска плагина действует на каждое текстовое поле: адреса почты, номера телефонов, ключи и токены известных
  форматов и шаблоны запрещённых данных из настроек проекта; правило данных текстом плагин проверить не может — его
  соблюдают агенты по заданию, а то, что можно описать шаблоном, владелец вносит в шаблоны;
- пути файлов — только из проверяемого diff (сторона базы или изменений); путь, на который срабатывает маска,
  заменяется на «[скрыто]», полная строка замечания остаётся в каталоге данных;
- сохранённая незапушенная работа — только числа (коммитов, изменённых и новых файлов) и «сохранено на компьютере
  <id>»; имена этих файлов показывает панель на этом компьютере;
- шаг после мержа — его имя из настроек, а если на имя срабатывает маска или имени нет — номер шага; и код выхода,
  без текста команды и вывода;
- тексты агентов (вопрос, суть замечания, решение решателя, разделы PR) и тексты задач, которые создаёт плагин (план,
  части деления, задачи приёмки), — правило данных в задании агента и маска; набор задач операции проходит маску до
  комментария начала, и задачи создаются из этого же набора; исходный текст остаётся в каталоге данных.

## Функции и критерии приёмки

Каждая функция — с экранами раздела «Экраны» (по названию) и критериями, которые проверяет автоматический тест. Задача
«Приёмочные тесты MVP» пишет e2e-тест на каждый критерий; критерий, который тест проверить не может, переписывается.

Тесты идут только с подделками (решение владельца «Только подделки»): поддельный хост Orca (`orca/testing`:
`mockHost`, `mountWorker`, `mount`), поддельные `gh`, CLI Orca и агенты, без сети и без настоящего GitHub; git —
настоящий, на временных локальных репозиториях, `origin` — локальный bare-репозиторий.
«Проверка очереди» в критериях — один проход координатора, который тест вызывает сам, а не ждёт по таймеру; время в
тестах — поддельное.

### Ф1. Подключение проекта

Мастер подключает проект Orca к очереди. Экраны: «Подключение проекта», «Проверка проекта».

1. Владелец выбирает проект из проектов Orca, ещё не подключённых. Подключён — в удалённой базовой ветке есть коммит
   подключения плагина (`.agent-queue.json`). Проект на agent-queue-kit (есть `.agent-queue/config.json`) в списке
   помечен «На agent-queue-kit — переход после MVP» и не выбирается: его файлы, метки и правило входа плагин не
   трогает.
2. Плагин проверяет: проект — git-репозиторий с удалённым репозиторием GitHub; `gh` установлен, вход выполнен, у

### Ф4. Координатор: захват и ведение задачи

Пока Orca открыта, координатор этого компьютера включён и очередь проекта не остановлена, плагин раз в интервал
(настройка, по умолчанию 5 минут) проверяет очередь каждого подключённого проекта и берёт самую старую задачу в
очереди: метка `agent-queue`, нет `blocked`, `split`, нет действующей заявки (ниже), нет открытых зависимостей, нет
отложения, задача не создана незаконченной операцией (Ф11–Ф13), задач в работе меньше предела проекта (и для задачи
MVP — в пределах `in_progress` и `per_day`, Ф12). Задачи, которые он уже ведёт, координатор проверяет и при
остановленной очереди (Ф9).

**Захват и перехват — один протокол отсчётов.** GitHub не даёт атомарного замка и условной записи комментариев и
меток, поэтому право вести задачу решает порядок комментариев, а исключительного права записи нет. У каждой заявки —
номер отсчёта: номер последнего отсчёта в задаче + 1 (у первой — 1). Координатор пишет заявку (обычную или
«перехват»), затем ставит `agent-queue:working`, через 60 секунд перечитывает комментарии. Ведёт задачу автор первой
по порядку GitHub заявки с наибольшим номером отсчёта; все координаторы читают один порядок и решают одинаково.
Действующая заявка — заявка последнего отсчёта, после которой нет комментария освобождения (блокировка, отложение,
деление, освобождение); `working` — только отражение для панели и фильтра. Новый отсчёт открывают: заявка после
освобождения и перехват (Ф10) — только когда ведущий последнего отсчёта молчит 3 часа. Два одновременных перехвата
пишут один и тот же номер — ведёт первый; проигравший пишет «Задачу ведёт <id>» и не запускает агентов.

Промежуточные состояния:

- заявка есть, `working` нет (сбой между записями): заявитель на следующей проверке (после перезапуска — по журналу
  операций) ставит метку, другие задачу не берут; через 10 минут без метки и без нового комментария хода заявителя
  задачу можно взять новым отсчётом, а вернувшийся заявитель видит новый отсчёт и уступает;
- `working` есть, последний отсчёт освобождён: через 10 минут задачу можно взять новым отсчётом;
- владелец снял `working` руками: ведущий, который ставил метку (запись в журнале) и не нашёл её, пишет комментарий
  «освобождение», останавливает агентов и сохраняет работу (Ф6).

**Право на действие и на ветку.** Перед каждым действием по задаче — запуск или сообщение агенту, комментарий,
метка, PR, мерж, удаление worktree — координатор перечитывает заявки; проверка действует 30 секунд, старше (сон
компьютера, долгий вызов) — перечитать перед записью. Ведёт не он — останавливает своих агентов этой задачи,
сохраняет незапушенную работу её worktree только локально, без пуша (пачка, патч, архив — как в Ф6; пуш сменил бы
голову ветки уже после перехвата), пишет об этом один комментарий и больше по задаче ничего не делает.
Окно между проверкой и записью остаётся: прежний ведущий после перехвата успевает не больше одной записи. Поэтому
ведущий нового отсчёта определяет этап только по комментариям своего отсчёта и по ветке и PR, которые сверил сам, а
метки и состояние PR перед своим шагом приводит к своему этапу. Запоздалый мерж прежнего ведущего GitHub отклоняет,
если голова PR уже не та; если та же — влит SHA с одобрением и зелёным прогоном, и новый ведущий видит `MERGED` и
доводит уборку (Ф10). Пуш агента прежнего ведущего, успевший после перехвата, ведущий обнаруживает: голова ветки не
та, что он ожидал (последний SHA его исполнителя или ветки при перехвате). Такой SHA не допускается к ревью и мержу;
исполнитель ведущего получает чужие коммиты как черновик — принять (с проверкой) или отбросить, и отчитаться, что
сделал.

**Worktree.** Ветка задачи на `origin` и голова PR — ровно `agent-queue/issue-<N>`; агенты и плагин пушат всегда
`git push origin HEAD:agent-queue/issue-<N>`. Исключение — пуш после rebase уже опубликованной ветки, как в ките:
только условный пуш `git push --force-with-lease=refs/heads/agent-queue/issue-<N>:<SHA> origin
HEAD:agent-queue/issue-<N>`, где SHA — голова ветки на `origin`, которую ведущий запомнил перед rebase. Отказ
(голова другая) — неожиданная голова, разбор по правилу «Право на действие и на ветку». Локальная ветка worktree — служебная: Orca может дать ей суффикс, если
имя занято, это не ошибка; сверяется HEAD, а не имя. Открытие: `git fetch origin`; стартовая ссылка —
`origin/agent-queue/issue-<N>`, если ветка есть на `origin`, иначе `origin/<базовая ветка>`; локальную ветку с этим
именем, не выбранную ни в одном worktree, плагин удаляет сам (коммиты, которых нет на `origin`, сначала сохраняет
пачкой, Ф6); worktree создаётся CLI Orca (`worktree create --branch agent-queue/issue-<N>` от стартовой ссылки), Orca
готовит его своей подготовкой проекта (`orca.yaml`); существующая локальная ветка, отставшая от `origin` или нет, не
переиспользуется никогда. Сверка: HEAD нового worktree равен SHA стартовой ссылки; не равен — worktree убирается,
задача блокируется со сбоем инфраструктуры. После удаления worktree плагин удаляет и его локальную ветку.

**Ведение.** Исполнитель в worktree с заданием: текст задачи и комментарии владельца; правила для заданий; правило
данных; что правило входа к нему не относится; ограничения — тесты только полной командой проекта; коммит и пуш
только в ветку задачи командой выше; не мержить и ничего не писать в GitHub, кроме пуша в ветку; не трогать `.env*`,
`.agent-queue.json`, `.agent-queue.md`; зависимости не менять, кроме пакетов, которые задание разрешает (Ф6, Ф12);
вопрос — в отчёт, не догадкой; выбор технологии, который задача и документы не фиксируют, — вопрос, не решение
исполнителя. Путь файла отчёта — в каталоге данных. Отчёт готов, когда агент в Orca закончил («done») и файл отчёта
есть. После первого пуша — черновой PR в базовую ветку с `Closes #N`. После каждого этапа — комментарий хода на языке
проекта со служебной меткой этапа: захват, исполнитель запущен, сделано и PR, прогон тестов, круг ревью k — m
замечаний, исправлено, влита; последний комментарий живой задачи не старше 2 часов.

**Тесты.** После отчёта исполнителя плагин сам запускает полную команду тестов в worktree на закоммиченном дереве без
незакоммиченных и неотслеживаемых файлов и записывает прогон: SHA, код выхода, время начала, длительность, чистое ли
дерево до и после, полный вывод — в каталог данных. Засчитывается только прогон с кодом 0 на чистом дереве, у которого
HEAD в конце тот же. Красный прогон — вывод уходит тому же исполнителю; три красных прогона подряд — блокировка (Ф6)
или деление (Ф12).

- К4.1. Тест: задача в «Ждут» → после проверки очереди у неё заявка отсчёта 1 с id координатора, метка
  `agent-queue:working`, worktree с HEAD на `origin/<базовая ветка>`, исполнитель запущен с заданием, где есть текст
  задачи, правила для заданий, правило данных и команда пуша в `agent-queue/issue-<N>`.
- К4.2. Тест: предел «одновременно в работе» 1 и одна задача в работе → вторая не берётся, пока первая не закрыта
  или не заблокирована.
- К4.3. Тест: координаторы A и B читают задачу свободной, затем A пишет заявку, затем B; оба перечитывают → агентов
  запускает только A; B пишет «Задачу ведёт A» и больше ничего не делает. Тот же результат при порядке чтений «A, B,
  запись B, запись A» для того, чья заявка в GitHub первая.
- К4.4. Тест: исполнитель отчитался, тесты красные → исполнитель получает вывод теста; после третьего красного прогона
  подряд задача заблокирована.
- К4.5. Тест: исполнитель запушил первый коммит → черновой PR из `agent-queue/issue-<N>` в базовую ветку с
  `Closes #<N>` в теле.
- К4.6. Тест: в worktree есть неотслеживаемый файл → прогон записан как «дерево не чистое» и для мержа не
  засчитывается.
- К4.7. Тест: в задаче есть комментарий другого пользователя GitHub → его текста нет в задании исполнителя.
- К4.8. Тест: ведёт A (отсчёт 1), B и C одновременно пишут перехват отсчёта 2 → ведёт тот из B и C, чья заявка в
  GitHub первая; второй пишет «Задачу ведёт <id>»; A перед следующим действием останавливает агентов, сохраняет
  незапушенный коммит только локально (голова ветки на `origin` не изменилась) и пишет только комментарий о
  сохранённой работе.
- К4.9. Тест: после перехвата агент прежнего ведущего запушил коммит → ведущий видит неожиданную голову ветки; этот
  SHA не идёт на ревью; исполнитель ведущего получает чужой коммит как черновик и отчитывается о нём.
- К4.10. Тест: `working` стоит, последний отсчёт освобождён 10 минут назад → проверка очереди захватывает задачу
  новым отсчётом.
- К4.11. Тест (настоящий git): worktree задачи удалён, локальная ветка `agent-queue/issue-<N>` осталась и отстаёт от
  `origin` → у нового worktree HEAD на голове ветки с `origin`, PR тот же, нового PR нет; имя ветки занято оставленным
  worktree → суффикс Orca принят, пуш исполнителя приходит в `agent-queue/issue-<N>` на `origin`; HEAD нового
  worktree не тот → worktree убран, задача заблокирована.
- К4.12. Тест: запись метки после заявки не прошла → тот же координатор на следующей проверке ставит метку; другой
  координатор 10 минут задачу не берёт, потом берёт новым отсчётом, а вернувшийся заявитель уступает.
- К4.13. Тест: перехват записан между проверкой права и комментарием прежнего ведущего → этот комментарий в этап не
  идёт, ведущий приводит метки к своему этапу, прежний ведущий больше ничего не пишет.
- К4.14. Тест: запоздалый мерж прежнего ведущего → при другой голове PR GitHub его отклоняет; при той же — новый
  ведущий видит `MERGED`, доводит уборку, второго мержа нет.
- К4.15. Тест: владелец снял `working` у задачи в работе → ведущий пишет «освобождение», агенты остановлены, работа
  сохранена.
- К4.16. Тест (bare-репозиторий): rebase опубликованной ветки, голова на `origin` — запомненный SHA → условный пуш
  проходит; голова на `origin` другая → пуш отклонён, новая голова разбирается как чужой коммит, ничего не
  перезаписано.

### Ф5. Ревью, круги замечаний и мерж

**Ревью.** Ревьюер запускается в worktree задачи с ожидаемым SHA и заданием: только чтение, ничего не писать в git и
GitHub; проверить изменения против задачи, правил и правила данных; запустить полные тесты; записать отчёт и файл
вердикта — `issue`, `round`, `reviewed_sha`, `verdict` (`approve`, `changes`, `head-mismatch`), замечания с важностью
(`critical`, `major`, `minor`, `nit`), путём файла из проверяемого diff со стороной (`base` — файл базы, например
удалённый по ошибке; `head` — файл проверяемого SHA), строкой и одной строкой сути без данных, которые запрещает
правило данных. Неверный файл вердикта (в том числе путь, которого нет на своей стороне diff) не засчитывается:
ревьюер получает причину, круг не считается.

Отнять у агента права записи плагин не может; он сверяет до и после ревью: в worktree — HEAD и `git status`; на
`origin` — голову ветки задачи; у PR — открыт ли, черновик ли, базу, голову; у задачи — открыта ли и метки плагина.

- Изменилось только локальное: ревью отброшено, worktree возвращён к проверявшемуся SHA, ревью этого SHA запущено
  снова, круг не считается.
- Голова ветки на `origin` другая: ревью отброшено, новое не запускается — сначала разбор чужого SHA по Ф4, потом
  тесты, потом ревью получившейся головы.
- Изменены PR или задача без локальных правок: ревью отброшено; плагин возвращает то, что ведёт сам (открывает PR,
  возвращает базу, черновик, метки), и запускает ревью снова; вернуть нельзя (PR влит) — блокировка.
- Изменилось несколько из них сразу: ревью отброшено; плагин сверяет и приводит в порядок каждое затронутое
  состояние — worktree к проверявшемуся SHA, PR и задачу к своему этапу, чужую голову ветки — разбором по Ф4; новое
  ревью — только когда все затронутые состояния сверены, а при чужой голове — после её разбора и тестов.

**Круги.** `changes` — замечания тому же исполнителю (его терминал не принимает — новый исполнитель в том же worktree
с отчётами), потом новый круг. Замечание о выборе технологии, который задача и документы не фиксируют, исполнителю не
идёт: сначала владелец (блокировка, Ф6) или решатель (Ф12), потом решение — исполнителю вместе с остальными
замечаниями круга. Не больше трёх кругов; после третьего только minor/nit — ещё один круг по изменениям после
последнего ревью; иначе блокировка (под автопилотом — Ф12).

**Допуск к мержу** (решение владельца «Как в ките»). Мерж только когда все условия выполнены на `fetch` прямо перед
вызовом мержа:

1. ревьюер одобрил SHA X (`approve`, файл вердикта верный);
2. есть засчитанный прогон тестов SHA Y, где Y = X, или Y — rebase X на новую базу без конфликтов, и изменения Y
   относительно базы совпадают с изменениями X (отличаются только строки контекста); rebase с разрешением конфликтов
   — ещё круг ревью разрешения, который одобряет сам Y;
3. база B (её SHA запоминается) — предок Y; PR открыт, его база — базовая ветка проекта, голова — Y; задача
   открыта; ветка задачи не меняет `.agent-queue.json` и `.agent-queue.md`.

База ушла вперёд — исполнитель делает rebase, полный прогон на новом SHA. Перед мержем тело PR переписано по итогам
(Зачем, Что сделано, Проверка, Ревью) и PR переведён из черновика в готовые. Мерж — merge-коммит GitHub с условием,
что голова PR — Y. Гарантия как в ките: у влитого Y есть зелёный прогон, база B — предок Y на `fetch` прямо перед
мержем; сдвиг базы в оставшиеся секунды обнаруживается после мержа (ниже). Защиту ветки GitHub плагин поддерживает,
но не требует: GitHub отклонил мерж (в том числе «ветка не актуальна» по защите ветки) — ничего не влито, снова
допуск с шага 2.

**После мержа.** До запроса мержа ведущий пишет комментарий хода этапа «мерж» с B, Y и номером PR — по нему любой
координатор проекта доведёт проверку без каталога данных ведущего. Пока у какой-либо задачи проекта, открытой или уже
закрытой, последний этап — «мерж» или «проверка после мержа» без комментария их завершения, новые задачи проекта не
берёт ни один координатор: сначала сверка этого PR. После ответа GitHub плагин читает PR: состояние `MERGED`, база —
базовая ветка; merge-коммит M: второй родитель — Y, первый — B. Не влит (GitHub отказал) — этап «мерж» завершается
возвратом к допуску. Первый родитель B — этап завершён. Первый родитель не B (база сдвинулась между проверкой и
мержем, а GitHub всё равно влил) — этап «проверка после мержа» (комментарий хода с B, Y, M): полные тесты на M в своём
worktree. На этапах «мерж» и «проверка после мержа» перехват короче общего (Ф4): ведущий молчит 30 минут — другой
координатор пишет заявку «перехват» нового отсчёта (тот же протокол отсчётов, только срок 30 минут вместо 3 часов) и
доводит сверку PR и проверку по B, Y и PR из комментария, даже если сам комментарий о сдвиге ещё не записан. Долгий
прогон тестов на M ведущий продлевает комментарием хода «проверка идёт» не реже раза в 10 минут; прежний ведущий,
вернувшись после перехвата, видит новый отсчёт и уступает. Зелёные
— этап завершён, в итоговом комментарии «база сдвинулась при мерже, тесты M зелёные»; красные — уведомление
«Базовая ветка после мержа #<N> не проходит тесты» и пауза проекта: issue с меткой `agent-queue:paused` и причиной;
запрет захвата этапа снимается только после подтверждённой записи паузы, а пока пауза открыта, новые задачи проекта
не берёт ни один координатор — пока владелец не закроет её («Запустить» в панели или в GitHub). Уборка (удаление
ветки и остальное) — только после завершения этапа. PR влит не в базовую ветку или не с головой Y — блокировка. Дальше: ветка удалена, задача закрыта (если
`Closes #N` её ещё не закрыл), итоговый комментарий, основной чекаут обновлён (когда он на базовой ветке и чистый),
шаги после мержа из настроек, worktree убран, `working` снята. Уборка, которую прервал перезапуск, доводится
сторожем (Ф10), в том числе у задачи, которую GitHub уже закрыл по `Closes #N`. Мержи проекта на одном компьютере
идут по одному.

- К5.1. Тест: ревьюер вернул `changes` с двумя замечаниями → исполнитель получает оба, идёт круг 2; в задаче
  комментарий «круг 1: 2 замечания» со строками замечаний (важность, путь, строка, суть).
- К5.2. Тест: `approve` и засчитанный прогон того же SHA → PR переведён в готовые, влит merge-коммитом с родителями
  B и Y; ветка удалена, задача закрыта, итоговый комментарий со ссылкой на PR, worktree убран, метки `working` нет.
- К5.3. Тест: `approve`, а засчитанного прогона этого SHA нет → мержа нет, плагин запускает полные тесты на этом SHA.
- К5.4. Тест: файл вердикта с чужим SHA, без `verdict` или с путём замечания, которого нет на его стороне diff → не
  засчитан, ревьюеру отправлена причина, номер круга не вырос; замечание о файле, удалённом изменениями, с путём
  стороны `base` — засчитано.
- К5.5. Тест: после третьего круга осталось замечание `major` (вне автопилота) → задача заблокирована, в комментарии
  оставшиеся замечания.
- К5.6. Тест: база ушла вперёд после `approve`, rebase без конфликтов, изменения совпадают → полный прогон нового SHA,
  влит новый SHA без нового круга ревью.
- К5.7. Тест: rebase с разрешением конфликта → круг ревью разрешения; мерж только после `approve` нового SHA.
- К5.8. Тест: GitHub влил PR, но первый родитель merge-коммита — не запомненная база B → пока идёт прогон на
  merge-коммите, новые задачи не берёт ни один координатор; зелёные — задача закрыта с пометкой «база сдвинулась при
  мерже»; красные — уведомление и issue паузы с меткой `agent-queue:paused`, координатор с другим id новую задачу не
  берёт, после закрытия issue паузы — берёт.
- К5.16. Тест: ведущий остановился после ответа GitHub на мерж со сдвинутой базой, до комментария «проверка после
  мержа»; GitHub уже закрыл задачу → координатор с другим id и пустым каталогом данных новых задач не берёт, через 30
  минут пишет перехват нового отсчёта, берёт B, Y и PR из комментария этапа «мерж», сверяет PR, гоняет тесты на M и
  только потом удаляет ветку; красный итог — новые задачи не берутся, пока issue паузы не записан и не закрыт; два
  претендента на перехват — ведёт первый по порядку заявки; вернувшийся прежний ведущий уступает; прогон дольше 30
  минут с комментариями «проверка идёт» не перехватывается.
- К5.9. Тест: плагин перезапущен после мержа, GitHub уже закрыл задачу по `Closes #N` → сторож доводит уборку: ветка
  удалена, итоговый комментарий, worktree убран, `working` снята; второго мержа нет.
- К5.10. Тест: ветка задачи меняет `.agent-queue.json` → мерж отказан, задача заблокирована с этой причиной.
- К5.11. Тест, четыре случая: ревьюер изменил файл в worktree → ревью отброшено, worktree на проверявшемся SHA, ревью
  запущено снова, номер круга не вырос; ревьюер запушил в ветку → ревью отброшено, новое ревью не запущено до отчёта
  исполнителя о чужом коммите; ревьюер закрыл PR или сменил его базу без локальных правок → ревью отброшено, PR открыт
  и база возвращена, ревью запущено снова; ревьюер изменил файл и закрыл PR → ревью запущено только после того, как
  worktree на проверявшемся SHA и PR открыт с верной базой.
- К5.12. Тест: ревьюер нашёл выбор технологии, которого задача не фиксирует (вне автопилота) → задача заблокирована с
  вопросом и остальными замечаниями круга; исполнитель этого замечания не получал.
- К5.13. Тест: шаг после мержа из настроек вышел с кодом 1 → мерж остаётся, итоговый комментарий называет имя шага
  и код выхода, текста команды в нём нет; имя шага содержит значение из шаблонов запрещённых данных (придуманный
  идентификатор клиента) → в комментарии номер шага вместо имени.
- К5.14. Тест: GitHub отклонил мерж («ветка не актуальна» по защите ветки) → ничего не влито, задача не закрыта,
  исполнитель делает rebase, прогон нового SHA, мерж.
- К5.15. Тест: суть замечания ревьюера содержит адрес почты и строку вида токена → в комментарии хода вместо них
  «[скрыто]», исходный текст — в каталоге данных; путь замечания содержит придуманный идентификатор клиента из
  шаблонов → путь в комментарии «[скрыто]».

### Ф6. Блокировка, сохранение работы и ответ владельца

**Когда.** Нужен человек: вопрос, на который задача и документы не отвечают (выбор технологии тоже); нужен новый пакет
или зависимость (под автопилотом — Ф12); задача требует изменить настройки очереди; три неудачи одного шага; ревью не
одобрено за разрешённые круги; конфликт rebase, который исполнитель не разрешил; сбой Orca, GitHub или агента,
который не запускается.

**Порядок.** Остановить агентов задачи → сохранить работу → записать блокировку в GitHub (комментарий, затем метка
`agent-queue:blocked` вместо `working` — последней записью) → только после подтверждения записи убрать worktree.

**Сохранение работы.** Незапушенные коммиты пушатся в ветку задачи. Пуш не прошёл или остались изменённые и
неотслеживаемые файлы — плагин сохраняет их в каталог данных (коммиты пачкой git, изменения патчем, неотслеживаемые
файлы архивом; `.env*` — никогда) и записывает в журнал путь оставленного worktree, его HEAD, голову ветки на
`origin`, какие части сохранены (пачка, патч, архив — только те, что были нужны) и хэш каждой части. Такой worktree остаётся, но рабочим деревом задачи больше не считается:
агентов в нём не запускают, сверку Ф4 к нему не применяют, удаляют только по правилу ниже. В комментарии блокировки —
только числа (коммитов, изменённых и новых файлов) и «сохранено на компьютере <id>»; имена файлов показывает панель
на этом компьютере.

**Блокировка.** Комментарий: что сделано, что мешает, точный вопрос; уведомление Orca. GitHub не принимает записи —
блокировка не записана: агенты остановлены, worktree не трогается, задача остаётся у координатора, уведомление «Не
удалось заблокировать #<N>: <ошибка>», повтор на следующей проверке.

**Ответ.** Владелец отвечает в панели («Ответ на блокировку») или в GitHub (комментарий и снятие метки). Панель пишет
комментарий со служебной меткой операции, затем снимает метку. Ответ GitHub потерян — повтор ищет комментарий с этой
меткой и пишет его, только если не нашёл; снятие метки повторяется отдельно. Задача снова в очереди, следующий захват
продолжает её с ветки, задание содержит ответ владельца, круги ревью считаются заново.

**Сохранённая работа при возобновлении** (порядок кита: новый исполнитель — в новом чистом worktree, старый остаётся
до принятого отчёта). Координатор, у которого есть сохранённая работа задачи, при захвате проверяет копию по журналу
— только части, которые журнал называет: хэш каждой совпадает, пачка проходит `git bundle verify` и содержит
записанный HEAD; не подтверждается — сохраняет её заново из оставленного worktree, а не вышло — блокировка
«сохранённая работа на компьютере <id> не читается», worktree не удаляется. Затем создаёт новый чистый worktree по Ф4 и отдаёт исполнителю копию как черновик: применить пачку
коммитов, патч и архив, проверить, закоммитить нужное, отбросить остальное; отчёт называет каждый сохранённый коммит
и файл — взят или отброшен и почему. Оставленный worktree и копия удаляются только после принятого отчёта. Другой
компьютер сохранённой работы не видит: его задание исполнителя говорит, что часть работы осталась на компьютере <id>.

**Зависимости вне автопилота.** Задача, которой нужен пакет, блокируется с вопросом. Владелец добавляет пакет в
базовую ветку сам, или отвечает в блокировке строкой «Пакеты: <имена>»: при зависимостях `own` задание следующего
исполнителя разрешает ставить именно эти пакеты — после того как плагин проверил, что каталоги зависимостей worktree
— его собственные (не симлинки и не общие с основным чекаутом); при `shared` такой ответ не принимается — задача
снова блокируется с объяснением. Экраны: «Ответ на блокировку», «Задача», «Очередь».

- К6.1. Тест: исполнитель написал в отчёте вопрос → метка `agent-queue:blocked`, комментарий с вопросом, уведомление
  Orca «#<N> ждёт ответа: <заголовок>», агенты остановлены, worktree убран после записи метки, последний коммит
  исполнителя в ветке задачи.
- К6.2. Тест: ответ в «Ответе на блокировку» → в задаче комментарий с этим текстом, метка `agent-queue:blocked`
  снята; следующая проверка очереди берёт задачу, и задание исполнителя содержит ответ.
- К6.3. Тест: метку сняли в GitHub после комментария владельца → задача берётся, задание содержит этот комментарий.
- К6.4. Тест: поле ответа пустое → кнопка «Ответить и вернуть в очередь» недоступна.
- К6.5. Тест (настоящий git): при блокировке пуш отклонён, в worktree незапушенный коммит и изменённый файл →
  worktree остаётся, копия (пачка и патч) в каталоге данных, комментарий блокировки — числа и «сохранено на
  компьютере <id>», без имён файлов и путей; после ответа владельца тот же компьютер создаёт новый чистый worktree на
  голове ветки, оставленный не тронут; задание исполнителя содержит пачку с этим коммитом и патч с этим файлом; до
  принятого отчёта оставленный worktree и копия на месте, после — удалены.
- К6.6. Тест: GitHub отказал в записи блокировки → метки не изменились, worktree на месте, уведомление «Не удалось
  заблокировать #<N>»; следующая проверка при рабочем GitHub записывает блокировку и только потом убирает worktree.
- К6.7. Тест: комментарий ответа записан, а ответ GitHub потерян → повтор находит комментарий по метке операции и
  второго не пишет; снимает метку.
- К6.8. Тест: ответ «Пакеты: left-pad» при зависимостях `own` и собственных каталогах зависимостей → задание
  исполнителя разрешает ставить `left-pad`; при `shared` → задача снова заблокирована с объяснением.
- К6.9. Тест: пуш прошёл, остался только изменённый файл → журнал называет только патч, проверка копии его хэш
  принимает, исполнитель получает патч; архив копии повреждён (хэш не совпал) → копия сохранена заново из
  оставленного worktree; оставленного worktree нет → блокировка «сохранённая работа на компьютере <id> не
  читается».

### Ф9. Стоп и пуск

Две разные остановки. **Пауза проекта** — общая для всех компьютеров: её ставит только плагин после красного прогона
на merge-коммите (Ф5) — issue с `agent-queue:paused`; снимает её закрытие этого issue — кнопкой «Запустить» в
панели или в GitHub; пока она открыта, новые задачи проекта не берёт ни один координатор. **«Остановить» очередь
проекта** — только кнопкой владельца, только на этом компьютере. Не делается: захват новых задач проекта, перехват чужих, новые шаги
автопилота по задаче «MVP» проекта (новое деление, сводка, приёмка). Продолжается для задач, которые координатор уже
ведёт: проверка их этапов, ревью, тесты, мерж, блокировка, сторож (восстановление после потери агента,
уведомления); начатое деление доводится до конца (части, перенос зависимостей, закрытие исходной), чтобы не оставить
его наполовину. «Запустить» — снова всё на этом компьютере; а открытая пауза проекта при этом закрывается — для
всех компьютеров.

**«Выключить автопилот»** на экране «MVP» снимает `agent-queue:autopilot` с задачи «MVP» — для всех компьютеров;
«Включить автопилот» — ставит. Без автопилота вопросы задач MVP идут владельцу (Ф6), новое деление и приёмка не
начинаются. Деление и раунд приёмки, у которых уже записан комментарий начала (Ф12), доводятся до конца по записанному набору
(как при остановке): их задачи становятся обычными задачами MVP, захватываемыми после отметки конца; задача с
`agent-queue:split`, деление которой не начато, получает `agent-queue:blocked` вместо `split` и комментарий
«Автопилот выключен: задача ждала деления — решите сами». Идущая приёмка: до комментария начала раунда (Ф12) — останавливается в
таком порядке: ревьюер приёмки остановлен, `down` стенда, worktree приёмки убран, итога нет; после комментария
начала — записанный набор задач раунда и отметка конца доводятся (как деление), другие записи итога («готов», «не
прошла», метка `blocked`) не делаются; после включения автопилота приёмка начинается
заново. Метка снимается для всех компьютеров, поэтому координатор, который ведёт приёмку, перечитывает задачу «MVP»
на каждой проверке и прямо перед каждой записью: автопилота нет или «MVP» заблокирована — не начинает новый раунд и
не пишет итог («готов», «не прошла», метка `blocked`) и останавливает стенд и ревьюера. Исключение — раунд с уже
записанным комментарием начала: его записанный набор задач и отметку конца он дописывает и при снятой метке. Экраны:
«Очередь», «MVP».

- К9.1. Тест: очередь проекта остановлена, одна задача в работе, одна ждёт → проверка очереди новую не берёт, задача в
  работе доходит до мержа.
- К9.2. Тест: «Запустить» → следующая проверка очереди берёт ждущую задачу.
- К9.3. Тест: «Выключить автопилот» → метка `agent-queue:autopilot` снята; следующий вопрос задачи MVP блокирует её
  (Ф6), решатель не спрашивается.
- К9.4. Тест: остановка очереди после создания первой части деления → деление доведено: все части созданы, зависимые
  ждут части, исходная закрыта; новых задач координатор не берёт.
- К9.5. Тест: автопилот выключен, у задачи `agent-queue:split`, деление не начато → метка `split` заменена на
  `blocked`, комментарий «Автопилот выключен: задача ждала деления — решите сами».
- К9.6. Тест: автопилот выключен после создания первой части деления → деление доведено до конца.
- К9.7. Тест: автопилот выключен, когда стенд приёмки поднят → ревьюер приёмки остановлен, выполнен `down`, worktree
  приёмки убран, комментария с итогом приёмки нет; метку сняли, когда приёмку ведёт координатор с другим id, а
  ревьюер уже отчитался → этот координатор итог не записывает.
- К9.8. Тест: очередь остановлена, агент задачи в работе пропал → сторож запускает нового агента по этапу задачи.
- К9.9. Тест: создана первая задача раунда приёмки, автопилот выключили с другого компьютера → ведущий «MVP»
  дописывает остальные задачи раунда по комментарию начала и отметку конца; задачи раунда берутся как обычные
  задачи MVP; новая приёмка не начинается.
- К9.10. Тест: «Запустить» при открытой паузе проекта → issue паузы закрыт, координатор другого компьютера на
  следующей проверке берёт задачу; issue паузы закрыт в GitHub → оба компьютера (и тот, что делал мерж) на следующей
  проверке берут задачи; красный прогон не ставит локальную остановку ни на одном компьютере.
- К9.11. Тест: автопилот выключен сразу после комментария начала раунда приёмки, до создания первой задачи →
  ведущий «MVP» создаёт задачи раунда по набору и отметку конца; комментария «готов» или «не прошла» и метки
  `blocked` нет.

### Ф10. Сторож

Внутри плагина, раз в 5 минут, пока Orca открыта. Сбой чтения GitHub никогда не считается пустой очередью или брошенной
задачей. Одно уведомление на условие, пока оно держится.

**Восстановление с подтверждённого этапа.** Этап задачи — служебная метка последнего комментария хода. Задача, которую
ведёт этот координатор, а её агента в Orca нет (перезапуск Orca, закрытый терминал): живые агенты задачи (их видно в
Orca) не дублируются; продолжение по этапу — исполнитель: новый исполнитель в worktree задачи (worktree нет — по Ф4)
с последним отчётом и сохранённой работой (Ф6); тесты: прогон заново; ревью: новый ревьюер того же SHA; мерж:
проверка PR в GitHub — `MERGED` доводится по Ф5. Комментарий «Продолжено после потери агента: <этап>». Сюда же —
задачи, закрытые (по `Closes #N` или плагином) с незавершённой уборкой: у них ещё стоит `working`, есть ветка или
worktree, или нет итогового комментария — уборка доводится, агенты не запускаются.

**Перехват.** Задача в работе у другого координатора, комментариев хода 3 часа → заявка «Перехват: предыдущий
координатор молчал 3 часа» нового отсчёта (Ф4); продолжение с ветки по этапу. Незапушенная работа прежнего
координатора остаётся на его компьютере: он сохранит её, когда увидит перехват (Ф4).

**Уведомления.** Агент задачи ждёт ввода человека 30 минут — «#<N>: агент ждёт ввода» (в панели у задачи — переход к
его терминалу). Агент упёрся в лимит использования — задача отложена на час: комментарий «Отложено до <время>», метка
`working` снята, до этого времени задачу не берут. GitHub не прочитан три проверки подряд. Задача «MVP» под
автопилотом: 6 часов ни одного мержа и ничего в работе; достигнут предел; готова к приёмке или заблокирована.

- К10.1. Тест: задача на этапе «исполнитель», агента в Orca нет → запущен новый исполнитель в worktree задачи,
  комментарий «Продолжено после потери агента: исполнитель».
- К10.2. Тест: задача на этапе «ревью» SHA X, ревьюера в Orca нет, исполнитель жив → запущен новый ревьюер с SHA X,
  нового исполнителя нет.
- К10.3. Тест: задача на этапе «мерж», PR в GitHub уже `MERGED`, задача закрыта GitHub → ветка удалена, итоговый
  комментарий, `working` снята, ни одного агента не запущено.
- К10.4. Тест: задача в работе у другого id, последний комментарий хода 3 часа назад → заявка «Перехват…» нового
  отсчёта, агенты этого координатора продолжают с ветки.
- К10.5. Тест: агент в состоянии «waiting» 30 минут → одно уведомление «#<N>: агент ждёт ввода»; вторая проверка
  нового не показывает; после выхода из ожидания условие снято.
- К10.6. Тест: GitHub не прочитан три проверки подряд → уведомление; ни одна задача не перехвачена и не взята.
- К10.7. Тест: отчёт агента о лимите использования → комментарий «Отложено до <время + 1 ч>», метки `working` нет;
  проверка до этого времени задачу не берёт, после — берёт.

### Ф11. Старт MVP

**Запуск агента.** «Начать MVP» в панели (подключённый проект без открытой задачи «MVP» и без незавершённого запуска —
ниже, «Итоговый коммит») запускает агента старта в
терминале Orca основного чекаута проекта с инструкцией плагина. Агент делает то, что сейчас навык
`/agent-queue-start`: спрашивает владельца в чате по блокам (цель, данные и интеграции, состав MVP, «только
владелец»), записывает ответы дословно в `decisions.md`, пишет ТЗ (экраны словами), после утверждения ТЗ — доску
дизайна `maket/index.html`, после утверждения дизайна — план `plan.json`; всё в `docs/mvp/` в своём worktree на ветке
`agent-queue/mvp-spec`, каждая версия — коммит. Вопросы и замечания владельца — в чате; решения, от которых зависит,
что будет построено, — в панели (ниже).

**Ревью и показ — через плагин.** Агент старта не публикует и не ревьюит сам: он кладёт в каталог старта запрос с
коммитом и файлами. Ревью: плагин запускает ревьюера из настроек в новом терминале с файлами этого коммита и
решениями владельца из `decisions.md`, записывает отчёт с вердиктом, кругом, коммитом и хэшами файлов; до трёх кругов
на показ, потом решатель отвечает по оставшимся замечаниям, потом ещё до трёх. `plan.md` агент не пишет: плагин строит
его из `plan.json` того же коммита (те же задачи со всеми полями), и ревью и показ плана — это `plan.md`, построенный
из этого `plan.json`, вместе с ним. Показ: плагин публикует файл артефактом Orca (решение владельца «Артефакты Orca,
как сейчас») только когда файл на диске совпадает с версией, которую видело последнее ревью этого показа (или ревью
не смогло пройти — тогда с пометкой «ревьюер не проверял: <причина>»); следующий показ того же файла обновляет тот
же артефакт, ссылка не меняется. Публикация — отдельное состояние показа, записанное в журнал до вызова Orca вместе
с точными байтами публикуемой версии и номером показа: с начала публикации до ответа Orca, который её подтверждает,
решения по этому файлу заблокированы — и по прежнему показу тоже, ведь ссылка уже может отдавать новую версию. Воркер
проверяет это состояние при каждом утверждении и ответе на запуск, в том числе после своего перезапуска. Исходы
публикации:

- ответ потерян или Orca не ответила (временный сбой) — плагин повторяет обновление того же файла (оно не создаёт
  второго артефакта), пока Orca не подтвердит; решения заблокированы;
- ошибки, которые устраняет только владелец, — без повтора, экран называет, что сделать, и даёт «Повторить
  публикацию» сохранённой версии, когда причина устранена; решения заблокированы до успешной публикации:
  публикация артефактов выключена (`artifact_sharing_disabled`) — «включите Settings → Artifacts в Orca»; Orca
  работает как сервер без настольного приложения (`sharing_unavailable_on_host`) — «откройте старт MVP в приложении
  Orca на компьютере»; в Orca не выполнен вход в аккаунт — «войдите в аккаунт Orca»;
- артефакт удалён владельцем в панели артефактов — плагин снимает устаревшую запись Orca и публикует файл заново (новая
  ссылка, экран об этом говорит);
- первая публикация файла (`share`) прервана — публичная ссылка может уже существовать, хотя Orca её ещё не
  записала: отметка «публикация начата» стоит до подтверждения, экран показывает «ссылка может быть открыта —
  проверьте панель артефактов Orca», даже когда адрес неизвестен; следующая публикация того же файла доводит
  прерванную.

Снятие ссылок так же: неподтверждённое снятие и файл с отметкой «публикация начата» без записи Orca экран называет
«ссылка может быть открыта». Ссылку и итог ревью агент передаёт
владельцу в чате, плагин — на экран «Старт MVP».

**Исчерпанные круги и сбой ревьюера.** Ревью не одобрило версию и после шестого круга (три, решатель, ещё три) — как
в ките, версия всё равно показывается, с оставшимися замечаниями и позицией решателя на экране «Старт MVP»; решает
владелец: «утверждаю» (или ответ на запуск) для такой версии записывается вместе с числом и списком принятых
замечаний. Ревьюер не смог проверить (не запустился, упал) — версия показывается с пометкой «ревьюер не проверял:
<причина>»; «утверждаю» или ответ на запуск для неё — явное подтверждение владельца, записывается с этой причиной.

**Решения владельца — в панели, по версиям.** У каждого показа — идентификатор: файл, коммит, хэш файла, номер
показа. На экране «Старт MVP» у показа ТЗ — «ТЗ: утверждаю» и «Есть правки», у показа доски — «Дизайн: утверждаю» и
«Есть правки»; на кнопке — короткий коммит и номер показа. Кнопки утверждения доступны только после «Открыть показ»
этого показа из панели (старую вкладку браузера плагин не видит) и только при подтверждённой публикации; новый показ
того же файла это сбрасывает. Нажатие
передаёт воркеру идентификатор показа, по которому нарисован экран; воркер сверяет его с последним показом этого
файла: не совпал — отказ «Показ обновился: откройте новую версию», решение не записано. Записанное решение хранит
идентификатор показа. Агент переходит к дизайну только с записанным «ТЗ: утверждаю» той версии ТЗ, что лежит в его
коммите, и к плану — только с «Дизайн: утверждаю» той версии доски; изменённое после утверждения ТЗ или доска снова
требуют показа и утверждения. «Есть правки» — агент спрашивает о них в чате, новые версии, ревью и показы по той же
ссылке.

**Подтверждение запуска.** Когда план показан, агент кладёт запрос запуска с коммитом. Сначала плагин проверяет сам
план (как в «План в очередь»: известные поля, уникальные ключи, зависимости только на ключи плана, без циклов, число
задач в пределах `total`); ошибка — вопроса запуска нет, показ остаётся, экран «Старт MVP» возвращается на шаг «План»
с причиной. Затем плагин принимает запрос, только если в этом коммите: `tz.md` и `maket/index.html` — те версии, что владелец утвердил; `plan.json` — тот, из которого
построен показанный `plan.md`, одобренный последним ревью, показанный после исчерпанных кругов с замечаниями или
показанный с пометкой «ревьюер не проверял».
Ответ на запуск доступен только после «Открыть показ» текущей подтверждённой версии плана. Экран «Старт MVP»
показывает сводку (задач, этапов,
пределы, «Только владелец», коммит, итоги ревью ТЗ, дизайна и плана) и вопрос «Запустить MVP?»: «Да» (с
автопилотом), «В обычную очередь», «Правки» (агент правит план, новое ревью и показ), «Нет». Ответ привязан к
запросу запуска и показу плана, по которым нарисован экран: новый запрос запуска или новый показ плана после открытия
экрана — ответ со старого экрана отклонён. В момент нажатия плагин сохраняет снимок `plan.json` этого коммита;
задачи создаются только из снимка и только после нажатия — файл плана сам по себе ничего не создаёт. Ответ
окончательный («Да», «В обычную очередь» или «Нет») — плагин сразу, до итогового коммита и пуша, снимает ссылки всех
показов старта (как в ките — после ответа на вопрос о запуске); снимок остаётся в каталоге старта для повтора
запуска; ссылка, которую снять не удалось, названа на экране — владелец удалит её в панели артефактов Orca.

**Итоговый коммит** (для «Да» и «В обычную очередь»). Промежуточные коммиты старта остаются на этом компьютере и в
GitHub не попадают: плагин делает один коммит от базовой ветки с итоговыми файлами `docs/mvp/` — `plan.md` — точные
байты показанного файла из каталога старта (не новая сборка); в `decisions.md` дописаны решения из панели — дата,
вопрос, нажатая кнопка, идентификатор показа; `tz.md`, `maket/index.html` и `plan.json` побайтно те же, что в коммите
запроса запуска; `launch.json` — запись запуска: устойчивый id плана, режим («Да» или «В обычную очередь»), время.
Ветка `agent-queue/mvp-spec` на `origin` указывает на этот коммит (новая ветка — обычный пуш, ветка прежнего старта —
условный пуш на её запомненную голову). Порядок: снимок → итоговый коммит → пуш → проверка, что ветка на `origin`
указывает на этот коммит → только потом задачи. SHA итогового коммита — в служебной метке плана и в тексте первой
задачи. Пуш отклонён или не подтверждён — ни одной задачи; worktree старта остаётся; экран показывает «Не удалось
запушить документы: <ошибка>» и «Повторить» (из снимка, без нового вопроса). После записи плана (или «Нет») плагин
убирает worktree старта.

**Незавершённый запуск.** `launch.json` на `origin`, а план ещё не записан (нет задачи «MVP» с отметкой «план
записан») — запуск не завершён. Пока так: «Начать MVP» в проекте недоступна на всех компьютерах («Запуск MVP не
завершён»), ветку `agent-queue/mvp-spec` плагин не заменяет; запуск доводит тот компьютер, где он начат, а если
задачи «MVP» этого плана нет 10 минут — любой координатор проекта по `launch.json` и `plan.json` итогового коммита
с `origin`.

**Маска документов.** Маска плагина (раздел «Данные») проверяет файлы `docs/mvp/` перед каждым показом и итоговый
коммит перед пушем. Сработала на показе — показа нет, экран «Старт MVP» называет файл; агент исправляет документ,
дальше — новое ревью и новый показ. Сработала впервые на итоговом коммите (в дописанных решениях из панели или в
записи запуска) — пуша и задач нет, ответ на запуск сброшен, снимок удалён, экран «Старт MVP» возвращается на шаг
«План» с причиной; агент исправляет документ, дальше — новое ревью, новый показ (ссылки уже сняты — публикация
заново, с новой ссылкой) и новый вопрос «Запустить MVP?».

**План в очередь.** Плагин проверяет снимок (известные поля, уникальные ключи, зависимости только на ключи плана, без
циклов) и пишет одной операцией с id: задача «MVP» со служебной меткой плана (id плана, коммит документов), затем
задачи плана по одной, каждая со служебной меткой своего ключа, затем чек-лист задачи «MVP», последней записью —
отметка «план записан» в служебной метке задачи «MVP». Повтор после сбоя или потерянного ответа GitHub находит уже
созданное по меткам и создаёт только недостающее. Пока отметки «план записан» нет, координаторы задачи этого плана не
берут. Первая задача плана — «Утверждённые документы MVP»: перенести `docs/mvp/` из итогового коммита ветки
`agent-queue/mvp-spec` (его SHA — в тексте задачи) в базовую ветку как есть; все остальные задачи зависят от неё; последняя — «Приёмочные тесты
MVP», зависит от всех остальных. Экраны: «Старт MVP», «MVP».

- К11.1. Тест: «Начать MVP» в подключённом проекте без задачи «MVP» → в Orca запущен агент старта из настроек с
  инструкцией плагина в основном чекауте проекта; экран «Старт MVP» в состоянии «идёт», кнопка недоступна.
- К11.2. Тест: у проекта открыта задача «MVP» → «Начать MVP» недоступна, экран «Старт MVP» ведёт на экран «MVP».
- К11.3. Тест: в каталоге старта запрос ревью `tz.md` коммита C → плагин запускает ревьюера из настроек в новом
  терминале с файлом коммита C и решениями владельца; отчёт с вердиктом, кругом, C и хэшем файла лежит в каталоге
  старта.
- К11.4. Тест: запрос показа файла, изменённого после последнего ревью → отказ «не проверенная версия», ничего не
  опубликовано; файл той версии, что видело ревью, → опубликован, второй показ того же файла обновляет тот же

- К11.5. Тест: «ТЗ: утверждаю» в панели для показанной версии V, затем в коммите запроса запуска `tz.md` другой версии
  → запрос запуска отклонён «ТЗ не той версии, что утверждена»; то же для доски.
- К11.6. Тест: `plan.json` в коммите запроса запуска не тот, из которого построен одобренный `plan.md` → запрос
  отклонён, вопроса запуска нет.
- К11.7. Тест: запрос запуска верный, владелец не нажимал → ни одной задачи не создано; «Да» → issue «MVP: <название>»
  с метками `agent-queue:mvp` и `agent-queue:autopilot`, критериями, «Только владелец», чек-листом по этапам,
  пределами и отметкой «план записан»; задачи плана с «MVP: #E», «Зависит от #N» и меткой `agent-queue` — из снимка,
  сделанного при нажатии.
- К11.8. Тест: «В обычную очередь» → та же задача «MVP» без метки `agent-queue:autopilot`.
- К11.9. Тест: снимок с неизвестным полем, зависимостью от ключа, которого нет в плане, или циклом зависимостей →
  отказ с причиной, ни одной задачи не создано.
- К11.10. Тест: сбой после создания задачи «MVP» и двух задач плана (или потерянный ответ GitHub на создание третьей),
  повтор → создаются только недостающие задачи, задача «MVP» одна, чек-лист полный; до отметки «план записан»
  проверка очереди задачи плана не берёт.
- К11.11. Тест: после «Да» ссылки всех показов старта сняты до итогового коммита и пуша; ссылку, которую снять не
  удалось, экран «Старт MVP» называет; пуш итогового коммита отклонён → ссылки уже сняты, снимок в каталоге старта,
  «Повторить» запускает из него без нового вопроса.
- К11.12. Тест: задачи плана, кроме первой, зависят от «Утверждённых документов MVP»; «Приёмочные тесты MVP» зависят
  от всех остальных.
- К11.13. Тест: `plan.md` показа построен плагином из `plan.json` того же коммита и содержит каждую его задачу со всеми
  полями.
- К11.14. Тест: пуш итогового коммита отклонён → ни одной задачи, worktree старта на месте, экран «Не удалось
  запушить документы»; после «Повторить» запуск проходит.
- К11.15. Тест (настоящий git): итоговый коммит на `origin` содержит утверждённые `tz.md` и доску, `plan.json` снимка,

- К11.16. Тест, для ТЗ, доски и запуска: экран нарисован для показа 1, опубликован показ 2, нажата кнопка показа 1 →

- К11.17. Тест: обновление артефакта показа 2 ушло, ответ Orca потерян → кнопки утверждения показа 1 и показа 2

  не открыт из панели → ответ на запуск недоступен.
- К11.18. Тест: ревью плана не одобрило версию после шестого круга → вопрос запуска показан с оставшимися

- К11.19. Тест: ревьюер не запустился при ревью плана → план показан с пометкой «ревьюер не проверял: <причина>»,

- К11.20. Тест: в `plan.json` придуманный идентификатор клиента из шаблонов запрещённых данных → показа нет, экран

- К11.21. Тест: итоговый коммит запушен, компьютер остановился до создания задачи «MVP» → через 10 минут координатор

- К11.22. Тест: публикация выключена (`artifact_sharing_disabled`) → повтора нет, экран называет, что включить, и

  вопрос запуска.

### Ф12. Автопилот MVP

Пока задача «MVP» открыта и у неё `agent-queue:autopilot`, там, где задача MVP была бы заблокирована, решает плагин:

| Вне автопилота | Под автопилотом |
|---|---|
| вопрос, на который задача и документы не отвечают (выбор технологии тоже, найденный исполнителем или ревьюером) | решатель решает; вопрос о ключах, оплате, аккаунтах, доступах, деплое или пункте «Только владелец» — блокировка |
| нужен пакет | зависимости worktree `own`, каталоги зависимостей worktree собственные (Ф6) и пакет в разделе «Пакеты» задачи — исполнитель ставит его в задаче (задание разрешает именно эти пакеты); другой пакет — решатель, разрешение приходит исполнителю после решения; зависимости `shared` — блокировка |
| ревью не одобрено после круга 3 | решатель один раз по оставшимся замечаниям, потом круги 4–6; не одобрено — деление |
| три неудачи одного шага | деление |
| конфликт rebase | одна новая попытка от свежей базовой ветки (прежняя ветка сохранена пачкой), потом деление |
| лимит агента | задача отложена (Ф10) |

Решение — комментарий «Решение по #<N>» (вопрос, решение, обоснование) в задаче и в задаче «MVP»; он же — запись,
по которой повтор после сбоя действует, не спрашивая решателя снова.

**Операции, которые создают задачи** (план — Ф11, деление, раунд приёмки и замечания владельца — Ф13) идут по одному
правилу, видному в GitHub, а не только в каталоге данных одного компьютера:

- до первой записи — комментарий начала с id операции и полным набором (ключ, заголовок, текст, критерии каждой
  задачи); ключи устойчивые: `split-<N>-<k>`, `accept-<id операции>-<k>`;
- каждая созданная задача — со служебной меткой операции и своего ключа; задачу с меткой операции не берут, пока у
  операции нет отметки конца;
- отметка конца — последней записью; в ней — утверждённое соответствие ключей номерам задач; захватываются только
  задачи из этого соответствия, а задача с меткой операции не из него — дубль: следующая проверка закрывает её;
- операция с началом без конца доводится первой — тем, кто её ведёт, а после перехвата — другим координатором — по
  набору из комментария начала, без нового запуска решателя и ревьюера; пока она не доведена, новая приёмка, деление
  и сводка не начинаются;
- исход создания задачи бывает неизвестен (ответ потерян, запоздалая запись прежнего ведущего после перехвата), а
  GitHub уникальность ключа не держит. Поэтому перед отметкой конца ведущий операции перечитывает все задачи с её
  меткой: на ключ несколько задач — остаётся меньший номер, остальные закрываются комментарием «Дубль #<номер>» и не
  берутся; зависимости и чек-лист — только на оставшиеся. Запоздалая запись после отметки конца в соответствие не
  входит, не берётся и закрывается следующей проверкой как дубль;
- у плана (Ф11) началом служит запись запуска `launch.json` в итоговом коммите на `origin` (id плана, режим) и
  `plan.json` того же коммита — полный набор; задача «MVP» несёт id плана и этот коммит; две задачи «MVP» одного плана
  — остаётся меньший номер, вторая закрывается как дубль. Отметка «план записан» хранит номер основной задачи «MVP»:
  вести (автопилот, сводка, приёмка) и показывать в панели можно только её; задача «MVP» того же плана с другим
  номером — дубль, даже если она создана позже отметки: следующая проверка её закрывает, приёмка по ней не
  начинается.

**Ведущий задачи «MVP».** Приёмку, задачи раунда, сводку и постановку замечаний владельца ведёт один координатор по
заявке в задаче «MVP» — тот же протокол отсчётов и перехват через 3 часа молчания, что в Ф4. Деление ведёт ведущий
самой задачи.

**Деление** — операция по правилу выше. Решатель делит задачу на 2–3 части; ответ с другим числом частей — отказ,
один повторный запрос, затем блокировка. Решение о частях (заголовки и тексты) — комментарий «Решение по #<N>:
деление», он же комментарий начала. Затем: части — новые задачи с «Часть #<N>», `MVP: #E` и материалом исходной
(ветка, причина, сохранённая работа); затем задачи, ждавшие #N, ждут части; затем чек-лист «MVP»; черновой PR закрыт
без мержа; исходная задача закрыта последней — пока у неё остаются зависимые, она открыта; затем отметка конца. Часть
или задача, начатая заново дважды, не делится — блокируется с историей попыток.

**Пределы.** Из текста задачи «MVP» (владелец может менять числа): `in_progress` — задач MVP в работе одновременно,
держит захват; `per_day` — задач MVP, взятых за последние 24 часа (скользящее окно), держит захват; `total` — всего
задач MVP с частями и задачами приёмки, держит только добавление задач (части, задачи приёмки), не захват. По
умолчанию 3, 20 и число задач плана × 1,5 с округлением вверх. Деление или задачи приёмки, которые превысили бы
`total`, не создаются: задача (или задача «MVP») блокируется с просьбой поднять `total`.

**Сводка.** Раз в сутки — комментарий в задаче «MVP»: влито, в работе, заблокировано, осталось. Экраны: «MVP».

### Ф13. Приёмка MVP

**Когда.** Только под автопилотом и только для основной задачи «MVP» плана (Ф12): все задачи MVP закрыты, задача
«MVP» открыта и не заблокирована, очередь проекта
на этом компьютере не остановлена. Ведёт приёмку ведущий задачи «MVP» (Ф12): два координатора, которые одновременно
увидели «все задачи закрыты», приёмку начинают один раз. Перед каждой записью итога ведущий перечитывает задачу
«MVP» (Ф9). В обычной очереди («В обычную очередь» или автопилот выключен) приёмки нет: экран «MVP» показывает «Все
задачи закрыты» и кнопку «Принимаю».

**Проверка.** Новый worktree на свежей базовой ветке → `setup` стенда → полная команда тестов → `up` → ожидание ответа
`url` → ревьюер проверяет MVP по критериям задачи «MVP», ТЗ и доске дизайна во встроенном браузере Orca → `down` →
worktree убран. `down` и уборка выполняются при любом исходе, ошибке тоже. Стенда в настройках нет — задача «MVP»
заблокирована с просьбой добавить стенд.

**Раунды** — как в ките. Раунд — проверка, после которой то, что не прошло, стало задачами того же MVP (в пределах
`total`, операцией по правилу Ф12: комментарий «Приёмка: раунд r начат» с id операции и полным набором задач — он же
комментарий начала) с комментарием «Приёмка не прошла: раунд <r> из 2». В одном цикле не больше
двух раундов: третья не прошедшая проверка — комментарий «Приёмка MVP не прошла за 2 раунда» с итогом, метка
`agent-queue:blocked` на задаче «MVP», уведомление. Проверка прошла — комментарий «MVP готов к вашей приёмке» с
числом задач MVP, метка `agent-queue:blocked`, уведомление. Цикл начинается заново после каждого итога для владельца
(«готов» или «не прошла за 2 раунда»): исправления после него снова получают два раунда. Раунды считаются по этим
комментариям задачи «MVP», а не по памяти плагина.

**Владелец.** «Открыть стенд» (когда итог — «готов» или «не прошла за 2 раунда») — плагин поднимает стенд базовой
ветки (`setup`, `up`) и открывает `url` во встроенном браузере Orca; «Закрыть стенд» — `down` и уборка. «Принимаю»
— два условия:

- под автопилотом: показан, только когда последний итог — «готов» и с него не добавлено задач MVP; при нажатии плагин
  перечитывает задачу «MVP»: все её задачи закрыты, и их число то же, что в комментарии «готов»;
- без автопилота: показан, когда все задачи MVP закрыты; при нажатии плагин перечитывает задачу «MVP» и её задачи
  прямо перед закрытием.

Условие выполнено — метки `agent-queue:autopilot` и `agent-queue:blocked` сняты (если были), комментарий «MVP принят
владельцем», задача «MVP» закрыта, проект дальше живёт обычной очередью; иначе отказ с причиной («Есть открытые задачи
MVP: #…», «Есть задачи MVP после итога»), ничего не изменено. «Есть замечания» (при
любом итоге) — агент старта в терминале Orca уточняет их с владельцем и кладёт файл задач того же MVP; плагин ставит
их операцией с id (как план, Ф11, в пределах `total`) и снимает блокировку — автопилот продолжает, потом снова
приёмка. Экраны: «MVP».

- К13.1. Тест: закрыта последняя задача MVP под автопилотом → в порядке: worktree базовой ветки, `setup`, полные
  тесты, `up`, ответ `url`, ревьюер с критериями MVP и адресом стенда, `down`, worktree убран.

- К13.4. Тест: проверка прошла → комментарий «MVP готов к вашей приёмке» с числом задач, метка

  замечания».
- К13.5. Тест: «Принимаю», все задачи закрыты и их число то же → метка `agent-queue:autopilot` снята, задача «MVP»

  проекта».
- К13.7. Тест: третья проверка цикла не прошла → комментарий «Приёмка MVP не прошла за 2 раунда», блокировка «MVP»;
  на экране «MVP» есть «Есть замечания» и «Открыть стенд», нет «Принимаю».

- К13.10. Тест: сбой после создания первой задачи раунда, повтор делает координатор с другим id и пустым каталогом

  запускается; до отметки конца задачи раунда не берутся.
- К13.11. Тест: два координатора одновременно видят «все задачи MVP закрыты» → приёмку начинает один (ведущий задачи
  «MVP»), второй стенд не поднимает.

### Ф14. Три системы, поставка и релиз

Плагин работает на macOS, Windows и Linux: пути, каталог данных, запуск команд проекта, git, `gh`, CLI Orca и агентов
— по правилам системы; команда тестов идёт оболочкой системы, на Windows — команда для Windows из настроек, если
задана. Манифест: id `agent-queue`, имя «Agent Queue» (решение владельца).

**CLI Orca.** Окружение воркера отфильтровано, `ORCA_CLI_COMMAND` в нём не гарантирована, поэтому плагин ищет CLI сам:
`ORCA_CLI_COMMAND`, если задана; иначе по системе — на Linux `orca-ide` (голый `orca` на Linux — никогда: вне
терминала Orca это экранный диктор GNOME), на macOS и Windows `orca` (так CLI Orca называется там по документации
Orca 1.4.273); не нашёлся в PATH — известный путь CLI в установке Orca этой системы. Не нашёлся вовсе — «Проверка
проекта» показывает проблему «CLI Orca не найден», а действия, которым он нужен (worktree, показы старта), не
начинаются. Найденный CLI проверяется ответом `orca status`.

Папка плагина проходит `plugin inspect` CLI Orca: инструменты разработки не кладут в неё симлинков (сейчас
`node_modules/.bin/tsc` заготовки ломает `inspect`). Установка зависимостей в подготовке worktree (`orca.yaml`) и
запуск TypeScript в `make test` меняются вместе, одной задачей, вместе с командой подготовки в README: установка без
bin-ссылок, TypeScript — по пути его пакета, а не через `node_modules/.bin`. GitHub Actions на `ubuntu-latest`, `macos-latest`,
`windows-latest`: CLI Orca из релиза Orca (как в пробном плагине: пакет Orca, CLI под Electron в режиме Node),
`plugin validate`, проверка типов и тестов плагина (`plugin test`); проверка поставки — на чистой выгрузке коммита
(`git archive`, без `node_modules` и `.orca`): `plugin inspect` проходит. Релиз: версия в манифесте, запись для
каталога Orca из `plugin release-entry` релизного коммита (запускается во временном клоне), README с установкой и
требованиями.

- К14.1. Тест: путь worktree и каталога данных на подделке Windows (`win32`) и macOS (`darwin`) → путь по правилам
  этой системы, без смешения разделителей.

  «Agent Queue»; после обычной подготовки worktree (`setup` из `orca.yaml`) и после команды подготовки из README в

### Ф16. Демо-стенд для приёмки этого MVP

Этот MVP принимает автопилот agent-queue-kit на стенде с адресом, а у панели на компонентах Orca своего адреса нет.
Демо-стенд даёт его только на подделках (решение владельца «Только подделки»), без воркера плагина и без настоящих
`gh`, git и агентов, и ничего не загружает в Orca:

- **Сценарии.** Для каждого экрана и состояния раздела «Экраны» — сценарий проверки панели (`panel.check`) с
  подставным хостом Orca и придуманными данными; ответы воркера (`plugin.request`) задаёт сценарий.
- **Действия владельца** (кнопки и поля экранов) проверяет `plugin test` через `orca/testing` (`mount`, нажатие,
  ввод, выбор с подставными ответами `plugin.request`). У каждого действия два сценария, «до» и «после»; данные
  сценария «после» берутся из того же файла, что и ожидание теста. Стенд показывает оба кадра и итог теста.
- **Демо-копия.** `stand-setup` собирает во временном каталоге демо-копию панели принимаемого коммита: манифест с id
  `agent-queue-demo`, профиль `execution: sandboxed-ui` (профилю `trusted-worker` нужен `main`), без `main` (воркера
  нет — координатор и сторож не запускаются, `gh`, git и агенты не вызываются), только вклад панели — вклады,
  которым нужен воркер (команды, хуки, события, строка состояния), удалены; из разрешений (`capabilities`) остаются
  только те, что профиль `sandboxed-ui` допускает для панели, остальные (например `terminal:send` воркера) удалены;
  `plugin validate` демо-копии проходит.
- **Съёмка** — в `stand-setup`, не в `stand-up`: приёмка кита ждёт ответа адреса стенда не дольше 300 секунд после
  `up`. Каждый кадр — только `plugin shot <папка демо-копии> --scenario <имя> --width <W> --theme <light|dark> --out
  <файл> --json` CLI Orca; загрузки в Orca, `--act` и `--window` нет (`--scenario` с ними несовместим или требует
  загруженного плагина). Ширины: 390 — панель на всю ширину кадра; для компьютера — панель шириной 420, а страница
  стенда вставляет её кадр в нарисованную рамку окна Orca шириной 1440 — ту же, что на доске дизайна; рамка — рисунок
  стенда, это сказано на странице. Кадр принят, когда ответ `--json` называет этот сценарий, `settled: true`, пустой
  `errors` и `themeApplied: true`; первый непринятый кадр останавливает съёмку. Съёмка со сценарием идёт только при
  свёрнутом или скрытом окне Orca: `stand-setup` ждёт этого не дольше 10 минут, потом выходит с ненулевым кодом и
  текстом «Сверните окно Orca» (пункт «Только владелец»).
- **Текст рядом с кадром.** Дерево экрана текстом (`tree()` или `summary()` из `orca/testing`): ревьюер кита делает
  скриншоты только при видимой вкладке и проверяет тексты и элементы без картинки.
- **Страница.** `stand-up` только отдаёт готовую страницу на `http://127.0.0.1:<порт>` — кадры по экранам и
  состояниям, кадры действий владельца, деревья текстом, итоги `plugin check` и тестов плагина (поведение воркера
  проверяют они, на подделках); при неполном наборе кадров `stand-up` падает. `stand-down` останавливает страницу и
  удаляет временный каталог.

Ревьюер приёмки открывает страницу во встроенном браузере Orca и сверяет кадры и деревья с доской дизайна и
критериями. Экраны: нет (стенд показывает экраны панели).

- К16.1. Тест: у каждого экрана и состояния раздела «Экраны» есть сценарий проверки панели, и у каждого сценария —
  экран и состояние из этого раздела.
- К16.2. Тест: `plugin check` CLI Orca на демо-копии рендерит все сценарии без ошибок.
- К16.3. Тест: демо-копия, которую собирает `stand-setup`, — манифест с id `agent-queue-demo`, профилем
  `sandboxed-ui`, без `main` и без вкладов, которым нужен воркер; в ней нет файлов воркера; основной манифест
  объявляет `terminal:send` → в демо-манифесте его нет; `plugin validate` демо-копии проходит.
- К16.4. Тест: страница стенда, собранная из набора кадров, перечисляет каждый сценарий с кадрами 390 и в рамке 1440,
  кадры «до» и «после» каждого действия владельца с итогом его теста, дерево каждого экрана и итоги `check` и тестов.
- К16.5. Тест (поддельный CLI Orca, который отклоняет `--scenario` вместе с `--act` и отказывает при видимом окне):
  при свёрнутом окне `stand-setup` снимает полный набор кадров только командами `plugin shot … --scenario … --json`;
  кадр с `settled: false` или непустым `errors` останавливает съёмку с ошибкой; `stand-down` после `stand-up` —
  страница не отвечает, временный каталог удалён.
- К16.6. Тест: окно Orca видимо дольше 10 минут → `stand-setup` выходит с ненулевым кодом и текстом «Сверните окно
  Orca», страницы нет.

  завершён: план ставится» без «Начать MVP»; публикация требует действия владельца — что сделать и «Повторить
  публикацию»; план не прошёл проверку или маска сработала на итоговом коммите — шаг «План» с причиной.
- Переходы: «Открыть чат старта» и «Есть правки» → терминал агента в Orca; «Открыть показ» → артефакт в браузере;
  «Да» и «В обычную очередь» → «MVP»; «Правки» → «Старт MVP» на шаге «План»; «Назад» → «Очередь».

## Вне MVP

- Перенос проектов, которые работают на agent-queue-kit (их очередей, `.agent-queue/`, открытых задач), на плагин:
  решение владельца «Свой формат» — отдельная работа после MVP, до неё они живут на ките, а мастер подключения их не
  предлагает.
- GitLab: в MVP только GitHub (решение владельца «Issues GitHub»).
- Ревью документов по правилу входа и согласование макетов дизайн-задач перед постановкой: сессия предложила их
  отложить (вопрос блока 3), владелец выбрал состав MVP без них. Ревью документов при старте MVP (Ф11) — в MVP.
- Тесты на настоящем GitHub и тестовый репозиторий для приёмки: решение владельца «Только подделки».
- Работа координатора и сторожа, когда Orca закрыта.
- Очередь самого плагина и его самообновление в стиле `bin/activate` кита: обновления — через каталог Orca.
- Деплой на прод.

## Только владелец

Что делает или даёт только владелец: аккаунты, ключи, оплата, домен, доступы внешних сервисов. Автопилот не делает
этого сам, а зовёт владельца.

- Внести плагин в каталог Orca со своего аккаунта — нужен для Ф14 (релиз); задача MVP готовит запись релиза.
- Включить GitHub Actions в репозитории плагина (у частного репозитория считаются минуты) — нужен для Ф14 (К14.3
  проверяет workflow, сам прогон на трёх системах — в Actions).
- Аккаунт Orca с включённой публикацией артефактов — нужен для показов старта MVP (Ф11) у каждого пользователя;
  у владельца он уже есть.
- Свернуть окно Orca на время приёмки этого MVP — нужен для Ф16: съёмка демо-стенда идёт только при свёрнутом или
  скрытом окне.
